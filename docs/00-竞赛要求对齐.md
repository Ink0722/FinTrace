# FinTrace 竞赛要求对齐与实施总方案

## 1. 文档目的

本文档将赛题的现实业务场景、三项技术攻关任务、量化指标和成果交付，映射到 FinTrace 的系统模块、比赛数据、补充数据、评测方法和实施阶段。

它是项目设计文档的最高层入口。数据用途和工具边界见 [01-数据与工具总览.md](01-数据与工具总览.md)，各专项设计见后续编号文档。

本文档区分三种状态：

| 状态 | 含义 |
|---|---|
| `已有基础` | 当前代码已存在且有测试覆盖的能力 |
| `比赛数据可实现` | 使用已提供五组数据可以落地，但代码尚需开发 |
| `需要补充` | 仅靠当前数据不能验证，必须补充数据、标注或模块 |

答辩材料必须如实使用这些状态，不把设计目标描述为已经实现的结果。

## 2. 业务场景与产品定位

赛题面向个人投资者金融信息服务。用户需求已经从简单检索升级为连续追问、多源查证和风险推演，但现有金融对话系统存在三个核心问题：

1. 长周期对话中容易遗忘公司、人物、期间和历史结论，工具调用又会随着话题变化发生错配；
2. 搜索结果通常停留在直接股东或单篇文本，不能还原多层持股、控制关系和事件演化；
3. 单表问答只能复述财务数字，难以完成跨报表、跨期间和跨科目的审计式勾稽。

FinTrace 因此定位为：

> 面向个人投资者的证据驱动型金融 Agent。系统通过分层记忆维持长周期上下文，通过确定性工具完成数据查询、图路径计算和财务勾稽，通过证据账本约束大模型解释，在无法获得可靠证据时明确拒绝猜测。

“全能型金融 AI 幕僚”是产品愿景，不意味着模型可以脱离数据源回答所有金融问题。可靠的能力边界和正确拒答是防幻觉设计的一部分。

## 3. 总体技术架构

```text
CLI / FastAPI / Web Demo
          |
          v
LangGraph Agent Harness
  - 会话加载与分层记忆
  - 实体、时间和意图解析
  - LLM Planner + 能力注册表
  - 计划与参数校验
  - 工具执行、受控重试和计划修复
  - 证据账本与回答校验
          |
          +----------------+----------------+----------------+
          |                |                |                |
 document_search  ownership_penetration  event_timeline  financial_risk_analysis
          |                |                |                |
    SQLite + FAISS   时序关系表/图库   事件表+文档库      财务宽表+指标层
          \______________________  ________________________/
                                 \/
                     统一证券主表与证据协议
```

架构坚持“一个主 Agent + 多个确定性工具”。复杂性放在可测试的数据接口、图算法、财务规则、状态管理和证据校验中，不依赖无限 ReAct 循环，也不为了形式上的多智能体而拆分多个自由对话模型。

## 5. 任务 1：长对话记忆与自适应路由

### 5.1 0.5M Tokens 的正确实现方式

赛题中的 0.5M Tokens 应理解为长周期会话历史规模，不应把全部历史在每轮原样塞入模型。FinTrace 使用四层记忆：

```text
L1 最近原始消息
  最近 4～8 轮，保留原文和局部推理所需上下文

L2 结构化会话状态
  公司、人物、比较对象、期间、指标、当前任务和待澄清项

L3 滚动摘要
  压缩较早话题、决策和未完成问题，保留版本与覆盖轮次

L4 已验证事实库
  只保存经过工具和证据验证的历史结论，可按实体、时间和主题检索
```

系统累计管理的历史可以超过 0.5M Tokens，但每轮送入模型的是经过检索和预算控制的必要上下文。这样既验证长期记忆，也避免依赖特定模型的超长输入上限。

### 5.2 记忆写入约束

- 用户偏好和对话目标可以写入会话记忆；
- 公司、期间和比较对象写入结构化上下文；
- 工具验证后的事实可以写入长期事实库；
- 模型猜测、失败结果和未验证数字不得写入长期事实库；
- 新话题不触发硬编码清空提示，由 Agent 自主判断是否使用历史；
- 每条长期事实保存证据 ID、生成 Turn、有效期和来源工具。

### 5.3 自适应路由

Planner 不仅看到工具名称，还应读取机器可读能力注册表：

```text
工具支持的意图
所需参数
数据时间范围
数据更新频率
可返回的证据类型
已知限制
```

路由流程：

```text
问题 + 必要会话上下文
  -> 候选能力检索
  -> LLM Planner 生成工具计划
  -> Schema 和能力范围校验
  -> 工具执行
  -> 结果完整性校验
  -> 回答、修复、重试或结构化拒答
```

### 5.4 自纠错闭环

自纠错必须是可观测的状态转移，而不是让模型无限尝试：

| 失败 | 处理 |
|---|---|
| 计划缺少必要工具 | 重新规划一次 |
| 公司同名或参数不完整 | 参数修复或要求澄清 |
| 参数格式错误 | 根据 Schema 修复一次 |
| 工具临时超时 | 使用相同幂等调用重试一次 |
| 数据源无覆盖 | 停止重试并返回 `unsupported` 或 `insufficient_evidence` |
| 证据不足 | 降低回答范围，不生成确定结论 |
| LLM 失败 | 返回结构化错误，不使用确定性答案冒充模型输出 |

每次修复保存原计划、错误类型、修复动作和最终状态，用于计算自纠错成功率。

### 5.5 任务 1 评测集

数据组 1 提供 35 个 Session、1,410 个 Turn，适合自然多轮回放，但还不足以单独验证 0.5M Tokens。评测分三层：

1. 原始会话回放：测试跨领域切换、拒答和工具选择；
2. 人工标注核心集：测试实体、期间、工具和事实准确率；
3. 长历史压力集：在会话历史中注入经过标注的早期事实、长文档和干扰信息，将累计历史扩展到 0.5M Tokens，再测试关键事实召回。

压力集必须保留标准事实位置、首次出现轮次、干扰实体和证据 ID，不能只统计模型是否“感觉记得”。

### 5.6 动态金融 API 适配

赛题明确要求 Agent 判断何时调用行情、宏观等动态数据源。仅返回 `unsupported` 可以证明系统不胡说，但不足以完整展示动态 API 路由能力。竞赛增强版至少应接入一类合法可用、可稳定复现的动态数据接口，优先顺序为：

1. 市场行情和交易日历；
2. 新闻或公告增量数据；
3. 宏观指标；
4. 用户授权后的自选股或持仓数据。

所有外部接口通过统一 Adapter 接入：

```text
capability metadata
request schema
response schema
freshness timestamp
source attribution
timeout and retry policy
rate-limit policy
```

演示和评测必须记录数据时间戳。接口不可用时返回结构化错误，不允许切换为大模型记忆答案。为保证复现，可保存经过授权的固定响应快照用于离线评测，但演示时必须明确区分实时模式和回放模式。

## 6. 任务 2：动态图谱、股权穿透与事件脉络

### 6.1 图谱不是静态 CSV 转图

动态知识图谱由多种来源共同构建：

```text
结构化股东快照
公告、招股说明书和年报文本
未来可接入的中证企业或工商关系
新闻舆情文本
```

统一实体类型至少包括：

```text
PERSON
COMPANY
LISTED_COMPANY
FUND
ASSET_MANAGEMENT_PLAN
REGULATOR
EVENT
DOCUMENT
```

统一关系至少包括：

```text
OWNS
CONTROLS
ACTS_IN_CONCERT
VOTING_RIGHTS
LEGAL_REPRESENTATIVE
RELATED_PARTY
INVOLVED_IN
DISCLOSED_BY
```

每条关系必须保存生效日期、失效日期、公告日期、来源文档、证据片段、抽取方式和置信状态。

### 6.2 数据组 2 的定位

十大股东快照用于建立高质量 `OWNS` 基线和部分上市公司多跳路径。它不能独立完成赛题要求的“穿透到底”，因此需要补充：

- 招股说明书中的发行前股权结构；
- 年报中的主要子公司和实际控制人信息；
- 控制权变更、一致行动和表决权协议公告；
- 中证企业或合法工商关系数据；
- LLM 文本抽取后经校验的关系。

文本抽取关系进入 `candidate` 状态，必须经过 Schema 校验、实体消歧、来源一致性或人工复核后才能用于确定性控制链回答。

### 6.3 图存储选择

第一版使用 SQLite 时序边表和 NetworkX 完成可复现路径查询。满足以下任一条件时迁移或同步 Neo4j：

- 关系规模和多类型查询使 SQLite 子图装载成为瓶颈；
- 需要频繁执行多跳模式匹配和图数据库可视化；
- 5 秒性能指标无法通过索引、子图裁剪和缓存达到；
- 答辩演示需要展示动态图谱查询。

Neo4j 是增强实现，不应在数据关系尚未可靠时成为先决条件。

### 6.4 股权穿透算法

```text
自然语言目标
  -> 实体消歧
  -> 查询日期解析
  -> 按时点构建相关子图
  -> 反向裁剪可达节点
  -> 有界简单路径搜索
  -> 每跳关系与比例校验
  -> 间接比例计算
  -> 路径排序、截断和证据组装
```

普通持股路径的间接比例可按每跳比例相乘。`CONTROLS`、一致行动和表决权关系不能用同一乘法替代法律控制判断，应单独标记路径类型。

### 6.5 事件抽取与聚类

事件管线：

```text
公告/新闻正文
  -> 文档解析与 Chunk
  -> 实体、时间、事件类型和事实槽位抽取
  -> Schema 校验和证据绑定
  -> 同公司、同主题候选召回
  -> 时间窗口、实体重合和文本相似度聚类
  -> 事件簇标题与摘要
  -> 与股权边和财务信号按时间对齐
```

当前数据组 3 只有违规公告索引。它可以构建标题级时间线和正文下载入口，但“海量新闻舆情聚合”仍需补充新闻数据源或赛方允许使用的公开语料。

事件时间线默认表达时序和证据关联，不自动声称事件之间存在因果关系。若回答使用“导致”，必须有正文证据或明确标记为机构观点。

### 6.6 任务 2 评测

- 构建深度大于 3 的人工复核路径集；
- 每条路径标注实体、关系类型、方向、比例、时点和证据；
- 端到端准确要求整条路径全部正确；
- 比例采用明确容差，缺失比例不得由模型猜测；
- 事件集标注核心节点、日期、类型、实体和所属事件簇；
- 图工具延迟统计使用预热后的 P50、P95 和最大值，并单独记录数据库查询与结果组装。

当前股东快照能用于构造部分基准，但不足以保证存在足量的真实三层以上控制链，需要补充案例数据。

## 7. 任务 3：财务异象甄别与解释报告

### 7.1 确定性财务引擎

```text
三张财务宽表
  -> 标准指标映射
  -> 公司类型和期间口径判断
  -> 同比、单季和跨表派生指标
  -> 规则适用性判断
  -> 风险信号和多维评分
  -> 证据化报告
```

大模型不直接计算财务指标。每个规则由程序保存：

```text
rule_id
适用公司类型
所需指标
比较期间
计算公式
阈值
triggered / not_triggered / not_evaluable
输入证据
解释模板
```

### 7.2 第一版规则域

| 规则域 | 当前数据支持 | 说明 |
|---|---|---|
| 利润与经营现金流背离 | 支持 | 使用同口径同比及现金流/利润比 |
| 存货与收入背离 | 支持 | 需结合存货余额和累计收入口径 |
| 应收账款与收入背离 | 支持 | 注意金融企业适用性 |
| 毛利率异常 | 部分支持 | 非金融企业可计算，需同行或历史基线 |
| 偿债压力 | 支持 | 资产负债率、流动比率、短债等 |
| 期间费用异常 | 部分支持 | 利润表可扩展销售、管理、研发、财务费用规则 |
| 异常汇兑 | 部分支持 | 需确认字段覆盖和公司适用性 |
| 非经常性损益依赖 | 当前不可评估 | 本批扣非净利润候选字段无有效值 |
| 收入与税务勾稽 | 部分支持 | 主表只能提供税费相关代理指标，严谨判断需附注或税务口径 |
| 关联交易异常 | 当前不足 | 需要年报附注、关联方和交易明细 |
| 审计意见、问询信号 | 需文档数据 | 由公告和文档检索补充 |

### 7.3 风险评分

多维评分不能简单累加所有缺失规则：

```text
维度得分 = 已触发规则权重 / 当前可评估规则权重
覆盖率 = 可评估规则权重 / 全部目标规则权重
```

报告同时展示风险得分和规则覆盖率。覆盖率低时不能输出“整体低风险”。

### 7.4 财务欺诈 F1 的标签要求

当前三张报表没有“问题财报/正常财报”标签，不能直接计算 F1。需要建立专家标注基准：

- 正样本：监管处罚、财务造假、重大会计差错或强制更正等经可靠来源确认的公司期间；
- 负样本：同公司其他期间或同行对照，经规则定义和人工复核；
- 标签单位：`company_id + report_period + risk_type`；
- 使用时间切分或公司级切分，避免同公司相邻期间泄漏；
- 固定规则阈值后再运行测试集，不在测试集上反复调参；
- 报告 Precision、Recall、F1 和各风险类型表现。

公告标题分类不能直接作为财务欺诈正标签，必须读取正文并确认事件性质和对应报告期。

### 7.5 专家盲评

每份报告隐去系统版本，由至少两名具备财务背景的评审独立评价：

- 数据引用正确；
- 计算逻辑正确；
- 风险归因合理；
- 表述审慎；
- 证据可追溯；
- 结论完整清晰。

预先定义“优秀”阈值和分歧仲裁规则，优秀率目标不低于 80%。

## 8. 五组数据在竞赛任务中的角色

| 数据组 | 直接作用 | 对应任务 | 不能替代的内容 |
|---|---|---|---|
| 1 多轮问题 | Agent 回放和路由评测 | 任务 1 | 标准答案、0.5M 压力集和故障注入集 |
| 2 股东快照 | 主要股东、持股变化、部分多跳路径 | 任务 2 | 完整控制关系、非上市公司链和最终受益人 |
| 3 公告索引 | 监管公告定位、标题级时间线、PDF 入口 | 任务 2、任务 3 | 公告正文事实和新闻舆情全集 |
| 4 财务报表 | 指标、勾稽、规则和风险信号 | 任务 3 | 附注、审计意见、关联交易和欺诈标签 |
| 5 研报摘要 | 机构观点检索和风险解释 | 任务 2、任务 3 | 客观事实、研报全文和完整一致预期 |

这些缺口应转化为明确的补充数据任务，而不是交给大模型自由发挥。

## 9. 量化指标定义

### 9.1 长文本关键事实 Recall

```text
Recall = 正确召回的标注事实数 / 应召回的标注事实总数
```

事实必须同时满足实体、属性、值和时间口径正确。仅提到相似主题不算召回。

### 9.2 回答准确率

以 Turn 为单位，要求可回答性决策正确、关键事实正确且无红线幻觉。部分回答按预先定义规则计分，不由裁判临时决定。

### 9.3 工具调用 Precision

```text
Tool Precision = 正确且必要或允许的工具调用数 / 全部工具调用数
```

同时报告必要工具 Recall，防止系统通过少调用工具虚高 Precision。

### 9.4 自纠错成功率

```text
Recovery Success = 最终成功且结果正确的可恢复故障案例数 / 全部可恢复故障案例数
```

不可恢复的数据缺失不进入分母，但系统错误地反复重试应计为失败。

### 9.5 股权穿透端到端准确率

一条案例只有在目标实体、全部路径节点、边方向、关系类型、比例、时点和证据均满足标准时才算成功。另行报告逐跳准确率用于诊断。

### 9.6 事件关键节点 Recall

```text
Event Recall = 正确召回的金标核心事件节点数 / 金标核心事件节点总数
```

事件还需检查日期、主体、类型、证据和簇归属。时序连续性由规则检查加专家复核。

### 9.7 财务风险 F1

```text
Precision = TP / (TP + FP)
Recall = TP / (TP + FN)
F1 = 2 * Precision * Recall / (Precision + Recall)
```

按风险类型和总体分别报告，`not_evaluable` 不得悄悄计为负类。

## 12. 答辩表达原则

1. 将“证据驱动、防幻觉、自适应工具闭环”作为贯穿三项任务的统一主线；
2. 展示真实数据、真实工具调用和证据，而不是只展示大模型回答；
3. 明确区分已实现、数据可实现和后续扩展；
4. 股东快照只称有限持股穿透，完整控制链来自增强图谱；
5. 公告索引只称标题级线索，正文解析后才升级为事实事件；
6. 财务异常只称风险信号，监管或专家确认后才可作为欺诈标签；
7. 0.5M Tokens 的创新点是分层记忆和检索，不是把全部文本暴力塞入 Prompt；
8. 所有量化指标必须给出数据集、公式、运行环境和可复现报告。

## 14. 最终原则

FinTrace 的最终方案必须同时满足“业务问题真实、工具计算可靠、证据能够追溯、指标可以复现”。现有比赛数据是核心底座，但不是全部任务的完整答案。

项目应先用现有数据把四个工具做实，再有针对性地补充长记忆压力集、控制关系、舆情语料和财务风险标签。这样既贴合竞赛要求，也避免用架构名词掩盖数据和验证不足。
