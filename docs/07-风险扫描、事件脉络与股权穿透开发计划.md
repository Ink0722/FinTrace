## 2. 共同实现原则

1. 离线构建负责解析、标准化、实体统一和索引冻结；在线工具只读 SQLite/索引，不临时读取原始大文件。
2. 所有调用使用统一 `ToolCall`，所有结果使用统一 `ToolResult`，失败必须返回结构化 `ErrorType`。
3. `knowledge_cutoff` 由工作流注入，Planner 无权扩大；历史问题还要遵守报告期、快照日、披露日和事件日的语义。
4. 工具只返回可复核结果，不生成投资建议或自由文本结论。
5. 关键结果必须带 `evidence_id`；计算结果还要保留输入、公式、规则或路径。
6. 空结果只表示当前索引未命中，不证明现实中不存在风险、事件或股权关系。

## 3. 财务风险扫描

### 3.1 调用契约

真实参数模型是 `tools/financial_analysis/interface.py::RiskScanArguments`：

```json
{
  "operation": "risk_scan",
  "company_ids": ["600519.SH"],
  "report_periods": ["2022-12-31", "2023-12-31", "2024-12-31"],
  "requested_periods": ["2024-12-31"],
  "target_period": "2024-12-31",
  "period_resolution_mode": "history_until_target",
  "rule_ids": null,
  "focus_topics": null,
  "knowledge_cutoff": "2026-05-28"
}
```

硬约束：

- 仅允许一个公司；
- `report_periods` 必须同为年报、同为一季报、同为半年报或同为三季报；
- `rule_ids` 与 `focus_topics` 不能同时提供；
- 未指定风险主题时运行全部规则；
- 用户指定单一目标年度时，确定性期间解析器可以扩展为截至该年度的同口径历史；
- 用户未指定期间时，优先选择截止日前全部年度数据。

期间选择实现位于 `harness/routing/financial_period_resolver.py`，工具参数一致性由 `harness/routing/action_validator.py` 校验。审查时要确认 Planner 不能把示例年份或未来年份写回工具参数。

### 3.2 规则与输出

规则目录位于 `tools/financial_analysis/risk_catalog.py`，版本为 `financial-risk-rules-v2`。当前八条规则覆盖：

- 利润与经营现金流背离；
- 应收账款与收入背离；
- 存货与收入背离；
- 流动性压力；
- 毛利率/营业利润率波动；
- 经营现金流持续为负；
- 销售收现与收入背离；
- 资产负债率压力。

规则计算位于 `tools/financial_analysis/risk_rules.py`，汇总位于 `tools/financial_analysis/risk_scan.py`。每条规则必须返回 `triggered`、`not_triggered`、`insufficient_data` 或 `not_applicable`，并给出逐期间观察、输入证据、阈值和公式。`insufficient_data` 与 `not_applicable` 不能解释成低风险。

当前阈值标记为 `expert_initial / uncalibrated`，`overall_score` 固定为 `null`，`scoring_status=disabled_until_calibrated`。这是有意的安全边界：在独立金标完成前不输出没有依据的综合分。

### 3.3 审查清单

- Repository 是否只查询截止日前披露且同口径的数据；
- 指标映射是否与 `tools/financial_analysis/metric_catalog.py` 的版本一致；
- 相邻期间比较是否遍历所有有效期间，而非只比首尾；
- 分母为零、负值和缺失值是否进入正确状态；
- `triggered_signals` 是否只是 `signals` 的受控子集；
- 每条输入指标能否回溯到财务行级证据；
- 最终回答是否将“风险信号”错误升级为“财务造假”。

## 4. 事件脉络

### 4.1 数据与调用契约

事件索引由 `data_pipeline/events/build_index.py` 从 normalized 公告标题离线构建，当前 mapping version 为 `announcement-events-v3.1`。在线参数模型是 `EventTimelineArguments`：

```json
{
  "operation": "event_cluster",
  "entity_ids": ["600519.SH"],
  "start_date": "2020-01-01",
  "end_date": "2024-12-31",
  "event_types": ["regulatory_inquiry", "risk_warning"],
  "keywords": null,
  "limit": 100,
  "window_days": 30,
  "knowledge_cutoff": "2026-05-28"
}
```

当前每次只支持一个主体；`window_days` 只允许用于 `event_cluster`；未知事件类型、倒置日期和过大 limit 在 Pydantic 层拒绝。

### 4.2 `event_query` 与 `event_cluster`

`event_query` 在 `tools/event_timeline/repository.py` 中按主体、类型、日期、关键词和截止日筛选排序，不进行自由摘要。无匹配时返回 `DATA_NOT_AVAILABLE` 及诊断字段，Agent 必须表述为“索引未命中”。

`event_cluster` 在 `tools/event_timeline/timeline.py` 中对查询结果进行有界聚合：

- 同类型事件可根据稳定文号或规范化主题签名聚合；
- 跨类型关系只允许共享稳定文号等明确依据；
- 每个簇保留全部成员事件和 `evidence_ids`；
- `match_reasons` 解释为什么被合并；
- 聚类表示时间/主题相关，不表示因果。

标题无法提供精确发生日时，事件使用公告日并标记 `date_precision=announcement_only`。处罚金额、原因和整改细节需要再调用 `document_search` 取得正文证据，事件工具不得从标题猜测。

### 4.3 审查清单

- `SUPPORTED_EVENT_TYPES` 是否与 Parser、Planner 和 README 完全一致；
- 否定历史陈述是否在离线构建时被排除；
- `knowledge_cutoff` 是否同时约束查询与无匹配诊断；
- 同标题不同公司、同公司不同日期是否被错误去重；
- 聚类是否保留成员，是否出现无依据跨类型关系；
- 空结果是否被回答层误写成“公司从未发生”；
- `execution_time_ms` 是否仅覆盖工具内部查询和组装。

## 5. 股权穿透

### 5.1 能力边界与实体桥接

底层数据是上市公司主要股东快照，不是完整工商股权库。可证明的基础边为 `holder_entity_id -> target_company_id`。只有企业股东经过 `entity_master.sqlite` 确认为某上市公司同一法定主体时，路径搜索才可从该上市公司节点继续扩展。

实体统一由 `data_pipeline/entity_resolution/` 离线完成，确认关系写入 ownership SQLite 的 `holder_company_links`。模糊匹配、同名歧义和待审候选不能进入在线图。`data_pipeline/ownership/build_index.py` 负责生成 `ownership-holdings-v3` 索引及 manifest。

因此该能力的准确名称是“基于主要股东快照和已确认主体桥接的有限持股路径搜索”，不能据此宣称完整实控人、最终受益人或全量控制链。

### 5.2 调用契约与算法

真实参数模型是 `PenetrationArguments`：

```json
{
  "operation": "penetration",
  "source_entity_id": "ENTITY-A",
  "target_entity_id": "000001.SZ",
  "as_of_date": "2024-12-31",
  "max_depth": 4,
  "max_paths": 10,
  "knowledge_cutoff": "2026-05-28"
}
```

`max_depth` 上限为 6，`max_paths` 上限为 50，起点和终点不得相同。名称型起点必须唯一解析；歧义和未找到分别返回 `ENTITY_AMBIGUOUS`、`ENTITY_NOT_FOUND`。

路径算法位于 `tools/ownership_analysis/penetration.py`：

1. 使用 BFS 队列优先返回较短路径；
2. Repository 针对每次扩展按 `as_of_date` 和 `knowledge_cutoff` 选择有效快照；
3. 当前路径的节点集合用于防环，不使用全局 visited 误删其他路径；
4. 每条边保留持股比例、快照日、披露日和证据；
5. `path_ratio` 为各跳比例乘积；多条路径不合并为总控制权；
6. 达到深度或路径上限时返回截断警告。

当前采用 SQLite 关系表即可满足已知数据规模。是否引入 Neo4j 应由关系类型、数据规模和查询性能证明，不是当前代码审查的缺失项。

### 5.3 审查清单

- `holder_company_links` 是否只导入 confirmed 同一主体关系；
- 历史查询是否按披露可见性和快照时点防前视；
- 每个中间节点是否使用自己的有效快照，而非终点公司的快照；
- 路径防环是否保留不同分支的合法路径；
- `path_ratio` 是否使用小数比例并正确逐跳相乘；
- 每一跳是否都有独立 `evidence_id`；
- 无路径、深度截断和数据覆盖不足是否均有明确限制。

## 6. Agent 组合调用

复杂调查不新增“综合工具”，而由 Planner 在统一工作流内组合原子能力：

```text
财务风险调查
  -> risk_scan
  -> 必要时 event_query / event_cluster
  -> 需要公告细节时 document_search
  -> final_answer

股权调查
  -> holding_query / holding_compare
  -> 起点、终点和时点明确后 penetration
  -> final_answer
```

审查重点不是“调用越多越好”，而是每一次调用是否解决明确证据缺口。无信息增益、重复参数或试图修改 `knowledge_cutoff` 的动作应由 `harness/routing/action_validator.py` 拒绝。

## 7. 完成与未完成的边界

已经实现并有自动化测试覆盖：

- 三项 operation 的参数 Schema、Repository 查询、结构化结果和错误；
- manifest 版本与源文件指纹校验；
- 防前视、空结果、边界状态和证据生成；
- capability、Planner、Validator、CLI 和 Agent 工作流接入。

尚不能主张完成：

- 财务风险 F1 不低于 85%；
- 三层以上股权路径端到端准确率不低于 85%；
- 事件关键节点 Recall 不低于 85%；
- 股权/事件工具所有正式样本均不超过 5 秒；
- 财务报告专家盲评优秀率不低于 80%。

上述结论必须等冻结金标、独立评测脚本和可复现报告完成后，登记到 `08-统一评测清单与实施记录.md`。
