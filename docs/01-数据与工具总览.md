# FinTrace 数据、工具与 Agent 能力映射

## 1. 文档目的

本文档定义比赛数据在 FinTrace 中的业务用途、标准化存储方式、工具归属、证据类型和能力边界，是后续数据导入、工具改造、Agent 路由和评测设计的上层依据。

在讨论 Excel 如何解析、字段如何转换或数据存在哪里之前，必须先回答以下问题：

1. 每份数据可以支持哪些事实和任务；
2. 哪些工具负责读取和计算这些数据；
3. Agent 在什么问题下应调用哪些工具；
4. 工具可以给出什么结论，不能给出什么结论；
5. 工具结果如何形成可追溯证据；
6. 数据不覆盖的问题应如何处理。

本设计不要求一个数据集只对应一个工具。一个数据源可以支持多个工具，一个工具也可以组合多个数据源，但必须明确主要用途、辅助用途和证据语义。

本方案的竞赛任务、量化指标和分阶段交付以 [00-竞赛要求对齐.md](00-竞赛要求对齐.md) 为上层依据。

### 1.1 与竞赛任务的关系

| 竞赛任务 | 本文档负责明确的内容 |
|---|---|
| 任务 1：长对话与动态路由 | 哪些工具和数据能力可供 Planner 选择，哪些问题必须拒答或补充外部 API |
| 任务 2：股权穿透与事件脉络 | 股东、公告、正文和未来图谱数据如何共同服务股权与事件工具 |
| 任务 3：财务异象与解释报告 | 财务事实、派生指标、风险信号和研报观点如何分层使用 |

现有五组数据是竞赛系统的核心底座，但不是全部技术指标的完整评测材料。0.5M Tokens 压力集、三层以上控制链金标、新闻舆情语料和财务风险标签需要单独补充。

## 2. 系统分层

FinTrace 应明确区分五个层次：

```text
原始比赛数据
  -> 标准化数据与索引
  -> 数据访问接口
  -> 确定性工具
  -> Agent 规划与回答
```

### 2.1 原始比赛数据

包括 Excel、CSV、数据字典和公告链接。原始目录保持只读，作为数据来源和审计依据，不直接承担在线查询。

### 2.2 标准化数据与索引

包括：

- SQLite 结构化表；
- 文档和 Chunk 元数据；
- FAISS 向量索引；
- 股权快照及动态投影图；
- 数据导入清单和质量报告。

该层负责统一类型、日期、主体标识、字段名称、质量标志和证据 ID。

### 2.3 数据访问接口

工具通过 Repository 或 DataSource 接口读取数据，不直接依赖某个 Excel 文件。CSV 可以作为测试实现，SQLite 作为比赛数据的正式实现，未来还可以增加数据库或外部 API 实现。

### 2.4 确定性工具

工具负责：

- 精确查询；
- 数值计算；
- 图路径搜索；
- 时间过滤；
- 规则判断；
- 数据校验；
- 证据生成。

大模型不能代替工具计算财务指标、股权比例或读取大规模原始表格。

### 2.5 Agent 规划与回答

Agent 负责：

- 理解当前问题和必要上下文；
- 选择工具和构造参数；
- 组合多个工具的结果；
- 根据证据生成自然语言回答；
- 在数据不足时部分回答、澄清或拒答。

所有事实性结论必须来自工具证据，不允许大模型凭记忆补充实时行情、财务数字或公告细节。

## 3. 五组比赛数据总览

| 数据组 | 内容 | 系统角色 | 主要工具 | 辅助工具 |
|---|---|---|---|---|
| 1 | 多轮问题集 | 评测输入 | 无 | 评测回放器与裁判 |
| 2 | 十大股东快照 | 结构化股权证据 | `ownership_penetration` | `event_timeline` |
| 3 | 违规公告索引 | 结构化事件证据和文档入口 | `event_timeline` | `document_search` |
| 4 | 三张财务报表 | 结构化财务证据 | `financial_risk_analysis` | `event_timeline`、`document_search` |
| 5 | 研报元数据和摘要 | 文本检索和机构观点证据 | `document_search` | `financial_risk_analysis` |

“辅助工具”表示该数据可以为其他工具提供补充证据或派生事件，不表示这些工具可以绕过自己的核心数据源。

## 4. 数据组 1：多轮问题集

### 4.1 数据角色

多轮问题集只用于：

- 向 Agent 提供评测输入；
- 回放 35 个独立会话；
- 评估多轮上下文、工具选择、可回答性判断和答案质量；
- 测试重复问题下的运行稳定性。

### 4.2 禁止用途

该数据不得：

- 作为事实证据；
- 加入生产知识库供 Agent 检索答案；
- 参与金融事实计算；
- 向被测 Agent 泄露预期工具、可回答性或评分标签。

推荐存储位置：

```text
evaluation/datasets/multi_turn_questions.jsonl
evaluation/labels/multi_turn_labels.jsonl
```

评测设计详见 [02-多轮评测方案.md](02-多轮评测方案.md)。

## 5. 数据组 2：十大股东快照

### 5.1 主要工具

十大股东快照主要支撑 `ownership_penetration`。工具内部建议支持：

| 查询模式 | 用途 |
|---|---|
| `snapshot` | 查询指定公司在指定时点的主要股东 |
| `change` | 比较两个时点的主要股东变化 |
| `concentration` | 计算第一、前三、前五或前十大股东集中度 |
| `paths` | 查询能够可靠连接的有限多层持股路径 |

### 5.2 辅助工具

股东快照可以为 `event_timeline` 生成派生事件：

- 股东进入主要股东名单；
- 股东退出主要股东名单；
- 持股数量或比例显著变化；
- 股权集中度显著变化；
- 限售股份结构变化。

这些事件必须标记为 `derived_event`，不能伪装为公告原文中的披露事件。“退出主要股东名单”也不等于已经清仓。

### 5.3 数据边界

该数据不能单独确认：

- 完整工商股权结构；
- 最终受益所有人；
- 一致行动关系；
- 表决权委托或协议控制；
- 实际控制人；
- 完整控制链。

由该数据形成的原始图关系应标记为 `OWNS`，不得直接标记为 `CONTROLS`。

详细设计见 [03-股东快照设计.md](03-股东快照设计.md)。

## 6. 数据组 3：违规公告索引

### 6.1 结构化事件用途

公告索引中的公司代码、公告日期、标题、分类代码和链接主要交给 `event_timeline`，支持：

- 查询某公司近期违规或监管公告；
- 构建处罚、风险提示和关联事项时间线；
- 按公司、时间和公告分类过滤；
- 将同类公告按时间聚合；
- 返回公告链接作为标题级证据。

### 6.2 文档检索用途

公告链接同时是 `document_search` 的文档入口：

```text
公告索引
  -> 下载 PDF
  -> 解析正文和表格
  -> 文档切分
  -> SQLite Chunk
  -> FAISS 向量索引
  -> document_search
```

没有下载和解析正文时，只能回答标题、日期和分类层面的事实。处罚金额、违规事实、责任人、监管依据和整改措施必须从公告正文获得。

### 6.3 工具职责区别

| 工具 | 负责回答 |
|---|---|
| `event_timeline` | 发生了什么、什么时候发生、事件如何排列 |
| `document_search` | 公告原文具体披露了什么 |

事件工具可以把公告正文的抽取结果作为补充事件字段，但不能让回答模型根据标题自行补写细节。

详细设计见 [04-公告索引设计.md](04-公告索引设计.md)。

## 7. 数据组 4：三张财务报表

### 7.1 主要工具

资产负债表、利润表和现金流量表主要支撑 `financial_risk_analysis`：

```text
财务宽表
  -> 标准指标映射
  -> 同口径期间选择
  -> 指标和同比计算
  -> 风险规则执行
  -> 财务证据与风险信号
```

工具内部可以提供多种能力：

| 内部能力 | 用途 |
|---|---|
| `metric_lookup` | 查询单个公司和期间的财务指标 |
| `company_comparison` | 比较多个公司同口径指标 |
| `trend_analysis` | 分析同一公司跨期趋势 |
| `risk_detection` | 执行财务异常规则 |

第一版不必把这些内部能力拆成多个 Agent 工具，避免增加 Planner 的选择复杂度。

### 7.2 可支持目标

- 营业收入、净利润、经营现金流等指标查询；
- 同比和同口径跨期比较；
- 利润与经营现金流背离；
- 存货、应收账款与收入增长背离；
- 毛利率、周转率和偿债能力分析；
- 多公司财务比较；
- 财务风险信号和可追溯解释。

### 7.3 辅助用途

财务工具命中的异常可以作为 `event_timeline` 的派生风险信号，例如“2024 年利润与经营现金流出现背离”。它必须标记为 `derived_signal`，不能描述为公司已经发生财务造假。

财务结果也可以与 `document_search` 返回的年报附注、公告或研报观点联合解释，但精确数字和指标计算仍以结构化财务数据为准。

### 7.4 存储原则

财务数据主要存入 SQLite，不以 FAISS 作为精确查询入口。向量检索适合查找相关文本，不适合保证财务数值、单位、期间和计算口径准确。

详细设计见 [05-财务报表设计.md](05-财务报表设计.md)。

## 8. 数据组 5：研报元数据和摘要

### 8.1 主要工具

研报主要支撑 `document_search`，在知识库中标记：

```text
document_type = research_report
```

一篇研报对应一份文档，标题、机构、作者、证券代码、评级、发布日期和行业作为结构化元数据，摘要正文切分为 Chunk 并建立向量索引。

### 8.2 可支持目标

- 查询某公司近期研报；
- 检索机构对某公司的主要观点；
- 分析评级变化；
- 对比多家机构观点；
- 检索行业关注点和风险提示；
- 为财务变化提供机构解释。

### 8.3 证据语义

研报内容属于机构观点，不等于客观事实。回答必须区分：

```text
财务报表显示……
某证券机构认为……
```

研报中的盈利预测、目标价和投资评级不能描述为已经实现的结果。目标价字段缺失较多，不应作为第一版核心能力。

### 8.4 是否新增工具

第一版不建议新增 `research_analysis` 工具。可以先通过 `document_search` 的文档类型和结构化过滤完成研报查询。只有在需要评级趋势统计、机构一致预期或复杂观点聚合时，再考虑增加专用工具。

详细设计见 [06-研报摘要设计.md](06-研报摘要设计.md)。

## 9. 数据与工具的多对多关系

完整关系如下：

```text
股东快照
  -> ownership_penetration：快照、变化、集中度、有限路径
  -> event_timeline：股东变化派生事件

公告索引和正文
  -> event_timeline：公告事件和时间线
  -> document_search：公告正文检索

财务报表
  -> financial_risk_analysis：指标、趋势、比较和风险规则
  -> event_timeline：财务异常派生信号

研报摘要
  -> document_search：研报检索和观点证据
  -> financial_risk_analysis：只作为解释补充，不参与确定性计算
```

一个问题可能需要多个数据源。例如：

```text
问题：某公司大股东减持后，财务风险和机构观点有什么变化？

ownership_penetration
  -> 查询股东持股变化

event_timeline
  -> 查询相关减持或股权公告

financial_risk_analysis
  -> 查询同期财务指标和风险信号

document_search
  -> 检索研报对该变化的解释
```

Agent 最终组合证据，但不能把不同来源的事实、推导和观点混为一种结论。

## 10. 统一数据访问接口

工具应依赖抽象数据接口：

```text
OwnershipRepository
  get_snapshot(company_id, as_of_date)
  compare_snapshots(company_id, start_date, end_date)
  get_incoming_holding_edges(company_id, as_of_date)

FinancialRepository
  get_statement(company_id, period, statement_type)
  get_metric_series(company_id, metric_code)
  compare_companies(company_ids, metric_code, period)

EventRepository
  get_events(company_id, event_types, start_date, end_date)

DocumentRepository
  search(query, company_id, document_types, start_date, end_date)
```

推荐的数据源实现：

| 实现 | 用途 |
|---|---|
| `SampleDataSource` | 示例演示和基础单元测试 |
| `CsvDataSource` | 小型测试数据和接口兼容性 |
| `SqliteDataSource` | 正式比赛结构化数据 |
| `KnowledgeBaseDataSource` | SQLite Chunk 和 FAISS 文档检索 |
| 外部 API DataSource | 未来实时行情、新闻或工商数据 |

这样未来更换数据源时，只需增加接口实现，不需要重写 Agent 工作流和工具返回协议。

## 11. 数据能力注册表

建议为每个数据源维护机器可读的能力描述：

```json
{
  "source_id": "competition_shareholder_snapshots",
  "source_type": "structured",
  "tools": ["ownership_penetration", "event_timeline"],
  "capabilities": [
    "shareholder_snapshot",
    "holding_change",
    "ownership_concentration",
    "limited_ownership_paths"
  ],
  "time_range": {
    "start": "2020-11-03",
    "end": "2026-06-02"
  },
  "limitations": [
    "top_shareholders_only",
    "no_complete_control_relationships",
    "no_beneficial_owner_guarantee"
  ],
  "evidence_types": ["reported_fact", "derived_metric", "derived_signal"]
}
```

能力注册表供以下模块使用：

- Planner：判断哪些工具具有候选能力；
- 工具：判断当前时间和数据范围是否可查询；
- Evidence Guard：检查结论是否超出来源能力；
- Answer Generator：生成限制说明；
- Evaluator：判断问题在当前系统中是否可回答。

能力注册表不能直接告诉被测 Agent 某条评测题的标准答案，只描述系统客观具备的数据和工具能力。

## 12. 统一证据分类

不同数据源生成的证据需要明确语义：

| 证据类型 | 含义 | 示例 |
|---|---|---|
| `reported_fact` | 原始数据直接披露的事实 | 财报净利润、公告日期、持股比例 |
| `derived_metric` | 程序从披露事实计算的指标 | 增长率、集中度、间接持股比例 |
| `derived_signal` | 规则根据指标生成的风险线索 | 现金流背离、主要股东显著减持 |
| `institution_opinion` | 证券机构观点或预测 | 研报评级、盈利预测、风险提示 |
| `document_excerpt` | 文档原文片段 | 公告、年报或研报 Chunk |

工具结果建议记录：

```json
{
  "data_source": {
    "source_id": "competition_shareholder_snapshots",
    "source_type": "structured",
    "storage": "sqlite",
    "as_of_date": "2025-12-31"
  },
  "evidence": [
    {
      "evidence_id": "EVID-...",
      "evidence_type": "reported_fact",
      "fact": {}
    }
  ]
}
```

回答模型必须区分“数据直接披露”“程序计算”“风险信号”和“机构观点”，不得在生成答案时抹平这些差异。

## 13. Agent 工具选择原则

Planner 根据问题的事实需求选择工具，而不是根据文件名选择工具。

| 用户需求 | 首选工具 | 可选补充工具 |
|---|---|---|
| 主要股东、持股比例、股权路径 | `ownership_penetration` | `event_timeline`、`document_search` |
| 财务指标、公司比较、财务风险 | `financial_risk_analysis` | `document_search` |
| 处罚、违规、股权或风险事件时间线 | `event_timeline` | `document_search` |
| 公告原文、研报观点和文本依据 | `document_search` | 对应结构化工具 |

多工具调用应由问题需要决定，不能为了显得复杂而调用全部工具。工具结果之间存在冲突时，Agent 应说明来源和口径差异，不得自行选择更符合预期的结论。

## 14. 当前数据未覆盖的能力

多轮问题集中包含许多当前数据无法支持的问题：

| 问题类型 | 当前状态 | 未来可能需要的工具 |
|---|---|---|
| 实时股价、涨跌停和指数行情 | 不支持 | `market_data` |
| 龙虎榜和主力资金流向 | 不支持 | `market_flow` |
| 用户自选股和持仓 | 不支持 | `portfolio` |
| 融资融券明细 | 不支持 | `margin_trading` |
| 证券账户及业务办理 | 不支持 | `brokerage_qa` |
| 实时新闻和政策 | 数据不足 | `news_search` |
| 确定性涨跌预测和收益保证 | 不应支持 | 只能提供证据化风险因素分析 |

上述缺失能力中，动态行情或新闻 Adapter 属于任务 1 的竞赛增强要求，不应永久停留在拒答状态。项目应优先接入至少一类合法、稳定且带时间戳的数据接口，用来展示 Planner 在静态数据库工具与动态 API 之间的自适应选择；其他尚未接入的能力继续通过能力注册表和正确拒答控制幻觉。

当前处理原则：

- 缺少公司、日期或用户账户上下文时返回 `clarification_required`；
- 系统没有对应数据或工具时返回 `unsupported`；
- 存在工具但没有查到充分证据时返回 `insufficient_evidence`；
- 不允许通用大模型凭训练记忆替代缺失工具；
- 不为了提高回答率编造实时结果。

## 15. 建议的标准化存储

第一版可以在同一个 SQLite 数据库中按业务域建表：

```text
data/structured/fintrace.sqlite

security_master
ownership_entities
shareholder_snapshots
shareholder_snapshot_edges
announcement_index
financial_balance_sheets
financial_income_statements
financial_cashflows
research_reports
derived_events
```

文档知识库继续独立保存：

```text
data/knowledge_base/fintrace_kb.sqlite
data/knowledge_base/vector.faiss
data/knowledge_base/vector_ids.json
```

结构化数据库负责精确过滤、数值计算、时点查询和图关系；知识库负责公告、年报、研报等文本的语义检索。两者通过 `company_id`、`document_id`、`event_id` 和 `evidence_id` 关联。

## 16. 数据接入顺序

建议按依赖关系实施：

1. 建立证券主表和统一公司标识；
2. 建立数据能力注册表和统一证据分类；
3. 导入三张财务报表并接入财务工具；
4. 导入十大股东快照并接入股权工具；
5. 导入公告索引并接入事件工具；
6. 导入研报摘要并建立文档索引；
7. 下载并解析允许使用的公告正文；
8. 实现跨工具证据组合；
9. 使用多轮问题集进行端到端评测；
10. 根据评测缺口决定是否增加实时行情等新工具。

证券主表优先，是因为公司名称、证券代码和主体代码映射同时被财务、股权、公告、研报和 Planner 使用。

## 17. 最终原则

FinTrace 的数据设计应遵循：

1. 原始数据保持只读；
2. 结构化事实通过 SQLite 精确查询；
3. 文档正文通过 SQLite Chunk 和 FAISS 检索；
4. 工具通过抽象接口访问数据；
5. 一份数据可以支持多个工具，但必须区分主要和辅助用途；
6. 一个工具可以组合多个数据源，但必须保留来源和时间口径；
7. 披露事实、计算指标、风险信号和机构观点必须分别标记；
8. Agent 只根据工具结果回答，不绕过工具使用训练记忆补充事实；
9. 数据能力之外的问题应澄清、部分回答或明确拒答；
10. 所有重要结论必须能够追溯到证据和原始数据。

明确数据如何服务工具之后，再确定导入格式、数据库表和代码接口，可以避免数据工程与 Agent 工作流反复返工。
