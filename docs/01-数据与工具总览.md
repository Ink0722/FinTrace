# FinTrace 数据、工具与 Agent 能力映射

## 1. 文档目的

本文档定义比赛数据在 FinTrace 中的业务用途、标准化存储方式、工具归属、证据类型和能力边界，是后续数据导入、工具改造、Agent 路由和评测设计的上层依据。

在讨论 Excel 如何解析、字段如何转换或数据存在哪里之前，必须先回答以下问题：

1. 每份数据可以支持哪些事实和任务；
2. 哪些工具负责读取和计算这些数据；
3. Agent 在什么问题下应调用哪些工具；
4. 工具可以给出什么结论，不能给出什么结论；
5. 工具结果如何形成可追溯证据；
6. 数据不覆盖的问题应如何处理。

本设计不要求一个数据集只对应一个工具。一个数据源可以支持多个工具，一个工具也可以组合多个数据源，但必须明确主要用途、辅助用途和证据语义。

本方案的竞赛任务、量化指标和分阶段交付以 [00-竞赛要求对齐.md](00-竞赛要求对齐.md) 为上层依据。

### 1.1 与竞赛任务的关系

| 竞赛任务 | 本文档负责明确的内容 |
|---|---|
| 任务 1：长对话与动态路由 | 哪些工具和数据能力可供 Planner 选择，哪些问题必须明确拒答 |
| 任务 2：股权穿透与事件脉络 | 现有股东快照、违规公告及正文如何服务有限持股路径和事件工具 |
| 任务 3：财务异象与解释报告 | 财务事实、派生指标、风险信号和研报观点如何分层使用 |

现有五组数据是本项目唯一的数据边界。它们不能支持完整控制链、全网新闻舆情、行情分析或已确认的财务欺诈标签，因此系统不得声称已经满足依赖这些数据的指标；相关问题应按能力边界返回限制或拒答。

## 2. 系统分层

FinTrace 应明确区分五个层次：

```text
原始比赛数据
  -> 标准化数据与索引
  -> 数据访问接口
  -> 确定性工具
  -> Agent 规划与回答
```

### 2.1 原始比赛数据

包括 Excel、CSV、数据字典和公告链接。原始目录保持只读，作为数据来源和审计依据，不直接承担在线查询。

### 2.2 标准化数据与索引

包括：

- SQLite 结构化表；
- 文档和 Chunk 元数据；
- FAISS 向量索引；
- 股权快照及动态投影图；
- 数据导入清单和质量报告。

该层负责统一类型、日期、主体标识、字段名称、质量标志和证据 ID。

### 2.3 数据访问接口

工具通过 Repository 或 DataSource 接口读取数据，不直接依赖某个 Excel 文件。CSV 可以作为测试实现，SQLite 作为比赛数据的正式实现；两种实现必须遵守同一数据范围和返回协议。

### 2.4 确定性工具

工具负责：

- 精确查询；
- 数值计算；
- 图路径搜索；
- 时间过滤；
- 规则判断；
- 数据校验；
- 证据生成。

大模型不能代替工具计算财务指标、股权比例或读取大规模原始表格。

### 2.5 Agent 规划与回答

Agent 负责：

- 理解当前问题和必要上下文；
- 选择工具和构造参数；
- 组合多个工具的结果；
- 根据证据生成自然语言回答；
- 在数据不足时部分回答、澄清或拒答。

所有事实性结论必须来自工具证据，不允许大模型凭记忆补充历史或实时行情、财务数字、持股关系或公告细节。

### 2.6 统一历史截止时点

每轮问题必须具有 `knowledge_cutoff`，表示用户提问时系统允许知道信息的最晚日期。该日期来自评测标注、会话状态或用户明确指定，不得由模型自行猜测。

`knowledge_cutoff` 与业务查询中的 `as_of_date` 含义不同：前者限制“当时已经公开的信息”，后者表示用户希望观察的业务时点。工具可以查询更早的 `as_of_date`，但使用的任何记录都必须在 `knowledge_cutoff` 之前已经披露。

所有数据访问统一执行以下限制：

- 公告仅使用 `ann_dt <= knowledge_cutoff` 的记录；
- 研报仅使用 `publish_date <= knowledge_cutoff` 的记录；
- 财务报表仅使用 `actual_ann_dt` 或 `ann_dt <= knowledge_cutoff` 的已披露版本；
- 股东快照必须同时检查快照截止日期和公告日期，并确保公告日期不晚于 `knowledge_cutoff`；
- “最新”表示截止 `knowledge_cutoff` 已披露的最新可用记录，不表示数据集全局最新记录；
- 禁止使用提问时点之后的记录解释、验证或反推当时的答案。

## 3. 五组比赛数据总览

| 数据组 | 内容 | 系统角色 | 主要工具 | 辅助工具 |
|---|---|---|---|---|
| 1 | 多轮问题集 | 评测输入 | 无 | 评测回放器与裁判 |
| 2 | 十大股东快照 | 结构化股权证据 | `ownership_analysis` | `event_timeline` |
| 3 | 违规公告索引 | 结构化事件证据和文档入口 | `event_timeline` | `document_search` |
| 4 | 三张财务报表 | 结构化财务证据 | `financial_analysis` | `event_timeline`、`document_search` |
| 5 | 研报元数据和摘要 | 文本检索和机构观点证据 | `document_search` | `financial_analysis` |

“辅助工具”表示该数据可以为其他工具提供补充证据或派生事件，不表示这些工具可以绕过自己的核心数据源。

## 4. 数据组 1：多轮问题集

### 4.1 数据角色

多轮问题集只用于：

- 向 Agent 提供评测输入；
- 回放 35 个独立会话；
- 评估多轮上下文、工具选择、可回答性判断和答案质量；
- 测试重复问题下的运行稳定性。

### 4.2 禁止用途

该数据不得：

- 作为事实证据；
- 加入生产知识库供 Agent 检索答案；
- 参与金融事实计算；
- 向被测 Agent 泄露预期工具、可回答性或评分标签。

推荐存储位置：

```text
evaluation/datasets/multi_turn_questions.jsonl
evaluation/labels/multi_turn_labels.jsonl
```

评测设计详见 [02-多轮评测方案.md](02-多轮评测方案.md)。

## 5. 数据组 2：十大股东快照

### 5.1 主要工具

十大股东快照主要支撑 `ownership_analysis`。工具内部建议支持：

| 查询模式 | 用途 |
|---|---|
| `holding_query` | 从公司查询主要股东、从股东反查公司，并返回快照内可计算的集中度 |
| `holding_compare` | 比较两个时点的主要股东和持股变化 |
| `penetration` | 查询能够可靠连接的有限多层持股路径 |

### 5.2 辅助工具

股东快照可以为 `event_timeline` 生成派生事件：

- 股东进入主要股东名单；
- 股东退出主要股东名单；
- 持股数量或比例显著变化；
- 股权集中度显著变化；
- 限售股份结构变化。

这些事件必须标记为 `derived_event`，不能伪装为公告原文中的披露事件。“退出主要股东名单”也不等于已经清仓。

### 5.3 数据边界

该数据不能单独确认：

- 完整工商股权结构；
- 最终受益所有人；
- 一致行动关系；
- 表决权委托或协议控制；
- 实际控制人；
- 完整控制链。

由该数据形成的原始图关系应标记为 `OWNS`，不得直接标记为 `CONTROLS`。

详细设计见 [03-股东快照设计.md](03-股东快照设计.md)。

## 6. 数据组 3：违规公告索引

### 6.1 结构化事件用途

公告索引中的公司代码、公告日期、标题、分类代码和链接主要交给 `event_timeline`，支持：

- 查询某公司近期违规或监管公告；
- 构建处罚、风险提示和关联事项时间线；
- 按公司、时间和公告分类过滤；
- 将同类公告按时间聚合；
- 返回公告链接作为标题级证据。

### 6.2 文档检索用途

公告链接同时是 `document_search` 的文档入口：

```text
公告索引
  -> 下载 PDF
  -> 解析正文和表格
  -> 文档切分
  -> SQLite Chunk
  -> FAISS 向量索引
  -> document_search
```

没有下载和解析正文时，只能回答标题、日期和分类层面的事实。处罚金额、违规事实、责任人、监管依据和整改措施必须从公告正文获得。

### 6.3 工具职责区别

| 工具 | 负责回答 |
|---|---|
| `event_timeline` | 发生了什么、什么时候发生、事件如何排列 |
| `document_search` | 公告原文具体披露了什么 |

事件工具可以把公告正文的抽取结果作为补充事件字段，但不能让回答模型根据标题自行补写细节。

详细设计见 [04-公告索引设计.md](04-公告索引设计.md)。

## 7. 数据组 4：三张财务报表

### 7.1 主要工具

资产负债表、利润表和现金流量表主要支撑 `financial_analysis`：

```text
财务宽表
  -> 标准指标映射
  -> 同口径期间选择
  -> 指标和同比计算
  -> 风险规则执行
  -> 财务证据与风险信号
```

工具内部可以提供多种能力：

| Operation | 用途 |
|---|---|
| `metric_query` | 查询指定公司和期间的财务指标，不执行比较计算 |
| `metric_compare` | 计算同一公司多个期间或多个公司同一期间的同口径指标差异 |
| `risk_scan` | 执行财务异常规则 |

第一版不必把这些内部能力拆成多个 Agent 工具，避免增加 Planner 的选择复杂度。

### 7.2 可支持目标

- 营业收入、净利润、经营现金流等指标查询；
- 同比和同口径跨期比较；
- 利润与经营现金流背离；
- 存货、应收账款与收入增长背离；
- 毛利率、周转率和偿债能力分析；
- 多公司财务比较；
- 财务风险信号和可追溯解释。

### 7.3 辅助用途

财务工具命中的异常可以作为 `event_timeline` 的派生风险信号，例如“2024 年利润与经营现金流出现背离”。它必须标记为 `derived_signal`，不能描述为公司已经发生财务造假。

财务结果可以与 `document_search` 返回的违规公告或研报观点联合解释，但精确数字和指标计算仍以结构化财务数据为准。当前文本库没有完整年报附注或审计报告，涉及这些材料的问题必须说明不支持。

### 7.4 存储原则

财务数据主要存入 SQLite，不以 FAISS 作为精确查询入口。向量检索适合查找相关文本，不适合保证财务数值、单位、期间和计算口径准确。

详细设计见 [05-财务报表设计.md](05-财务报表设计.md)。

## 8. 数据组 5：研报元数据和摘要

### 8.1 主要工具

研报主要支撑 `document_search`，在知识库中标记：

```text
document_type = research_report
```

一篇研报对应一份文档，标题、机构、作者、证券代码、评级、发布日期和行业作为结构化元数据，摘要正文切分为 Chunk 并建立向量索引。

### 8.2 可支持目标

- 查询某公司近期研报；
- 检索机构对某公司的主要观点；
- 分析评级变化；
- 对比多家机构观点；
- 检索行业关注点和风险提示；
- 为财务变化提供机构解释。

### 8.3 证据语义

研报内容属于机构观点，不等于客观事实。回答必须区分：

```text
财务报表显示……
某证券机构认为……
```

研报中的盈利预测、目标价和投资评级不能描述为已经实现的结果。目标价字段缺失较多，不应作为第一版核心能力。

### 8.4 是否新增工具

不新增 `research_analysis` 工具。研报查询通过 `document_search` 的文档类型和结构化过滤完成；超出研报摘要能够支持的统计或观点聚合明确返回证据不足。

详细设计见 [06-研报摘要设计.md](06-研报摘要设计.md)。

## 9. 数据与工具的多对多关系

完整关系如下：

```text
股东快照
  -> ownership_analysis：快照、变化、集中度、有限路径
  -> event_timeline：股东变化派生事件

公告索引和正文
  -> event_timeline：公告事件和时间线
  -> document_search：公告正文检索

财务报表
  -> financial_analysis：指标、趋势、比较和风险规则
  -> event_timeline：财务异常派生信号

研报摘要
  -> document_search：研报检索和观点证据
  -> financial_analysis：只作为解释补充，不参与确定性计算
```

一个问题可能需要多个数据源。例如：

```text
问题：某公司大股东减持后，财务风险和机构观点有什么变化？

ownership_analysis
  -> 查询股东持股变化

event_timeline
  -> 查询相关减持或股权公告

financial_analysis
  -> 查询同期财务指标和风险信号

document_search
  -> 检索研报对该变化的解释
```

Agent 最终组合证据，但不能把不同来源的事实、推导和观点混为一种结论。

## 10. 目标工具集与函数设计

### 10.1 四个公共金融工具

结合现有五组比赛数据的实际覆盖范围，目标版本采用四个公共金融工具：

| 工具 | 主要职责 | 是否为新增工具 |
|---|---|---|
| `document_search` | 违规公告正文和研报摘要检索 | 否 |
| `financial_analysis` | 财务指标查询、比较、趋势和风险扫描 | 由现有财务风险工具扩展 |
| `ownership_analysis` | 股东快照、持股变化、集中度和股权穿透 | 由现有股权穿透工具扩展 |
| `event_timeline` | 公司事件查询、聚类和时间线组织 | 否 |

当前代码中的 `financial_risk_analysis` 和 `ownership_penetration` 是早期入口名称。目标设计分别迁移为 `financial_analysis` 和 `ownership_analysis`；迁移期间可以保留兼容别名，但 Planner、标注文档和新接口统一使用目标名称。

每个工具使用一个稳定入口和多个确定性内部函数。Planner 只选择工具和 `operation`，不直接选择内部函数，避免工具列表和规划空间无限膨胀。

所有工具调用统一在 `arguments.operation` 中声明操作类型。工具结果必须回显 `operation`，并统一返回：

```text
status      success、warning 或 failed
data        该 operation 的结构化结果
evidence    支撑结果的证据列表
warnings    数据口径、时效性和能力限制
metrics     执行时间、候选数量等运行指标
```

工作流在工具调用之外统一注入 `knowledge_cutoff`，工具结果必须回显实际使用的数据截止日期。Planner 不负责生成或修改该值，避免模型通过参数绕过历史时点限制。

`required` 参数缺失时不得自行填入示例公司或默认日期；能够通过多轮上下文唯一恢复时由 Agent 前置解析补齐，否则返回 `clarification_required`。表中未列出的参数均不得由 Planner 随意编造。

#### 10.1.1 统一参数字典

| 参数 | 统一含义 | 格式或取值 |
|---|---|---|
| `operation` | 当前工具要执行的操作 | 各工具声明的枚举值 |
| `query` | 用户的检索文本 | 字符串 |
| `company_ids` | 一个或多个上市公司标识，即使只有一个也使用数组 | 例如 `["600519.SH"]` |
| `entity_ids` | 公司、机构或人物等通用主体标识 | 字符串数组 |
| `holder_ids` | 股东主体标识，用于反向持股查询或股东过滤 | 字符串数组 |
| `source_entity_id`、`target_entity_id` | 持股路径的起点和终点 | 单个主体标识 |
| `metric_codes` | 标准财务指标代码 | 例如 `REVENUE`、`NET_PROFIT` |
| `report_periods` | 一个或多个财务报告期，即使只有一个也使用数组 | `YYYY-MM-DD` 数组 |
| `as_of_date` | 希望观察的业务状态时点 | `YYYY-MM-DD` |
| `start_date`、`end_date` | 公告、事件或快照变化的自然日期区间 | `YYYY-MM-DD` |
| `knowledge_cutoff` | 提问时允许使用信息的最晚披露日期，由工作流注入 | `YYYY-MM-DD` |
| `scope` | 事件查询范围 | `entity` 或 `corpus` |
| `order_by` | 事件结果排序方式 | `event_date_asc`、`event_date_desc` 或 `relevance` |
| `statement_types` | 需要读取的财务报表类型 | `balance_sheet`、`income_statement`、`cashflow_statement` |
| `top_k` | 最多返回的结果数量 | 正整数 |

`report_periods`、`as_of_date` 和 `knowledge_cutoff` 不得合并：它们分别表示财务归属期集合、业务观察时点和信息可知截止日。所有同类集合参数始终使用复数数组，不接受“单个值时传字符串”的动态类型。`scope` 只用于事件查询范围；工具调用中的财务报表选择统一使用 `statement_types`，不使用容易与事件范围混淆的 `statement_scope`。原始数据记录中的单值字段不受工具接口命名规则影响。

### 10.2 `document_search`

建议入口：

```python
document_search(call: ToolCall) -> ToolResult
```

支持的 `operation`：

```text
search
```

| Operation | 必填参数 | 可选参数 | 主要结果 |
|---|---|---|---|
| `search` | `query` | `company_ids`、`document_types`、`start_date`、`end_date`、`publishers`、`top_k`、`mode` | 按相关性排序的 Chunk、文档元数据、检索分数和原文证据 |

`search` 是唯一对 Planner 开放的文档操作。按 ID 加载 Chunk、BM25、向量召回和重排均为工具内部步骤，不作为独立 operation 暴露。

配套函数：

| 函数 | 功能 |
|---|---|
| `resolve_document_filters()` | 从参数中解析公司、文档类型、日期和发布机构过滤条件 |
| `search_bm25()` | 使用关键词索引进行精确词项召回 |
| `search_vector()` | 使用 Embedding 和 FAISS 进行语义召回 |
| `merge_hybrid_hits()` | 合并 BM25 与向量候选并去重 |
| `rerank_hits()` | 根据相关性、主体、时间和文档类型重排候选 |
| `load_chunks_by_ids()` | 按 Chunk ID 精确加载人工标注或检索命中的原文 |
| `build_document_evidence()` | 将命中 Chunk 转换为带来源、日期和文档 ID 的证据 |

`document_type` 只允许 `announcement` 和 `research_report`。当前知识库不包含政策新闻、券商业务说明或研报全文，不得通过放宽过滤条件伪造这些能力。

### 10.3 `financial_analysis`

建议入口：

```python
financial_analysis(call: ToolCall) -> ToolResult
```

支持的 `operation`：

```text
metric_query
metric_compare
risk_scan
```

| Operation | 必填参数 | 可选参数 | 主要结果 |
|---|---|---|---|
| `metric_query` | `company_ids`、`metric_codes`、`report_periods` | `statement_types`、`currency` | 指定公司和期间的指标值、单位、报表口径和来源 |
| `metric_compare` | `company_ids`、`metric_codes`、`report_periods` | `comparison_method` | 跨期有序序列、相邻变化、累计变化，或跨公司的同口径数值和差异 |
| `risk_scan` | `company_ids`、`report_periods` | `focus_topics`、`rule_ids` | 按公司、报告期和规则分组的风险信号、计算过程和证据 ID |

`report_periods` 中每项使用标准报告期截止日；“最新”先由 Agent 解析为截止 `knowledge_cutoff` 已披露的具体日期，再作为单元素数组传给工具。各 operation 的基数约束如下：

| Operation | `company_ids` | `report_periods` |
|---|---|---|
| `metric_query` | 至少 1 个 | 至少 1 个 |
| `metric_compare`（跨期） | 恰好 1 个 | 至少 2 个 |
| `metric_compare`（跨公司） | 至少 2 个 | 恰好 1 个 |
| `risk_scan` | 至少 1 个 | 至少 1 个 |

`metric_query` 只返回查询结果，不计算公司间或期间间差异。`metric_compare` 根据参数基数确定比较维度：跨期模式按报告期排序，返回各期数值、相邻变化额、相邻变化率、首尾累计变化，并可按需计算 CAGR；跨公司模式返回同一报告期各公司的同口径数值、排序及差异，但不自动构造行业基准或全市场排名。当 `company_ids` 和 `report_periods` 同时包含多个值时，比较维度不唯一，必须返回 `invalid_argument`。其他不满足基数约束的参数同样不能静默取数组第一项。

`metric_compare` 只负责确定性数值处理，不输出“增长动能减弱”“趋势反转”等语言判断。Agent LLM 根据工具返回的序列和变化值解释上升、下降、增速变化或拐点，但不得自行计算、修改或补充工具没有返回的数值。需要规则阈值和风险定性的异常检测仍由 `risk_scan` 完成。

配套函数：

| 函数 | 功能 |
|---|---|
| `resolve_financial_period()` | 把年度、季度和“最新报告期”转换为标准报告期 |
| `load_statement_records()` | 加载指定公司、报表类型和期间的原始记录 |
| `get_metric_value()` | 查询营业收入、净利润、存货等标准指标 |
| `calculate_derived_metric()` | 计算毛利率、周转率、ROE、复合增长率等派生指标 |
| `compare_metrics()` | 根据公司和报告期基数，计算跨期序列、相邻及累计变化，或比较多个指定公司的同口径指标 |
| `run_financial_risk_rules()` | 执行现金流背离、存货异常、应收异常等风险规则 |
| `build_financial_evidence()` | 返回原始数值、单位、期间、公式和来源记录 |

精确数值和计算必须由上述函数完成；LLM 只负责解释结果。原有四条财务风险规则属于 `risk_scan`，不再代表整个财务工具的能力边界。

### 10.4 `ownership_analysis`

建议入口：

```python
ownership_analysis(call: ToolCall) -> ToolResult
```

支持的 `operation`：

```text
holding_query
holding_compare
penetration
```

| Operation | 必填参数 | 可选参数 | 主要结果 |
|---|---|---|---|
| `holding_query` | `as_of_date`，以及 `company_ids`、`holder_ids` 中至少一项 | `holder_types`、`top_n` | 公司到主要股东或股东到公司的快照记录；公司方向同时返回第一、前三、前五和前十大股东集中度 |
| `holding_compare` | `company_ids`、`start_date`、`end_date` | `holder_ids`、`change_threshold` | 股东进入、退出、增持、减持及持股数量和比例变化 |
| `penetration` | `source_entity_id`、`target_entity_id`、`as_of_date` | `max_depth`、`max_paths` | 快照能够证明的持股路径、每跳比例、路径乘积和完整性警告 |

`holding_query` 根据主体参数确定方向：只提供 `company_ids` 时查询公司主要股东，只提供 `holder_ids` 时反查股东出现在哪些公司快照中，两者同时提供时执行交叉过滤，两者都缺失时返回 `invalid_argument`。集中度由工具对公司方向的快照记录进行确定性求和，不作为独立 operation；Agent 可以解释集中程度，但不得自行累加或修改比例。

`holding_query` 和 `holding_compare` 均基于披露快照。反向查询结果只能称为“该主体在数据集的主要股东名单中可见”，不能称为完整持仓；主体未出现也不能推断其没有持股。`penetration` 只使用由有效快照投影的 `OWNS` 关系，不能用“进入十大股东”推断控制关系、实际控制人或最终受益人。

配套函数：

| 函数 | 功能 |
|---|---|
| `query_holdings()` | 根据公司和股东参数执行正向查询、反向查询或交叉过滤 |
| `compare_holdings()` | 比较两个快照时点的股东进入、退出和持股变化 |
| `calculate_ownership_concentration()` | 计算第一、前三、前五和前十大股东集中度 |
| `build_ownership_graph()` | 根据同一历史时点的有效快照构建 `OWNS` 查询子图 |
| `find_ownership_paths()` | 搜索主体到目标公司的有界持股路径 |
| `calculate_indirect_ratio()` | 计算路径中披露持股比例的乘积 |
| `build_ownership_evidence()` | 为快照、变化和每一跳关系生成证据 |

十大股东快照可以通过 `holding_query` 支持正向快照、反向主体查询和集中度，通过 `holding_compare` 支持快照变化，但不能单独证明完整控制链。基金与其他股东类型使用相同的反向查询接口，不再设置基金专用 operation。所有反向结果都受“主要股东快照”覆盖范围限制；`penetration` 只能返回现有快照能够证明的有限路径，证据不足时必须明确返回。

### 10.5 `event_timeline`

建议入口：

```python
event_timeline(call: ToolCall) -> ToolResult
```

支持的 `operation`：

```text
event_query
event_cluster
```

| Operation | 必填参数 | 可选参数 | 主要结果 |
|---|---|---|---|
| `event_query` | `scope` | `entity_ids`、`event_types`、`start_date`、`end_date`、`keywords`、`include_derived`、`order_by`、`top_k` | 经过筛选、去重和排序的违规公告及可选派生事件节点和来源证据 |
| `event_cluster` | `scope`、`start_date`、`end_date` | `entity_ids`、`event_types`、`window_days`、`entity_overlap_threshold` | 违规公告事件簇、成员事件、时间跨度和聚合依据 |

`scope` 只取 `entity` 或 `corpus`。当 `scope=entity` 时必须提供 `entity_ids`；`scope=corpus` 表示搜索当前违规公告语料全集，不代表完整市场事件。保留 `scope` 可以防止主体解析失败后把定向查询静默扩大到全语料。日期范围还必须受 `knowledge_cutoff` 约束。

`event_query` 统一承担事件检索和时间线节点准备。工具负责筛选、去重和按 `order_by` 排序，Agent LLM 负责把返回节点组织成自然语言时间线，不得编造工具未返回的事件或日期。`include_derived=true` 时可以加入财务风险和持股变化产生的派生节点，但必须保留 `derived_signal` 类型，不能伪装成公告直接披露的事实。

`event_cluster` 负责按事件类型、时间窗口和实体重合度聚合相关节点。它只表达相关性和时序，不输出自动因果结论；除非证据明确披露，Agent 也不能把时间相近或同簇事件描述为因果关系。

配套函数：

| 函数 | 功能 |
|---|---|
| `query_events()` | 按范围、主体、事件类型、关键词和日期查询结构化事件 |
| `deduplicate_events()` | 根据事件标识、来源和内容特征去除重复事件节点 |
| `extract_events_from_documents()` | 从违规公告正文抽取事件候选，离线执行并保留原文证据 |
| `normalize_event_entities()` | 统一事件中的公司、人物和机构标识 |
| `cluster_related_events()` | 按类型、时间窗口和实体重合度聚合事件 |
| `align_derived_signals()` | 将股东变化或财务风险信号对齐到时间线 |
| `order_event_nodes()` | 按发生日期、披露日期或相关性排序事件节点 |
| `build_event_evidence()` | 返回事件来源、日期、文档和证据类型 |

事件聚类只能表达相关性和时序，不应自动生成未经证据支持的因果关系。

### 10.6 内部实体解析与不新增工具的能力

公司名称和代码解析属于 Agent 前置基础设施，不作为公共工具暴露给 Planner。系统只从现有股东、公告、财报和研报记录构建 `entity_alias_index`，用于把数据集中出现的名称和代码连接起来。研报中的行业字段保留为带发布日期和来源的机构分类标签，不视为官方行业成分数据。

实体解析返回多个候选时必须澄清；没有匹配时返回 `entity_not_found`，不得填入示例公司或依靠模型记忆生成代码。

以下需求不应继续增加公共金融工具：

| 需求 | 处理方式 |
|---|---|
| 投资建议 | Agent 只能基于现有财务、股东、事件和文档证据解释风险，不提供行情判断或收益预测 |
| 公司名称和代码解析 | 使用内部 `entity_alias_index`，不作为 Planner 工具 |
| 财务公式计算 | 由 `financial_analysis` 内部确定性函数完成 |
| 数据集以外的券商业务办理说明 | 返回 `unsupported` |
| 上下文继承 | 由 Agent Memory 和状态管理完成，不是工具 |
| 用户自选股和持仓 | 返回 `unsupported` |
| 实际买卖和撤单 | 返回 `unsupported` |

```json
  "source_type": "structured",
  "tools": ["ownership_analysis", "event_timeline"],
  "capabilities": [
    "holding_query",
    "holding_compare",
    "concentration_summary",
    "limited_ownership_paths"
  ],
  "time_range": {
    "start": "2020-11-03",
    "end": "2026-06-02"
  },
  "limitations": [
    "top_shareholders_only",
    "no_complete_control_relationships",
    "no_beneficial_owner_guarantee"
  ],
  "evidence_types": ["reported_fact", "derived_metric", "derived_signal"]
}
```

能力注册表供以下模块使用：

- Planner：判断哪些工具具有候选能力；

- Evidence Guard：检查结论是否超出来源能力；
- Answer Generator：生成限制说明；
- Evaluator：判断问题在当前系统中是否可回答。

能力注册表不能直接告诉被测 Agent 某条评测题的标准答案，只描述系统客观具备的数据和工具能力。

## 13. 统一证据分类

不同数据源生成的证据需要明确语义：

| 证据类型 | 含义 | 示例 |
|---|---|---|
| `reported_fact` | 原始数据直接披露的事实 | 财报净利润、公告日期、持股比例 |
| `derived_metric` | 程序从披露事实计算的指标 | 增长率、集中度、间接持股比例 |
| `derived_signal` | 规则根据指标生成的风险线索 | 现金流背离、主要股东显著减持 |
| `institution_opinion` | 证券机构观点或预测 | 研报评级、盈利预测、风险提示 |
| `document_excerpt` | 文档原文片段 | 违规公告正文或研报摘要 Chunk |

工具结果建议记录：

```json
{
  "data_source": {
    "source_id": "competition_shareholder_snapshots",
    "source_type": "structured",
    "storage": "sqlite",
    "as_of_date": "2025-12-31",
    "knowledge_cutoff": "2026-01-15"
  },
  "evidence": [
    {
      "evidence_id": "EVID-...",
      "evidence_type": "reported_fact",
      "fact": {}
    }
  ]
}
```

回答模型必须区分“数据直接披露”“程序计算”“风险信号”和“机构观点”，不得在生成答案时抹平这些差异。

## 14. Agent 工具选择原则

Planner 根据问题的事实需求选择工具，而不是根据文件名选择工具。

| 用户需求 | 首选工具 | 可选补充工具 |
|---|---|---|
| 主要股东、持股比例、股权路径 | `ownership_analysis` | `event_timeline`、`document_search` |
| 财务指标、公司比较、财务风险 | `financial_analysis` | `document_search` |
| 处罚、违规、股权或风险事件时间线 | `event_timeline` | `document_search` |
| 公告原文、研报观点和文本依据 | `document_search` | 对应结构化工具 |
| 数据集中出现的公司名称或代码解析 | 内部实体解析 | 无需 Planner 调用 |
| 研报中的行业标签 | `document_search` | 仅作为带来源的机构分类元数据 |

多工具调用应由问题需要决定，不能为了显得复杂而调用全部工具。对于单一指标、公告或股东事实查询，只调用必要工具；对于企业综合分析、尽调、风险画像或投资风险研判，即使用户没有逐项点名，Planner 也应主动考虑 `financial_analysis` 和 `ownership_analysis`，需要文本或事件佐证时再增加对应工具。必要维度未执行或证据不足时，回答必须明确写入限制，不能由 LLM 自行补齐。

工具结果之间存在冲突时，Agent 应说明来源、披露时间和口径差异，不得自行选择更符合预期的结论。

## 15. 当前数据未覆盖的能力

多轮问题集中包含许多当前数据无法支持的问题：

| 问题类型 | 当前状态 | Agent 处理方式 |
|---|---|---|
| 历史或实时股价、涨跌停、指数行情、估值和技术指标 | 不支持 | 返回 `unsupported`，说明数据集不含行情数据 |
| 龙虎榜、资金流向、融资融券和大宗交易 | 不支持 | 返回 `unsupported`，说明数据集不含交易行为数据 |
| 用户自选股和持仓 | 不支持 | 返回 `unsupported`，说明系统未连接用户账户 |
| 完整证券资料、上市状态和官方行业成分 | 不支持 | 仅回答现有材料能够证明的名称、代码或研报行业标签 |
| 证券账户状态及实际业务办理 | 不支持 | 返回 `unsupported` |
| 数据集以外的券商业务说明 | 不支持 | 返回 `unsupported` |
| 实时新闻、政策和全市场事件 | 不支持 | 返回 `unsupported`，不得用违规公告语料冒充完整新闻源 |
| 确定性涨跌预测和收益保证 | 不应支持 | 只能提供现有证据范围内的风险因素分析 |

当前处理原则：

- 缺少公司、日期或用户账户上下文时返回 `clarification_required`；
- 系统没有对应数据或工具时返回 `unsupported`；
- 存在工具但没有查到充分证据时返回 `insufficient_evidence`；
- 不允许通用大模型凭训练记忆替代缺失工具；
- 不为了提高回答率编造实时结果。

## 17. 数据接入顺序

建议按依赖关系实施：

1. 从现有五组数据建立实体别名索引和统一公司标识；
2. 建立数据能力注册表和统一证据分类；
3. 导入三张财务报表并接入财务工具；
4. 导入十大股东快照并接入股权工具；
5. 导入公告索引并接入事件工具；
6. 导入研报摘要并建立文档索引；
7. 下载并解析允许使用的公告正文；
8. 实现跨工具证据组合；
9. 使用多轮问题集进行端到端评测；
10. 对用户账户、行情和交易指令保持明确拒答。

实体别名索引优先，是因为公司名称、证券代码和主体代码映射同时被财务、股权、公告、研报和 Planner 使用。该索引仅汇总比赛数据中已有标识，不扩展为权威证券主数据。

## 18. 最终原则

FinTrace 的数据设计应遵循：

1. 原始数据保持只读；
2. 结构化事实通过 SQLite 精确查询；
3. 文档正文通过 SQLite Chunk 和 FAISS 检索；
4. 工具通过抽象接口访问数据；
5. 一份数据可以支持多个工具，但必须区分主要和辅助用途；
6. 一个工具可以组合多个数据源，但必须保留来源和时间口径；
7. 披露事实、计算指标、风险信号和机构观点必须分别标记；
8. Agent 只根据工具结果回答，不绕过工具使用训练记忆补充事实；
9. 数据能力之外的问题应澄清、部分回答或明确拒答；
10. 所有查询遵守 `knowledge_cutoff`，不得使用提问时点之后披露的信息；
11. 综合企业分析主动检查财务风险和现有证据支持的持股路径；
12. 所有重要结论必须能够追溯到证据和原始数据。

明确数据如何服务工具之后，再确定导入格式、数据库表和代码接口，可以避免数据工程与 Agent 工作流反复返工。
