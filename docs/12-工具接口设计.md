# FinTrace 工具接口设计

## 1. 文档定位

本文从项目 README 和《数据与工具总览》中提取并整合目标工具设计，作为后续实现、评审和测试公共金融工具的接口基线。本文描述的是**目标接口**，当前代码中的 `financial_risk_analysis`、`ownership_penetration` 等早期入口可能尚未完成迁移。

工具设计必须以现有五组比赛数据为边界。不得因为模型能够生成某类答案，就把行情、完整基金持仓、完整控制关系、研报全文或外部业务办理信息写成系统已经具备的能力。

## 2. 设计原则

1. Planner 只选择公共工具和 `operation`，不直接选择内部函数。
2. 工具负责检索、过滤、排序、数值计算、图搜索和规则判断等确定性工作。
3. Agent LLM 负责理解问题、选择工具、组织语言和解释结果，不得自行补充工具未返回的事实或数值。
4. 每项关键结果必须绑定证据；数据不足时返回警告，不得用模型常识补齐。
5. 必填参数缺失时不得填入示例公司或默认日期。上下文无法唯一恢复时返回 `clarification_required`。
6. 财务异常只能表述为风险信号；事件相关或时间相近不能自动表述为因果关系。
7. 工具必须能够脱离 Agent 独立调用、独立计时和独立评测。

## 3. 公共工具集

| 工具 | 主要职责 | Operations |
|---|---|---|
| `document_search` | 检索违规公告正文和研报摘要 | `search` |
| `financial_analysis` | 查询及比较财务指标，执行财务风险规则 | `metric_query`、`metric_compare`、`risk_scan` |
| `ownership_analysis` | 查询及比较主要股东快照，执行有限股权穿透 | `holding_query`、`holding_compare`、`penetration` |
| `event_timeline` | 查询、排序和聚合事件节点 | `event_query`、`event_cluster` |

公司名称和代码解析由内部 `entity_alias_index` 完成，不作为公共工具暴露。上下文继承属于 Agent Memory，财务公式属于财务工具内部函数，也不应增加新的 Planner 工具。

## 4. 统一调用协议

每个公共工具只有一个稳定入口：

```python
tool(call: ToolCall) -> ToolResult
```

`ToolCall.arguments.operation` 指定本次操作。工作流在 Planner 之外注入 `knowledge_cutoff`，Planner 无权生成或修改该值。

工具结果统一包含：

| 字段 | 含义 |
|---|---|
| `operation` | 回显实际执行的操作 |
| `status` | `success`、`warning` 或 `failed` |
| `data` | operation 对应的结构化结果 |
| `evidence` | 支撑结果的证据列表 |
| `warnings` | 数据范围、口径、完整性和时效性限制 |
| `metrics` | 执行时间、候选数量和最终结果数量等运行指标 |
| `knowledge_cutoff` | 实际采用的信息可知截止日期 |

`warning` 表示工具完成执行，但证据不完整或结果存在明确边界；`failed` 表示参数非法、数据源不可用或执行失败。失败时不得生成看似正常的替代答案。

## 5. 统一参数

| 参数 | 统一含义 | 格式或取值 |
|---|---|---|
| `operation` | 当前工具执行的操作 | 工具声明的枚举值 |
| `query` | 文档检索文本 | 字符串 |
| `company_ids` | 一个或多个上市公司标识 | 字符串数组，例如 `["600519.SH"]` |
| `entity_ids` | 公司、机构或人物等通用主体标识 | 字符串数组 |
| `holder_ids` | 用于反向查询或过滤的股东主体标识 | 字符串数组 |
| `source_entity_id` | 持股路径起点 | 单个主体标识 |
| `target_entity_id` | 持股路径终点 | 单个主体标识 |
| `metric_codes` | 标准财务指标代码 | 字符串数组 |
| `report_periods` | 财务报告期截止日 | `YYYY-MM-DD` 数组 |
| `as_of_date` | 观察股权状态的业务时点 | `YYYY-MM-DD` |
| `start_date`、`end_date` | 事件或快照变化的自然日期区间 | `YYYY-MM-DD` |
| `knowledge_cutoff` | 允许使用信息的最晚披露日期 | `YYYY-MM-DD`，由工作流注入 |
| `scope` | 事件查询范围 | `entity` 或 `corpus` |
| `order_by` | 事件排序方式 | `event_date_asc`、`event_date_desc` 或 `relevance` |
| `statement_types` | 财务报表类型 | `balance_sheet`、`income_statement`、`cashflow_statement` |
| `top_k` | 最大返回数量 | 正整数 |

所有集合参数始终使用复数数组，即使只有一个值也不得传入字符串。`report_periods`、`as_of_date` 与 `knowledge_cutoff` 分别表示财务归属期、业务观察时点和信息可知截止日，不能合并。

## 6. `document_search`

### 6.1 Operation

| Operation | 必填参数 | 可选参数 | 结果 |
|---|---|---|---|
| `search` | `query` | `company_ids`、`document_types`、`start_date`、`end_date`、`publishers`、`top_k`、`mode` | 按相关性排序的 Chunk、文档元数据、检索分数和原文证据 |

`search` 是唯一向 Planner 开放的文档操作。按 ID 加载 Chunk、BM25、向量召回、结果合并和重排都是内部步骤。

### 6.2 内部流程

```text
resolve_document_filters()
  -> search_bm25() + search_vector()
  -> merge_hybrid_hits()
  -> rerank_hits()
  -> load_chunks_by_ids()
  -> build_document_evidence()
```

### 6.3 能力边界

- `document_types` 只允许 `announcement` 和 `research_report`。
- 公告具有正文 Chunk；研报当前只有摘要，不代表研报全文。
- 精确财务数值优先使用 `financial_analysis`，不能把文本检索结果当作统一口径财务数据库。

## 7. `financial_analysis`

### 7.1 Operations

| Operation | 必填参数 | 可选参数 | 结果 |
|---|---|---|---|
| `metric_query` | `company_ids`、`metric_codes`、`report_periods` | `statement_types`、`currency` | 指标值、单位、报表口径和来源 |
| `metric_compare` | `company_ids`、`metric_codes`、`report_periods` | `comparison_method` | 跨期序列及变化，或跨公司同口径数值及差异 |
| `risk_scan` | `company_ids`、`report_periods` | `focus_topics`、`rule_ids` | 风险信号、规则计算过程和证据 ID |

### 7.2 参数基数

| Operation | `company_ids` | `report_periods` |
|---|---|---|
| `metric_query` | 至少 1 个 | 至少 1 个 |
| `metric_compare`：跨期 | 恰好 1 个 | 至少 2 个 |
| `metric_compare`：跨公司 | 至少 2 个 | 恰好 1 个 |
| `risk_scan` | 至少 1 个 | 至少 1 个 |

`company_ids` 和 `report_periods` 同时包含多个值时，比较维度不唯一，`metric_compare` 必须返回 `invalid_argument`。

### 7.3 职责边界

- `metric_query` 只查询，不计算公司间或期间间差异。
- 跨期 `metric_compare` 返回有序数值、相邻变化额、相邻变化率、首尾累计变化，并可计算 CAGR。
- 跨公司 `metric_compare` 返回同一期间的同口径数值、排序及差异，不构造行业基准或全市场排名。
- 工具负责数值计算；Agent 负责解释上升、下降、增速变化或拐点。
- `risk_scan` 执行明确规则和阈值，只输出风险信号，不能直接认定财务造假。

### 7.4 内部流程

```text
resolve_financial_period()
  -> load_statement_records()
  -> get_metric_value() / calculate_derived_metric()
  -> compare_metrics() 或 run_financial_risk_rules()
  -> build_financial_evidence()
```

## 8. `ownership_analysis`

### 8.1 Operations

| Operation | 必填参数 | 可选参数 | 结果 |
|---|---|---|---|
| `holding_query` | `as_of_date`，以及 `company_ids`、`holder_ids` 中至少一项 | `holder_types`、`top_n` | 正向、反向或交叉持股快照；公司方向附集中度 |
| `holding_compare` | `company_ids`、`start_date`、`end_date` | `holder_ids`、`change_threshold` | 股东进入、退出、增持、减持及数量和比例变化 |
| `penetration` | `source_entity_id`、`target_entity_id`、`as_of_date` | `max_depth`、`max_paths` | 有限持股路径、每跳比例、路径比例乘积和完整性警告 |

### 8.2 查询方向

| 参数组合 | 行为 |
|---|---|
| 只有 `company_ids` | 从公司查询主要股东，并计算快照集中度 |
| 只有 `holder_ids` | 从股东反查其出现在哪些公司主要股东快照中 |
| 两者都有 | 对公司和股东执行交叉过滤 |
| 两者都没有 | 返回 `invalid_argument` |

集中度是 `holding_query` 公司方向的派生结果，不再作为独立 operation。基金与自然人、企业等其他股东使用同一反向查询接口。

### 8.3 内部流程

```text
holding_query:
  query_holdings()
  -> calculate_ownership_concentration()
  -> build_ownership_evidence()

holding_compare:
  compare_holdings()
  -> build_ownership_evidence()

penetration:
  build_ownership_graph()
  -> find_ownership_paths()
  -> calculate_indirect_ratio()
  -> build_ownership_evidence()
```

### 8.4 能力边界

- 数据只覆盖主要股东快照，不代表完整持仓。
- 反向查询未命中不能证明主体没有持股。
- 进入十大股东不能直接证明控制关系、实际控制人或最终受益人。
- `penetration` 只能返回当前快照关系能够证明的有限路径；路径不完整时必须警告。

## 9. `event_timeline`

### 9.1 Operations

| Operation | 必填参数 | 可选参数 | 结果 |
|---|---|---|---|
| `event_query` | `scope` | `entity_ids`、`event_types`、`start_date`、`end_date`、`keywords`、`include_derived`、`order_by`、`top_k` | 筛选、去重并排序的事件节点和来源证据 |
| `event_cluster` | `scope`、`start_date`、`end_date` | `entity_ids`、`event_types`、`window_days`、`entity_overlap_threshold` | 事件簇、成员节点、时间跨度和聚合依据 |

`scope=entity` 时必须提供 `entity_ids`；`scope=corpus` 只表示当前违规公告语料全集，不代表完整市场事件。显式保留 `scope` 可以防止主体解析失败后把定向查询扩大到全语料。

### 9.2 职责边界

- `event_query` 负责筛选、去重和排序事件节点；Agent 负责将节点表达成自然语言时间线。
- `include_derived=true` 时可以包含财务风险和持股变化节点，但必须保留 `derived_signal` 类型。
- `event_cluster` 按事件类型、时间窗口和实体重合度聚合节点，只表达相关性和时序。
- 时间相近或处于同一事件簇不等于存在因果关系。

### 9.3 内部流程

```text
event_query:
  query_events()
  -> normalize_event_entities()
  -> deduplicate_events()
  -> align_derived_signals()
  -> order_event_nodes()
  -> build_event_evidence()

event_cluster:
  query_events()
  -> normalize_event_entities()
  -> deduplicate_events()
  -> cluster_related_events()
  -> build_event_evidence()
```

文档事件抽取由 `extract_events_from_documents()` 离线执行并保留原文证据，不应在每次在线查询时重复运行。

## 10. 证据与结论等级

| 类型 | 含义 | 示例 |
|---|---|---|
| `reported_fact` | 原始数据直接披露的事实 | 财报净利润、公告日期、持股比例 |
| `derived_metric` | 程序从披露事实确定性计算的指标 | 增长率、集中度、间接持股比例 |
| `derived_signal` | 规则根据指标生成的风险线索 | 现金流背离、主要股东显著减持 |
| `institution_opinion` | 证券机构的观点或预测 | 研报评级、盈利预测、风险提示 |
| `document_excerpt` | 可追溯的原文片段 | 违规公告正文或研报摘要 Chunk |

Agent 生成回答时必须区分披露事实、程序计算、风险信号和机构观点，不能把低等级结论提升为已经证实的事实。

## 11. 数据访问抽象

工具不应直接依赖某一种 CSV、JSONL 或数据库实现，而应通过 Repository 访问数据：

```text
DocumentRepository
  search(query, company_ids, document_types, start_date, end_date)

FinancialRepository
  get_statement(company_id, report_period, statement_type)
  get_metric_series(company_id, metric_code)
  compare_metrics(company_ids, metric_codes, report_periods, comparison_method)

OwnershipRepository
  query_holdings(company_ids, holder_ids, as_of_date)
  compare_holdings(company_ids, holder_ids, start_date, end_date)
  get_incoming_holding_edges(company_id, as_of_date)

EventRepository
  get_events(entity_ids, event_types, start_date, end_date)

EntityResolver
  resolve_dataset_entity(name_or_code, knowledge_cutoff)
```

Repository 负责屏蔽底层存储差异，工具层负责 operation 语义、参数校验、计算和证据组装。

## 12. 不支持的能力

现有数据不能可靠支持以下需求，工具必须返回 `unsupported` 或证据不足：

- 历史或实时行情、收益率、技术指标和市场排名；
- 完整基金持仓、完整控制关系和最终受益人保证；
- 数据集之外的政策新闻、券商业务办理说明和交易执行；
- 研报全文中未出现在摘要里的内容；
- 用户自选股、真实账户持仓、买卖和撤单；
- 缺乏证据的投资收益预测或确定性投资建议。

## 13. 后续实现顺序

1. 冻结 `ToolCall`、`ToolResult`、统一参数和错误码 Schema。
2. 实现 Repository 接口并对现有五组数据建立一致的读取层。
3. 按 operation 实现参数校验和确定性内部函数。
4. 为每个结果生成稳定的 evidence ID、来源和时间字段。
5. 将四个公共工具注册到统一 Registry，再接入 Planner。
6. 增加 Evidence Guard，检查回答是否超出工具结果和数据能力。
7. 分别编写工具单元测试、边界测试、错误测试和性能测试。

每个 operation 至少应覆盖：正常调用、缺少必填参数、数组基数错误、无数据、超出 `knowledge_cutoff`、数据源失败和证据不足七类测试场景。
