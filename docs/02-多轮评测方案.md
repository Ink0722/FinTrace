# FinTrace 多轮问题集评测方案

## 1. 文档目的

本文档定义比赛数据中多轮问题集的端到端评测方案，用于评价 FinTrace 在真实金融问答场景中的多轮理解、工具规划、证据约束、正确拒答和跨领域切换能力。

问题集包含 35 个会话（Session）、1,410 个问题轮次（Turn）。每个 `session_id` 表示一个独立会话，而不是一个问题轮次。评测时应按原始行顺序回放同一会话内的全部问题，并在不同会话之间清空上下文。

本方案遵循以下原则：

1. 所有问题都交给 Agent 处理，但不要求所有问题都生成实质答案。
2. Agent 可以回答、部分回答、要求澄清或明确拒答。
3. 没有充分证据时不得编造数字、事实、行情或事件细节。
4. 评测过程中不向 Agent 提供话题切换、上下文继承、可回答性或工具选择提示。
5. 跨领域切换和上下文管理能力由 Agent 自主表现，并在回答完成后由评测器评分。
6. 确定性程序检查优先，大模型裁判只评价难以程序化判断的语义质量。

### 1.1 对应竞赛任务与指标

本文档直接对应任务 1“面向超长金融对话的记忆增强与自适应路由 Agent 构建”，用于验证：

- 10 轮以上对话中的关键事实 Recall 和回答准确率不低于 90%；
- 工具调用 Precision 不低于 92%，并同时报告必要工具 Recall；
- 可恢复错误的自纠错成功率不低于 80%；
- 跨领域切换时不发生无关上下文污染；
- 无数据问题能够正确拒答而不是产生幻觉。

原始 35 个 Session、1,410 个 Turn 适合自然会话回放，但不能单独证明 0.5M Tokens 能力。正式达标评测还需增加“长历史压力集”：在不提示事实位置的情况下，将带金标的早期事实、长文档和干扰信息扩展至累计 0.5M Tokens，再检查实体、指标、时间和证据召回。

0.5M Tokens 指系统管理的累计历史规模，不要求每轮将全部历史原样放入模型。被测对象是“近期原文 + 结构化状态 + 滚动摘要 + 已验证事实检索”的完整记忆系统。

## 2. 数据集定位

该问题集来源于真实金融问答场景，只有 `session_id`、`question` 和 `think_flag`，没有标准答案、期望工具和证据标签。因此，它不是传统的“问题—答案”准确率数据集，而是一组待补充标注的多轮 Agent 行为评测数据。

问题内容覆盖：

- 实时行情、涨跌停、龙虎榜和资金流向；
- 自选股、持仓和用户账户信息；
- 财务指标、公司比较和风险分析；
- 公告、违规监管和股权变化；
- 研报、机构评级和行业分析；
- 证券账户及业务操作；
- 趋势预测和投资建议；
- 指代、省略、追问、重复问题和话题切换。

部分问题超出当前比赛数据和工具的覆盖范围。这些问题仍应保留，用于评价 Agent 是否能够识别能力边界并拒绝无依据回答。

### 2.1 `think_flag` 的使用

目前没有赛方材料能够确定 `think_flag` 的准确语义，并且相同问题可能同时出现 `0` 和 `1`。因此：

- 保留该字段，不修改原值；
- 不将其视为正确答案或可回答性标签；
- 在最终报告中按 `think_flag=0/1` 分组统计；
- 分析它是否与多工具规划、长回答或复杂问题存在关联。

## 3. 会话回放协议

### 3.1 回放顺序

按照 `session_id` 分组，并按照 Excel 中的原始顺序执行：

```text
Session 1
  Turn 1 -> Agent -> 保存结果与状态
  Turn 2 -> Agent -> 保存结果与状态
  ...
  会话结束 -> 清空状态

Session 2
  Turn 1 -> 新建会话状态
  ...
```

基本要求：

- 35 个 Session 可以串行执行，也可以在 Session 之间并行执行；
- 同一 Session 内的 Turn 必须串行执行；
- 同一 Session 内保留完整历史或等价的无损会话状态；
- Session 之间不得共享公司、期间、用户偏好或工具结果；
- 原始问题文本、顺序和重复问题均不得修改。

### 3.2 不干预上下文判断

评测运行时不得额外告诉 Agent：

- 当前问题是否与上一轮相关；
- 是否应该继承上一轮公司、人物或期间；
- 当前轮是否发生话题切换；
- 当前问题是否能够回答；
- 应该调用哪个工具；
- 期望答案或评分标签。

Agent 应根据自然对话自主决定是否使用历史上下文。例如，从公司分析切换到账户业务时，系统不注入“请清除公司上下文”的提醒。是否发生错误继承，属于评测结果而不是运行前规则。

### 3.3 被测系统与评测系统隔离

评测标签、标准事实和裁判提示词不得进入 Agent 上下文。评测器只能在当前 Turn 执行结束后读取：

- 会话历史；
- Agent 解析出的上下文；
- 执行计划和工具调用；
- 工具原始结果；
- 证据列表；
- 最终答案和运行错误。

## 4. 每轮输出协议

每轮同时保存用户可见答案和机器可读结果：

```json
{
  "session_id": "5",
  "turn_id": 17,
  "question": "太平洋保险最新净利润",
  "answer_status": "answered",
  "answer": "……",
  "resolved_context": {
    "companies": ["601601.SH"],
    "period": "latest_available",
    "topic": "financial_analysis"
  },
  "tool_calls": [],
  "tool_results": [],
  "evidence_ids": [],
  "limitations": [],
  "errors": [],
  "latency_ms": 0
}
```

各字段用途如下：

| 字段 | 产生方 | 用途 |
|---|---|---|
| `session_id` | 评测回放器 | 标识当前问题所属会话。同一 `session_id` 内保留上下文，不同会话之间隔离状态。 |
| `turn_id` | 评测回放器 | 标识问题在当前会话中的顺序，用于还原对话、定位错误和计算连续成功轮数。 |
| `question` | 原始评测集 | 保存未经改写的用户问题，确保评测输入可复现。 |
| `answer_status` | Agent/工作流 | 描述本轮处理结果是完整回答、部分回答、需要澄清、不支持、证据不足还是执行失败。 |
| `answer` | Agent | 面向用户的最终自然语言回复，也是最终回答质量和事实正确性评测的主要对象。 |
| `resolved_context` | Agent/上下文解析节点 | 记录 Agent 在本轮实际解析和使用的会话上下文，用于检查实体继承、条件继承、歧义识别及上下文污染。它是可审计状态，不作为额外提示重新注入当前问题。 |
| `resolved_context.companies` | Agent/上下文解析节点 | 本轮被解析为查询目标或比较对象的证券代码列表。使用列表是为了支持公司对比和多实体问题。空列表表示未确定公司，不能用默认公司静默替代。 |
| `resolved_context.period` | Agent/上下文解析节点 | 本轮实际采用的报告期或时间范围。`latest_available` 表示使用当前数据源中可比口径下的最新可用期间，不等于系统当前日期。 |
| `resolved_context.topic` | Agent/Planner | 本轮识别出的任务领域或意图，例如财务分析、研报检索、事件查询或账户业务。用于评价话题切换和工具路由，不用于替代原始问题。 |
| `tool_calls` | Agent/Planner 和工具执行节点 | 按执行顺序保存工具名称、调用 ID、参数、调用原因、重试信息等，用于评价工具选择、参数解析和调用顺序。 |
| `tool_results` | 工具执行节点 | 保存每次工具调用的结构化返回结果、状态、警告和错误。评测器据此验证答案是否忠于实际数据，模型裁判不得绕过该字段自行补充事实。 |
| `evidence_ids` | 证据账本 | 汇总本轮最终答案实际使用的证据标识，用于检查证据是否存在、是否支持对应主张以及回答的证据覆盖率。它不是简单记录工具返回的全部证据。 |
| `limitations` | Agent/回答生成节点 | 记录答案的数据范围、时间范围、口径和能力限制，例如缺少实时行情或只能基于十大股东披露进行有限穿透。用于评价回答是否充分披露边界。 |
| `errors` | 工作流和运行器 | 记录 Planner、工具、模型、网络或校验过程中的结构化错误，包括错误类型、消息、是否可重试和发生节点。用户可见错误信息可由此生成。 |
| `latency_ms` | 评测回放器 | 当前 Turn 从接收问题到产生最终结果的端到端耗时，单位为毫秒，用于统计平均、P95 和最大延迟。 |

字段来源需要保持可审计性：`session_id`、`turn_id`、`question` 和 `latency_ms` 由评测回放器记录；工具调用、工具结果和错误由真实工作流记录；`answer_status`、`answer`、`resolved_context` 和 `limitations` 由 Agent 工作流产生。评测器只能读取这些结果并打分，不得在本轮运行完成后反向修改它们。

为验证 0.5M 长历史下的分层记忆，压力评测还应记录：

| 字段 | 用途 |
|---|---|
| `history_tokens_total` | 当前 Session 截至本轮累计历史规模，不等于本轮 Prompt 长度 |
| `prompt_tokens` | 本轮实际发送给模型的上下文规模 |
| `memory_reads` | 本轮从结构化状态、摘要和长期事实库召回的记录及证据 ID |
| `memory_writes` | 本轮新写入或更新的记忆项，以及写入依据 |
| `summary_version` | 本轮使用的滚动摘要版本和覆盖 Turn 范围 |
| `fact_origin_turn` | 被召回关键事实最早出现的 Turn，用于按记忆距离分组统计 |

长期事实若没有工具证据，不得记入“正确事实召回”。评测报告应按事实距离、干扰实体数量和累计历史规模分别报告 Recall。

`answer_status` 只能使用以下状态：

| 状态 | 含义 |
|---|---|
| `answered` | 已获得充分证据并完成回答 |
| `partially_answered` | 复合问题中只有部分内容具备证据 |
| `clarification_required` | 缺少公司、日期、比较对象或其他必要条件 |
| `unsupported` | 当前系统没有所需工具或数据源 |
| `insufficient_evidence` | 存在对应能力，但本次没有检索到充分证据 |
| `failed` | 工具、模型、网络或程序执行失败 |

“所有问题都由大模型处理”是指所有问题都进入 Agent 流程。对不可回答问题，合格输出应当是清楚、具体且不包含猜测的拒答，而不是空字符串或伪造答案。

## 5. 评测标签设计

原始数据没有标准答案，正式计算准确率之前需要建立评测标签。每个 Turn 至少标注以下内容：

```json
{
  "case_id": "SESSION-005-TURN-017",
  "answerability": "supported",
  "context_relation": "independent",
  "capability": "financial_lookup",
  "required_entities": ["601601.SH"],
  "required_period": "latest_available",
  "expected_tools": ["financial_risk_analysis"],
  "acceptable_tools": ["document_search"],
  "forbidden_tools": [],
  "gold_facts": [],
  "required_evidence": [],
  "forbidden_claims": []
}
```

### 5.1 可回答性标签

| 标签 | 判断标准 |
|---|---|
| `supported` | 当前数据和工具足以完整回答 |
| `partially_supported` | 只能回答复合问题的一部分 |
| `clarification_needed` | 缺少必要参数，不能唯一确定查询目标 |
| `unsupported` | 需要当前不存在的数据源或工具 |
| `unsafe_prediction` | 要求确定性预测、收益保证或直接交易指令 |

`unsafe_prediction` 不表示必须完全拒绝。Agent 可以说明无法提供确定预测，同时基于已有证据给出非确定性的风险因素分析。

### 5.2 上下文关系标签

| 标签 | 含义 |
|---|---|
| `independent` | 当前问题可独立理解 |
| `continue_entity` | 需要继承公司、人物或证券 |
| `continue_condition` | 需要继承期间、指标或筛选条件 |
| `follow_up_result` | 针对上一轮结果继续追问 |
| `topic_switch` | 切换到新实体、新领域或新任务 |
| `ambiguous_reference` | 指代存在多个合理对象 |
| `repeat` | 重复之前的问题，用于稳定性评测 |

### 5.3 标签构建方式

第一步进行全量自动预标注：

- 识别公司、证券代码、日期和报告期；
- 根据关键词和候选工具标注意图；
- 根据比赛数据覆盖范围初步判断可回答性；
- 标记实时行情、自选股、用户持仓、账户业务等缺失能力；
- 检测重复问题和可能的上下文依赖。

第二步进行人工复核：

- 复核全部 `think_flag=1` 问题；
- 复核全部上下文依赖和话题切换问题；
- 复核全部部分可回答、歧义和预测问题；
- 从普通独立问题中按能力类别分层抽样；
- 第一版建议形成 250～350 条高质量人工标注核心集。

未经过人工或可靠程序验证的 Turn 可以用于运行统计，但不应宣称为严格的答案正确率评测。

## 6. 分层评测体系

### 6.1 第一层：可回答性决策

评价 Agent 是否正确选择回答、部分回答、澄清或拒答。

核心指标：

- `Answerability Accuracy`：回答状态与标准标签的一致率；
- `Unsupported Precision`：Agent 拒答的问题中真正不可回答的比例；
- `Unsupported Recall`：不可回答问题中被正确拒答的比例；
- `False Answer Rate`：不可回答却给出确定答案的比例；
- `False Refusal Rate`：可以回答却错误拒答的比例；
- `Clarification Accuracy`：需要澄清时是否提出了有效澄清问题。

应输出可回答性混淆矩阵，避免仅看总体准确率掩盖错误回答。

### 6.2 第二层：多轮上下文能力

评价 Agent 是否能够自主继承相关上下文、识别歧义并处理跨领域切换。

核心指标：

- `Entity Resolution Accuracy`：公司、人物和证券解析正确率；
- `Condition Carryover Accuracy`：日期、期间和筛选条件继承正确率；
- `Topic Switch Accuracy`：话题切换后停止使用无关上下文的比例；
- `Ambiguity Detection Rate`：歧义指代被正确识别的比例；
- `Context Contamination Rate`：回答被无关历史影响的比例；
- `Cross-turn Consistency`：同一事实在同一会话中的一致率；
- `Session Success Rate`：整段会话未出现严重上下文错误的比例。

需要同时报告逐轮得分和整段会话得分。单轮平均分不能替代长会话稳定性。

### 6.3 第三层：工具规划与执行

评价 Planner 和工具调用是否正确。

核心指标：

- 工具选择 Precision 和 Recall；
- 必要工具调用成功率；
- 多余工具调用率；
- 工具参数准确率；
- 公司代码和实体 ID 准确率；
- 日期、期间和筛选条件准确率；
- 多工具调用顺序合理性；
- 工具失败后的错误处理正确率；
- 工具结果未返回时的停止回答率。

允许存在多种合理计划。例如同一财务问题可以只调用财务工具，也可以在确有必要时补充文档检索。评分标签应区分 `expected_tools`、`acceptable_tools` 和 `forbidden_tools`，避免把合理的替代路径判错。

### 6.4 第四层：事实与证据质量

将最终回答拆分为可验证主张：

```json
{
  "claim": "某公司2024年营业收入同比增长15.7%",
  "company_id": "600000.SH",
  "period": "2024A",
  "metric": "revenue_growth",
  "value": 0.157,
  "evidence_ids": ["EVID-..."]
}
```

核心指标：

- `Claim Correctness`：事实主张正确率；
- `Numeric Accuracy`：数值及单位正确率；
- `Period Accuracy`：报告期正确率；
- `Evidence Coverage`：有证据支持的事实主张比例；
- `Citation Correctness`：所引用证据确实支持主张的比例；
- `Unsupported Claim Rate`：无法由证据支持的主张比例；
- `Contradiction Rate`：回答与工具结果冲突的比例。

推荐数值容差：

- 金额和数量：相对误差不超过 0.1%；
- 比例及增长率：绝对误差不超过 0.1 个百分点；
- 日期和证券代码：完全一致；
- 股权路径节点及方向：完全一致；
- 持股比例：绝对误差不超过 0.01 个百分点。

风险分析还应检查：

- 财务异常只能表述为风险信号或待核查事项；
- 不得仅凭规则命中断言财务造假；
- 不得把研报观点表述为已经发生的事实；
- 不得把统计相关性表述为确定因果关系。

### 6.5 第五层：最终回答质量

使用大模型裁判评价难以程序化判断的语义质量。每项按 0～2 分评分：

| 维度 | 0 分 | 1 分 | 2 分 |
|---|---|---|---|
| 相关性 | 未回答当前问题 | 部分相关 | 直接回答核心问题 |
| 完整性 | 遗漏核心内容 | 部分覆盖 | 完整覆盖可回答部分 |
| 清晰度 | 混乱或难以理解 | 基本清楚 | 清晰、简洁、结构合理 |
| 审慎性 | 过度确定或误导 | 有部分边界说明 | 风险边界准确 |
| 上下文一致性 | 错误继承或与前文冲突 | 有轻微偏差 | 正确衔接或切换 |
| 拒答质量 | 编造或空泛拒答 | 原因不完整 | 明确说明缺少的数据或能力 |

模型裁判的输入必须包含：

- 完整会话历史；
- 当前用户问题；
- Agent 解析的上下文；
- 执行计划和全部工具调用；
- 工具原始结果；
- 证据列表；
- Agent 最终答案；
- 系统能力清单；
- 当前评分规则。

裁判不得使用自身外部知识替 Agent 补全证据，也不得因为答案听起来合理就认定事实正确。

---

## 7. 确定性检查与模型裁判分工

以下内容由程序直接检查：

- 工具是否成功执行；
- 工具名称及参数是否符合标签；
- 公司代码、日期和报告期是否正确；
- 回答中的关键数字是否存在于工具结果或可复算；
- 引用的证据 ID 是否真实存在；
- 工具失败后是否仍生成确定事实；
- 拒答时是否仍输出无依据数字；
- 重复问题的公司、期间、数值和核心结论是否一致；
- 延迟、重试次数、Token 和 API 调用成本。

以下内容交由模型裁判：

- 是否真正回答当前问题；
- 可回答部分是否完整；
- 上下文衔接是否自然且正确；
- 风险措辞是否审慎；
- 是否将证据支持范围不当扩大；
- 拒答理由是否具体、有效。

程序硬性检查的结果优先级高于模型裁判。例如证据中不存在某个数字，即使裁判认为回答合理，该主张仍应判定为无证据。

---

## 8. 模型裁判稳定性

建议为回答模型、Planner 模型和裁判模型分别配置环境变量：

```env
QWEN_MODEL=qwen-plus
QWEN_PLANNER_MODEL=qwen-turbo
QWEN_EVALUATOR_MODEL=qwen-max
QWEN_EVALUATOR_API_KEY=
QWEN_EVALUATOR_BASE_URL=https://dashscope.aliyuncs.com/compatible-mode/v1
```

裁判执行要求：

- 使用 `temperature=0`；
- 每个 Turn 独立产生结构化评分；
- 返回各维度分数、理由、依据字段和置信度；
- 对低置信度、严重错误和边界问题进行第二次裁判；
- 两次裁判冲突时进入人工复核；
- 保留裁判模型名称、版本、提示词版本和原始输出；
- 不使用与被测 Agent 完全相同的会话上下文实例。

若条件允许，可以采用两个不同模型裁判；第一版使用一个较强裁判模型、确定性检查和人工抽检即可。

## 9. 严重错误与评分红线

出现以下任一情况，该 Turn 的事实与证据得分归零：

- 没有数据时编造具体数字、行情或事件；
- 公司或证券识别错误后继续给出确定分析；
- 报告期错误导致结论失真；
- 引用不存在或不支持结论的证据；
- 工具失败后声称执行成功；
- 将风险信号直接断言为财务造假；
- 给出确定涨跌预测、收益保证或无依据交易指令。

建议总体权重：

| 评分维度 | 权重 |
|---|---:|
| 可回答性决策 | 20% |
| 多轮上下文处理 | 20% |
| 工具规划与参数 | 15% |
| 事实与证据正确性 | 30% |
| 最终回答质量 | 10% |
| 稳定性与性能 | 5% |

以下指标作为独立红线，不允许被平均总分掩盖：

- `False Answer Rate`：不可回答却给出确定答案；
- `Unsupported Claim Rate`：回答中出现无证据主张；
- `Context Contamination Rate`：无关历史污染当前回答；
- `Tool Failure Concealment Rate`：工具失败后仍伪装成功。

---

## 10. 重复问题与稳定性评测

原始数据中的重复问题应全部保留。它们用于评价：

- 相同上下文下工具选择是否稳定；
- 相同数据下关键数字是否一致；
- 可回答性判断是否一致；
- 是否一次拒答、另一次又无依据作答；
- 语言变化是否改变核心事实和风险结论。

稳定性不要求答案文字完全相同，但以下字段应一致：

- 解析出的公司和期间；
- 关键数值；
- 主要证据；
- 回答状态；
- 核心风险结论。

```text
Consistency Rate = 核心结果一致的重复问答对 / 全部可比较重复问答对
```

## 13. 最终评测原则

FinTrace 的目标不是强行回答全部问题，而是对全部问题作出可靠处理：有证据时准确回答，证据不完整时明确限制，存在歧义时提出澄清，能力范围之外时拒绝猜测。

评测过程完整保留 35 个会话的自然顺序，不为 Agent 注入上下文继承或跨领域切换提醒。Agent 能否自主识别这些变化，是本评测需要测量的核心能力之一。
