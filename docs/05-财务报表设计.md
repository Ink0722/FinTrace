# FinTrace 财务报表数据设计与 Agent 应用方案

## 1. 文档目的

本文档定义比赛数据组 4 三张 A 股财务报表的字段使用、期间口径、标准化存储、指标计算、风险规则和 Agent 接入方案。

财务数据是精确结构化数据，应由程序查询和计算，不应依赖向量检索或大模型心算。所有财务结论必须保留公司、报告期、报表类型、公告日期、指标字段和计算公式。

### 1.1 对应竞赛任务与指标

本文档对应任务 3“财务异象智能甄别与多维评分引擎”。三张主表能够支撑利润/现金流背离、存货和应收异常、偿债压力及部分期间费用规则，但关联交易、审计意见、税务口径和非经常性损益仍需附注或公告正文补充。

竞赛要求的风险预警 F1 不低于 85%，必须建立独立金标集后计算。当前财务表没有欺诈标签，不能把规则命中率称为 F1。金标单位建议为 `company_id + report_period + risk_type`，正样本需要监管正文或专家确认，并采用公司级或时间切分避免数据泄漏。

专家盲评优秀率不低于 80% 的报告应同时展示预警点、数据对比、公式、输入证据、可能业务风险和限制说明。风险信号不得直接写成财务造假结论。

## 3. 三张报表的业务差异

### 3.1 资产负债表

资产负债表是时点数据，表示报告期末的资产、负债和权益余额，例如：

- 货币资金；
- 应收账款；
- 存货；
- 流动资产；
- 总资产；
- 短期借款；
- 流动负债；
- 总负债；
- 股东权益。

2025-06-30 的存货可以直接理解为该日余额，但不能与收入一样理解为“上半年累计发生额”。

### 3.2 利润表

利润表是期间流量数据，通常表示本年初至报告期末的累计金额，例如：

- 营业收入；
- 营业成本；
- 管理费用、销售费用和研发费用；
- 营业利润；
- 净利润；
- 归母净利润。

半年报和三季报通常是年初至期末累计口径，不能将相邻报告期直接当成相邻季度独立值。

### 3.3 现金流量表

现金流量表同样是期间流量数据，通常表示累计现金流，例如：

- 销售商品收到的现金；
- 经营活动现金流入和流出；
- 经营活动现金流量净额；
- 投资活动现金流量净额；
- 筹资活动现金流量净额；
- 现金及现金等价物净增加额。

财务工具必须在 Schema 中区分 `instant` 与 `year_to_date`，否则增长率和季度比较会发生口径错误。

## 4. 通用字段

| 字段 | 含义 | 系统用途 |
|---|---|---|
| `object_id` | 来源记录唯一 ID | 行级主键和证据来源 |
| `s_info_windcode` | 证券代码 | 标准 `company_id` |
| `wind_code` | Wind 代码 | 与证券代码交叉校验 |
| `ann_dt` | 首次公告日期 | 历史可知性判断 |
| `actual_ann_dt` | 实际公告日期 | 优先用于公告时间和防止前视偏差 |
| `report_period` | 报告期截止日 | 统一转换为 ISO 日期和期间标签 |
| `statement_type` | 报表类型代码 | 保留原值，待代码语义确认 |
| `crncy_code` | 货币代码 | 当前样本主要为 CNY，仍需逐行保留 |
| `comp_type_code` | 公司类型代码 | 区分非金融、银行、保险、证券等口径 |
| `s_info_compcode` | 公司主体代码 | 连接证券主表和股权数据 |
| `opdate` | 来源侧操作日期 | 数据审计字段 |
| `opmode` | 来源侧操作模式 | 语义未确认前保留，不据此过滤记录 |
| `is_calculation` | 是否计算报表 | 保留来源值；本批资产负债表该列呈 `null` 文本，不能当作有效布尔值 |

同一经济指标可能存在新旧准则字段或合计字段，不能只按名称相似就相加或互相覆盖。指标映射必须记录选用了哪个原始字段。

## 5. 标准指标映射

第一版应只映射规则和常见问答真正需要的指标，并逐步扩展。推荐候选映射如下：

| 内部指标 | 优先原始字段 | 报表 | 说明 |
|---|---|---|---|
| `TOTAL_ASSETS` | `tot_assets` | 资产负债表 | 总资产 |
| `TOTAL_LIABILITIES` | `tot_liab` | 资产负债表 | 总负债 |
| `CURRENT_ASSETS` | `tot_cur_assets` | 资产负债表 | 流动资产合计 |
| `CURRENT_LIABILITIES` | `tot_cur_liab` | 资产负债表 | 流动负债合计 |
| `INVENTORY` | `inventories` | 资产负债表 | 存货 |
| `ACCOUNTS_RECEIVABLE` | `acct_rcv` | 资产负债表 | 应收账款，需评估新口径字段 |
| `MONETARY_CAPITAL` | `monetary_cap` | 资产负债表 | 货币资金 |
| `REVENUE` | `oper_rev` 或 `tot_oper_rev` | 利润表 | 应根据公司类型和字段可用性确定，不得重复计入 |
| `OPERATING_COST` | `less_oper_cost` | 利润表 | 营业成本 |
| `NET_PROFIT_PARENT` | `net_profit_excl_min_int_inc` | 利润表 | 归属于母公司股东的净利润口径 |
| `OPERATING_PROFIT` | `oper_profit` | 利润表 | 营业利润 |
| `R_AND_D_EXPENSE` | `rd_expense` | 利润表 | 研发费用 |
| `OPERATING_CASHFLOW` | `net_cash_flows_oper_act` | 现金流量表 | 经营活动现金流量净额 |
| `CASH_RECEIVED_FROM_SALES` | `cash_recp_sg_and_rs` | 现金流量表 | 销售商品、提供劳务收到的现金 |

映射记录应包含：

```text
metric_code
source_statement
source_column
applicable_company_types
value_nature
unit
mapping_version
```

### 5.1 毛利润

非金融企业可以在字段和口径均可用时计算：

```text
GROSS_PROFIT = REVENUE - OPERATING_COST
GROSS_MARGIN = GROSS_PROFIT / REVENUE
```

银行、保险和证券公司业务结构不同，不能沿用普通工商企业毛利率公式。工具应根据 `comp_type_code` 返回“不适用”或使用行业专门指标。

### 5.2 非经常性损益

现有规则需要 `NON_RECURRING_PROFIT`，但本批数据中的扣非净利润候选字段没有有效覆盖。因此第一版不能可靠计算“非经常性损益依赖”。

正确行为是：

```text
rule_status = not_evaluable
reason = missing_non_recurring_profit_metric
```

不能把指标缺失解释为规则未触发，也不能输出低风险结论。

## 6. 期间标准化与比较规则

### 6.1 统一期间标签

建议同时保存：

```text
report_period_date = 2025-06-30
fiscal_year = 2025
period_type = H1
value_nature = instant | year_to_date
```

常见期间映射：

| 截止日 | `period_type` |
|---|---|
| 03-31 | `Q1` |
| 06-30 | `H1` |
| 09-30 | `Q3_YTD` |
| 12-31 | `FY` |

如果公司会计年度并非自然年度或截止日异常，应标记并避免自动套用。

### 6.2 同比比较

默认使用同类报告期同比：

```text
2025Q1 对比 2024Q1
2025H1 对比 2024H1
2025Q3_YTD 对比 2024Q3_YTD
2025FY 对比 2024FY
```

禁止将 `2025H1` 与 `2024FY` 直接计算增长率。当前代码按排序后的相邻期间比较，需要在比赛数据接入时修改。

### 6.3 单季度值

只有在累计口径完整时才能推导单季度值：

```text
Q2 = H1 - Q1
Q3 = Q3_YTD - H1
Q4 = FY - Q3_YTD
```

推导值必须标记为 `derived_metric`，并同时引用两个来源期间。缺少任一期间时不计算。

### 6.4 时点可知性

回答历史问题时必须过滤：

```text
actual_announcement_date <= as_of_date
```

若用户问“2025 年 3 月 1 日当时已知的财务情况”，不能使用之后公告的 2024 年报或 2025 年一季报。

### 6.5 修订和版本

当前业务键 `(company_id, report_period, statement_type)` 未发现重复，但仍应保留 `object_id`、`ann_dt`、`actual_ann_dt` 和来源侧操作字段，以支持未来更正报表和版本选择。

## 7. 本数据可以实现的功能

### 7.1 精确指标查询

- 某公司某期营业收入、净利润和经营现金流；
- 某公司最新可用报告期的资产、负债、存货和应收账款；
- 指标单位、报告期和公告日期；
- 多个指标的结构化财务摘要。

### 7.2 趋势和公司比较

- 同一公司同口径同比变化；
- 多家公司同一报告期指标比较；
- 资产负债率、流动比率和现金流质量比较；
- 行业比较，但前提是存在可靠的行业映射和可比公司集合。

### 7.3 财务风险信号

可以基于已有字段实现或改进：

- 净利润增长与经营现金流背离；
- 存货增长显著快于营业收入；
- 应收账款增长显著快于营业收入；
- 资产负债率和短期偿债压力；
- 毛利率异常，仅适用于合适公司类型；
- 经营现金流与收入质量；
- 期间费用变化；
- 资产减值和信用减值信号。

规则必须输出 `triggered`、`not_triggered` 或 `not_evaluable`，并列出所需指标、实际指标和阈值。

### 7.4 与文档和事件联合分析

- 用公告正文解释财务更正、处罚或问询；
- 用研报摘要补充机构观点；
- 将财务异常作为 `derived_signal` 放入事件时间线；
- 将主要股东变化与财务风险时点对齐。

## 8. 本数据不能单独支持的结论

三张财务主表不能单独支持：

- 财务造假认定；
- 审计意见和审计调整细节；
- 财务附注中的关联交易、客户集中度和会计政策；
- 行业排名，除非建立完整行业分类和可比样本；
- 实时业绩和报告期之后的经营情况；
- 由财务变化直接导致股价涨跌的因果结论；
- 缺少指标时的“未触发风险”判断。

风险规则只能产生核查线索，必须结合年报附注、审计报告、问询函和业务背景。

## 9. 标准化存储设计

### 9.1 保留宽表

正式数据库建议保留三张来源宽表：

```text
financial_balance_sheets
financial_income_statements
financial_cashflows
```

优点是保留原始字段、便于审计且避免把数百万空值拆成长表。

### 9.2 建立指标视图或窄表

同时建立只包含已映射常用指标的窄表：

```text
financial_metrics
- company_id
- report_period_date
- period_type
- statement_type
- metric_code
- value
- currency
- value_nature
- source_table
- source_column
- source_object_id
- actual_announcement_date
- evidence_id
- mapping_version
- quality_flags
```

这样既能保留完整原始宽表，又能让在线工具高效查询有限指标。

### 9.3 推荐索引

```sql
CREATE INDEX idx_fin_metric_company_period
ON financial_metrics(company_id, report_period_date, metric_code);

CREATE INDEX idx_fin_metric_ann_date
ON financial_metrics(company_id, actual_announcement_date);
```

## 10. 数据访问接口

建议提供：

```text
FinancialRepository
  get_available_periods(company_id, as_of_date)
  get_metrics(company_id, period, metric_codes, as_of_date)
  get_metric_series(company_id, metric_code, period_type, as_of_date)
  compare_companies(company_ids, metric_codes, period, as_of_date)
```

Repository 负责：

- 公司和期间过滤；
- 公告日期过滤；
- 原始字段映射；
- 单位和数值类型；
- 数据质量标志；
- 来源证据。

指标计算和风险规则位于工具领域层，不应塞进 SQL Loader。

## 11. 接入 `financial_risk_analysis`

### 11.1 查询模式

```json
{
  "company_ids": ["600519.SH"],
  "query_mode": "risk_detection",
  "period": "latest_comparable",
  "as_of_date": "2026-05-26",
  "metric_codes": [],
  "focus_topics": ["cashflow", "inventory"]
}
```

| 模式 | 用途 |
|---|---|
| `metric_lookup` | 精确查询指标 |
| `trend_analysis` | 同口径跨期趋势 |
| `company_comparison` | 多公司比较 |
| `risk_detection` | 风险规则执行 |

为了兼容现有 Planner，可以继续接受单个 `company_id`，内部统一转换为 `company_ids`。

### 11.2 工具工作流

```text
参数校验
  -> 证券主表解析公司
  -> Repository 选择可用期间和指标
  -> 期间口径校验
  -> 计算派生指标
  -> 逐条运行风险规则
  -> 规则可评估性检查
  -> 生成 reported_fact / derived_metric / derived_signal 证据
  -> 返回结构化结果
```

### 11.3 风险规则状态

建议将当前布尔 `triggered` 扩展为：

```text
triggered
not_triggered
not_evaluable
```

`not_evaluable` 必须包含缺失指标和原因，不计入低风险评分。

## 12. 证据设计

原始指标证据：

```text
EVID-FIN-<object_id>-<source_column>
```

事实内容：

```json
{
  "company_id": "600519.SH",
  "report_period": "2024-12-31",
  "period_type": "FY",
  "metric_code": "NET_PROFIT_PARENT",
  "source_column": "net_profit_excl_min_int_inc",
  "value": 0,
  "currency": "CNY",
  "actual_announcement_date": "2025-03-31"
}
```

派生指标应生成独立证据，记录公式和输入证据：

```json
{
  "evidence_type": "derived_metric",
  "metric_code": "REVENUE_GROWTH_YOY",
  "formula": "(current - prior) / abs(prior)",
  "input_evidence_ids": ["EVID-FIN-...", "EVID-FIN-..."]
}
```

风险信号引用派生指标证据，不重复伪装成原始披露事实。

## 13. 回答生成约束

回答模型必须：

- 明确公司、报告期、口径和单位；
- 区分累计值、时点值和推导的单季度值；
- 说明实际使用的可比期间；
- 对缺失指标说明“无法评估”，不能写成“未发现风险”；
- 将规则结果称为风险信号；
- 不把机构观点混入财务表事实；
- 不根据财务异常断言财务造假；
- 不输出工具结果中不存在的精确数字。

---

## 14. 与当前代码的适配缺口

现有财务工具读取标准化长表，并实现四条规则。接入比赛宽表前需要：

1. 三张宽表的 SQLite 导入；
2. 原始字段到内部指标的版本化映射；
3. `FinancialRepository`；
4. 同报告期同比选择，替换当前相邻期间比较；
5. 累计流量与时点余额区分；
6. 单季度推导及证据链；
7. 公司类型适用性判断；
8. 风险规则 `not_evaluable` 状态；
9. 禁用当前不可计算的非经常性损益规则，直到获得可靠指标；
10. 指标查询、趋势、比较和风险四种模式；
11. 财务证据分类和公式记录；
12. 数据质量及端到端测试。

---

## 15. 推荐实施顺序

1. 建立证券主表和公司类型映射；
2. 导入三张原始宽表；
3. 建立第一版指标映射表；
4. 生成 `financial_metrics`；
5. 实现精确指标查询；
6. 实现可比期间选择和同比；
7. 改造现有四条风险规则的可评估状态；
8. 加入公司比较和趋势分析；
9. 增加更多经过验证的财务规则；
10. 与公告、研报和股权工具联合测试。

第一版优先保证指标值、期间和证据正确，再扩充规则数量。规则少但口径可靠，比大量口径错误的风险标签更有比赛价值。

---

## 16. 最终原则

三张财务报表应被建设为 FinTrace 的精确财务事实层。SQLite 负责数据查询，程序负责期间选择、公式计算和规则判断，大模型只负责解释结果。

任何财务风险结论都必须回答三个问题：使用了哪一期数据、采用了什么公式、哪些证据支持该结论。缺少其中任何一项，都不应生成确定性风险判断。
