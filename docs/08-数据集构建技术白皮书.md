# FinTrace 数据集构建技术白皮书

## 1. 文档定位

本文描述 FinTrace 项目如何将赛题提供的五组原始数据，构建为可检索、可计算、可追溯的数据底座。内容覆盖数据盘点、格式转换、类型标准化、公告正文获取、异常修复、质量验收和最终排除策略。

这不是一份只介绍命令的操作手册。它还回答以下工程问题：

1. 为什么原始 Excel 和 CSV 不能直接交给 Agent；
2. 五组数据为什么最终形成七个 JSONL 文件；
3. 如何在不加载整个工作簿的情况下处理 64 万行 Excel；
4. 为什么网页可以打开，却仍然可能没有公告正文；
5. HTML、PDF、DOC 和 DOCX 如何使用统一流程处理；
6. 下载失败、无文本层和真正不可用如何区分；
7. 哪些数据可以进入正文知识库，哪些数据只能保留标题级索引；
8. 如何证明最终产物没有缺行、乱码、空文件和误收录。

本文与 [数据与工具总览](01-数据与工具总览.md)、[公告索引设计](04-公告索引设计.md) 共同构成数据层设计依据。其中，前两份文档定义数据的业务用途和语义边界，本文重点说明数据资产如何被实际构建出来。

---

## 2. 建设目标与原则

### 2.1 建设目标

数据集构建工作的最终目标不是简单地“把 Excel 改成 JSON”，而是形成三类可以被系统稳定使用的资产：

| 资产类型 | 主要用途 | 典型消费者 |
|---|---|---|
| 结构化 JSONL | 精确查询、过滤、计算和后续入库 | 股权工具、财务工具、评测系统、事件工具 |
| 公告纯文本 | 全文检索、切片、向量化和证据引用 | `document_search`、本地知识库 |
| 质量报告与清单 | 审计、重试、问题定位和结果验收 | 数据工程人员、项目负责人 |

### 2.2 核心原则

整个流程遵循以下原则：

1. **原始数据只读**：不修改赛题目录中的 Excel、CSV 和数据字典。
2. **来源可追溯**：保留来源字段、原始链接、来源 ID 和处理状态。
3. **结构化事实与正文分离**：JSONL 与 `documents/` 平级，避免把索引和正文混为一体。
4. **类型转换必须确定**：日期、数值、空值和代码字段采用明确规则，不依赖模型猜测。
5. **下载成功不等于正文成功**：必须检查内容类型和可提取文本质量。
6. **失败可以重试，成功不重复下载**：支持断点续跑和定向修复。
7. **宁可明确排除，也不错误入库**：无有效正文的文件不能伪装成可检索文档。
8. **所有关键写入采用原子替换**：避免中断后产生半个 JSONL 或半个 TXT。

### 3.2 五组数据的角色

| 组别 | 数据内容 | 原始格式 | 系统角色 |

构建完成后的核心目录保持简单：

```text

├── announcement_timeout_retry_report.json
├── announcement_exclusions.csv
└── announcement_exclusion_report.json
```

这里有两个重要约定：

- `jsonl/` 保存结构化记录，一行对应一个完整 JSON 对象；
- `documents/` 只保存通过正文质量检查、允许进入知识库的纯文本。

这两个目录平级，使结构化查询和全文检索可以独立建设，也便于分别做版本管理、校验和重建。

## 5. 总体构建流程

整个流程可以概括为：

```text
原始 XLSX / CSV / 字典
          |
          v
结构检查与字段识别
          |
          v
流式解析与类型标准化
          |
          +----------------------+
          |                      |
          v                      v
     结构化 JSONL          公告链接队列
                                 |
                                 v
                         HTML 正文优先获取
                                 |
                    +------------+------------+
                    |                         |
                正文有效                  仅元数据/失败
                    |                         |
                    v                         v
                保存 TXT             附件 PDF/DOC/DOCX
                                              |
                                              v
                                        解析并保存 TXT
                                              |
                                   +----------+----------+
                                   |                     |
                                成功                  无文本层
                                   |                     |
                                   v                     v
                              允许入库              保留索引并排除正文
```

该流程由以下脚本实现：

| 脚本 | 职责 |
|---|---|
| `data_pipeline/competition/preprocess.py` | 主转换、公告下载、正文解析和一般修复 |
| `data_pipeline/competition/retry_announcement_timeouts.py` | 只重试网络超时记录 |
| `data_pipeline/competition/convert_legacy_doc.ps1` | 使用本机 Microsoft Word 提取旧版 DOC 文本 |
| `data_pipeline/competition/finalize_announcement_exclusions.py` | 最终排除无文本层公告并清理壳 TXT |

## 6. Excel 与 CSV 的解析设计

### 6.1 为什么没有直接依赖 `openpyxl`

股东工作簿包含 646,449 条记录，文件解压后的工作表 XML 规模远大于压缩包本身。如果使用普通模式一次性加载整个工作簿，会产生不必要的内存压力。

主脚本直接利用 XLSX 的开放格式特性：XLSX 本质上是一个 ZIP 包，单元格和共享字符串分别保存在 XML 文件中。处理流程为：

1. 打开 XLSX 压缩包；
2. 解析 `xl/sharedStrings.xml`，建立共享字符串表；
3. 使用 XML `iterparse` 流式读取 `sheet1.xml`；
4. 每完成一行即转换并写入，不长期保留历史行；
5. 根据单元格引用恢复稀疏列的位置。

这种方式的优势是：

- 不需要额外安装 `openpyxl`；
- 内存占用主要取决于共享字符串和当前行，而不是总行数；
- 可以稳定处理几十万行工作簿；
- 不会受到 Excel 临时文件 `~$clean.xlsx` 干扰。

### 6.2 CSV 解析

三张财务表和研报数据采用 Python 标准库 `csv.DictReader` 流式读取。实际文件编码验证为 UTF-8，读取时使用 `utf-8-sig`，同时兼容可能存在的 BOM。

CSV 每次只保留当前记录，因此即使研报文件约 174 MB，也不需要整体载入内存。

### 6.3 JSONL 作为中间标准格式

JSONL 的每一行都是独立 JSON 对象，例如：

```json
{"s_info_windcode":"300838.SZ","ann_dt":"2024-01-02","s_holder_name":"王秀国","s_holder_quantity":10892000,"s_holder_pct":7.99}
```

选择 JSONL 的原因包括：

- 可以流式写入和流式读取；
- 单行损坏不会破坏整个文件结构；
- 保留对象、数组、数字、布尔值和 `null` 等类型；
- 便于后续导入 SQLite、Elasticsearch、数据湖或训练流水线；
- 适合逐条抽样、审计和并行处理。

所有 JSONL 使用 UTF-8 编码并直接保留中文，不把中文转成 `\uXXXX`。

## 7. 字段与类型标准化

### 7.1 空值

原始数据中的空字符串和空单元格统一转换为 JSON `null`：

```text
"" / 空单元格 -> null
```

这样可以区分“没有数据”和数值 `0`，也避免下游把空字符串误当作有效值。

### 7.2 日期

源数据中同时存在以下日期形式：

```text
20240102
2025-03-31
46168
```

其中 `46168` 是 Excel 日期序列值。脚本将可识别日期统一为 ISO 8601：

```text
20240102 -> 2024-01-02
46168    -> 2026-05-26
```

统一日期后，排序、区间过滤、时间线构建和数据库索引都更可靠。

### 7.3 数值

明确的数值字段转换为 JSON 数字：

```text
"10892000" -> 10892000
"7.99"     -> 7.99
```

这使财务计算和持股比例计算不再依赖每次查询时临时解析字符串。

### 7.4 标识符和代码

股票代码、公司 ID、报表类型代码、公告分类代码等字段始终保留为字符串。例如：

```text
000001.SZ
5507060000
408006000
```

代码看起来像数字，但不能参与算术运算。将其转换为整数可能丢失前导零，也会破坏与外部系统的连接键。

### 7.5 公告分类

公告字段 `n_info_fcode` 可能使用 `|` 包含多个分类。构建时：

1. 保留原始 `n_info_fcode`；
2. 拆分得到 `category_codes` 数组；
3. 根据数据字典补充 `category_names`。

示例：

```json
{
  "n_info_fcode": "5507060000|5506190000",
  "category_codes": ["5507060000", "5506190000"],
  "category_names": ["违纪违规", "个股其他公告"]
}
```

## 8. 各数据组的输出设计

### 8.1 多轮问题 `questions.jsonl`

核心字段：

```text
session_id
question
think_flag
```

该数据只用于评测回放和多轮上下文测试，不进入事实知识库。相同问题可以在同一会话中重复出现，不能擅自去重。

### 8.2 股东快照 `shareholders.jsonl`

核心信息包括证券代码、公告日、快照截止日、股东名称、持股数量、持股比例、股份性质和限售数量。

该表描述的是特定时点的主要股东快照。它可以支撑集中度和变化分析，但不能单独证明最终受益人、协议控制或完整股权链。

### 8.3 公告索引 `announcements.jsonl`

公告记录在保留 11 个原始字段的基础上，增加：

```text
category_codes
category_names
source_urls
selected_url
selected_format
document_path
download_status
repair_status
index_document
download_error
```

其中：

- `source_urls.html` 保存 HTML 来源；
- `source_urls.pdf` 沿用原始字段名语义，实际附件可能是 PDF、DOC 或 DOCX；
- `selected_format` 记录最终实际使用的格式；
- `index_document` 明确正文是否允许进入知识库；
- `document_path` 只指向已通过质量检查的 TXT。

### 8.4 财务报表 JSONL

三张表分别输出：

```text
balance_sheets.jsonl
income_statements.jsonl
cashflows.jsonl
```

保留宽表结构的原因是来源字段已经具有稳定、明确的财务语义。此阶段只做无损标准化，不提前把所有指标转成长表，避免在尚未确定查询模式前引入大量重复行。

后续导入 SQLite 时，可以在宽表基础上建立常用指标索引或生成派生长表。

### 8.5 研报 `research_reports.jsonl`

研报数据包含机构、作者、标题、发布日期、证券代码、评级、目标价、行业分类和摘要。当前来源没有研报全文链接，因此以摘要作为可检索文本证据，并明确其证据类型是“机构观点”，不能替代公司公告或财务报表事实。

## 9. 公告正文获取策略

公告数据是整个构建流程中最复杂的部分，因为一条记录通常同时提供 HTML 页面和附件链接。

### 9.1 来源选择顺序

最终策略为：

1. 优先请求 HTML；
2. HTML 有实质正文时，直接提取并保存 TXT；
3. HTML 只有标题、日期和附件信息时，判定为 `metadata_only`；
4. HTML 失败或只有元数据时，请求附件；
5. 根据附件真实格式选择解析器；
6. 只有提取到有效正文后才写入最终 TXT。

选择 HTML 优先，是因为 HTML 通常体积更小、解析更快，也无需保存二进制中间文件。但“页面能打开”并不代表“页面包含正文”。

### 9.2 HTML 壳页面识别

实际数据中存在大量 HTML 页面只包含：

```text
公告标题
公告日期
附件名称.pdf
```

这类页面如果仅根据 HTTP 200 或总字符数判断，会被错误标记为正文成功。

最终判定规则综合使用：

- 清洗后文本长度小于 300 字符；
- 非空行数不超过 8 行；
- 页面包含 `.pdf`、`.doc`、`.docx` 或 `.rtf` 附件标识。

满足条件时标记为 `html_metadata_only`，并自动回退到附件。

这条规则比单纯使用“正文超过 80 字”更可靠，因为标题、日期和附件名本身就可能超过 80 字。

### 9.3 内容格式不能只看 URL

原始字段名叫 `n_info_annlink`，但链接不一定是 PDF。处理器优先检查文件头，再参考响应类型和 URL 扩展名：

| 文件特征 | 识别格式 |
|---|---|
| `%PDF` | PDF |
| `D0 CF 11 E0 A1 B1 1A E1` | 旧版 DOC/OLE |
| `PK 03 04` | DOCX/ZIP 容器 |
| `<html`、`<!DOCTYPE` 或 HTML Content-Type | HTML |

这种“内容优先”策略可以避免把错误页面交给 PDF 解析器，也解决了扩展名与真实文件类型不一致的问题。

### 9.4 各格式的文本提取

| 格式 | 处理方式 |
|---|---|
| HTML | 标准库 `HTMLParser`，忽略脚本、样式和不可见节点 |
| PDF | PyMuPDF 按页提取文本 |
| DOCX | `python-docx` 提取段落和表格 |
| 旧版 DOC | 优先 LibreOffice；Windows 环境可调用 Microsoft Word COM |

所有格式最终都只保留 UTF-8 TXT。PDF、DOC 和 DOCX 二进制内容只在内存或临时目录中存在，解析完成后不进入最终数据目录。

### 9.5 正文文件命名

公告来源 `id` 在当前 7,311 条数据中无重复，因此正文采用：

```text
data/documents/announcements/{id}.txt
```

这样可以从 JSONL 的 `id` 稳定定位本地正文，也不会受到标题中的特殊字符和超长文件名影响。

## 10. 网络可靠性与断点修复

### 10.1 下载控制

下载器具备以下保护：

- 连接和读取超时；
- 单文档墙钟总时限；
- 指数退避重试；
- 并发数限制；
- 单文档 50 MiB 上限；
- HTTP 状态检查；
- 成功文件跳过；
- 失败原因结构化记录。

墙钟总时限尤其重要。普通 HTTP 读取超时只表示“连续多久没有收到新字节”；如果服务端持续以极慢速度发送数据，任务仍可能长时间不结束。总时限为整个文件下载设置明确上界。

### 10.2 原子写入

正文先写入同目录临时文件：

```text
{id}.txt.tmp
```

只有下载、解析和质量检查全部成功后，才使用原子替换生成 `{id}.txt`。因此失败任务不会覆盖已有的有效正文。

JSONL 也采用相同策略：先完整写入 `.tmp`，再替换正式文件。定向修复过程中每完成 10 条即保存一个断点，长任务被中断后不需要从头开始。

### 10.3 分层重试

实践中采用两层重试：

1. 主流程以适中并发完成绝大多数链接；
2. `retry_announcement_timeouts.py` 只选择 `content_unavailable` 且错误包含超时的记录，在更稳定的网络环境下使用低并发和较长时限重试。

独立超时重试脚本不会触碰：

- 已经成功的公告；
- 解析失败但不是网络问题的公告；
- 已确认无文本层、需要 OCR 的公告。

换网络前可以先执行：

```powershell
F:\conda_envs\FinTrace\python.exe -m data_pipeline.competition.retry_announcement_timeouts --dry-run
```

它只统计符合条件的记录，不会发起网络请求。

## 11. 数据质量检查与问题闭环

### 11.1 检查维度

构建过程不是以“脚本退出码为 0”作为唯一成功标准，而是进行以下检查：

| 检查项 | 验收方法 |
|---|---|
| 记录完整性 | JSONL 行数与源文件有效记录数一致 |
| JSON 合法性 | 每行可以独立反序列化 |
| 主键质量 | 公告 7,311 个 `id` 无重复 |
| 类型质量 | 日期为 ISO 格式，数值为 JSON 数字，代码为字符串 |
| 文件一致性 | 每条正文成功记录都有对应非空 TXT |
| 内容质量 | 成功 TXT 不能仍是附件壳页面 |
| 编码质量 | UTF-8 读取无替换字符 `�` |
| 路径质量 | `document_path` 与真实文件一一对应 |
| 排除质量 | 不可用记录必须 `index_document=false` |
| 入库安全 | `documents/` 中不能残留被排除的壳 TXT |

### 11.2 初始下载结果

首次完整构建得到：

```text
公告总数：7311
初始成功：7307
初始失败：4
```

进一步抽查发现，初始成功中存在 HTML 只有附件信息、没有正文的情况。这说明 HTTP 成功率不能直接作为正文成功率。

### 11.3 定向修复

定向修复完成了以下工作：

- 将 HTML 壳页面回退到附件；
- 重试最初 4 条完全失败记录；
- 识别并解析 PDF、DOC 和 DOCX；
- 使用 Word 成功处理旧版 DOC；
- 对网络超时记录在新网络环境下单独重试。

最初 4 条完全失败记录最终全部修复：3 条通过 HTML 重试恢复，1 条旧版 DOC 通过 Word 提取正文。

### 11.4 无文本层附件

网络问题解决后，剩余 33 条附件可以下载，但 PDF 没有足够的可提取文本层。这类文件通常是扫描件、图片型 PDF 或正文文本编码异常。

本项目没有为了追求表面上的 100% 成功率而把空文本或附件元数据写入知识库。最终采用：

```json
{
  "download_status": "excluded_no_text_layer",
  "repair_status": "excluded",
  "index_document": false,
  "document_path": null,
  "excluded_reason": "attachment_has_no_extractable_text_layer"
}
```

同时执行以下操作：

1. 保留证券代码、公告日期、标题、分类和原始链接；
2. 删除对应的 33 个壳 TXT；
3. 写入 `announcement_exclusions.csv`；
4. 防止知识库构建器递归扫描时误收录这些文件。

这里删除 TXT 是必要的。现有知识库构建器会递归扫描指定目录下所有受支持文件，并不会读取公告 JSONL 中的 `index_document`。如果只改状态、不清理文件，壳文本仍可能进入检索库。

## 13. 状态模型与数据血缘

### 13.1 公告处理状态

公告记录的主要状态流转如下：

```text
not_requested
   |
   v
success -------------------------------> 可入库
   ^
   |
failed / content_unavailable
   |
   +--> 网络重试成功 -------------------> success
   |
   +--> 附件解析成功 -------------------> success
   |
   +--> 确认无文本层 -------------------> excluded_no_text_layer
```

### 13.2 来源字段

每条公告保留：

- 原始 `object_id` 和 `id`；
- 证券代码和来源侧公司 ID；
- 公告日期和收录日期；
- 原始分类代码；
- HTML 与附件 URL；
- 最终选择的 URL 和实际格式；
- 下载、修复、排除状态及时间；
- 本地正文路径或排除原因。

因此，从任何一个 TXT 都可以回溯到公告索引和原始链接；从任何一个公告索引也可以判断它是否具备正文证据。

## 16. 与知识库构建的衔接

公告正文已经统一为 UTF-8 TXT，文本格式本身可以被现有文档摄取模块解析。但是，当前公告文件采用 `{id}.txt` 命名，而 `knowledge_base.document_ingestion.build_kb` 目前主要从文件名和目录推断公司、日期与文档类型，两者还需要一层元数据适配。

如果现在直接执行以下命令：

```powershell
F:\conda_envs\FinTrace\python.exe -m knowledge_base.document_ingestion.build_kb `
  --raw-dir data\documents `
  --kb-dir data\knowledge_base `
  --skip-unchanged
```

正文能够被切片，但公告文件会被错误地赋予类似以下默认元数据：

```text
company_id = DOCUMENTS
published_date = 1970-01-01
document_type = announcements
title = 公告 id
```

因此，上述命令只能用于验证文本解析和切片，不能作为正式知识库构建命令。

正式接入推荐扩展知识库构建器，使其读取 `announcements.jsonl` 作为元数据清单，通过 `document_path` 关联正文，并使用：

```text
s_info_windcode -> company_id
ann_dt          -> published_date
n_info_title    -> title
固定值          -> document_type = announcement
id/object_id    -> source document id
```

适配后的知识库构建过程应：

1. 递归发现 TXT；
2. 通过相对路径关联公告 JSONL；
3. 从结构化记录读取公司、日期、标题和来源链接；
4. 切分为可检索 Chunk；
5. 写入 SQLite；
6. 可选构建 FAISS 向量索引。

结构化 JSONL 不应被当作普通全文文档切片，但应作为正文元数据和结构化事实来源。其余股东、财务和研报记录应通过后续数据导入步骤进入 SQLite 结构化表，由确定性工具查询和计算。

也可以在入库前生成符合现有解析规则的暂存文件名，例如 `{company_id}_{published_date}_announcement-{id}.txt`。但这种方式把业务元数据编码进文件名，长期可维护性不如显式清单关联，因此只建议作为临时兼容方案。

## 17. 已知边界与后续演进

### 17.1 当前边界

1. 33 条扫描型或无文本层公告没有正文文本；
2. 公告标题和分类是候选事实，不能替代正文确认；
3. 股东快照不是完整工商股权图；
4. 研报摘要是机构观点，不是公司事实披露；
5. 三张财务表完成了结构化标准化，但尚未在本流程中生成风险标签；
6. 当前文档目录主要包含公告正文，不等于完整企业文档库。

### 17.2 可选 OCR 扩展

如果未来确实需要补齐 33 条公告，可以增加 OCR 阶段：

```text
无文本层 PDF
  -> 页面渲染为图像
  -> 中文 OCR
  -> 版面顺序恢复
  -> 文本质量检查
  -> 人工抽样
  -> 恢复 index_document=true
```

OCR 不应只追求“识别出字符”。金融公告中证券代码、金额、日期、责任人和法规条款对准确性要求较高，因此必须增加数字混淆检查和人工抽样。

### 17.3 版本化建议

后续数据更新建议记录：

- 数据源版本和文件哈希；
- 脚本 Git 提交号；
- 构建开始与结束时间；
- 每个输出文件的行数和哈希；
- 下载成功率和格式分布；
- 排除记录及原因；
- 知识库文档数和 Chunk 数。

这样可以回答“某个答案使用的是哪一版数据”，也便于在规则、解析器或 OCR 能力升级后做差异重建。

## 18. 结论

FinTrace 数据集构建最终完成了从异构赛题文件到标准化数据资产的转换：

- 五组原始数据被拆分为七个职责清晰的 JSONL；
- 827,598 条结构化记录完成类型统一；
- 7,278 份公告正文通过 HTML、PDF、DOC 或 DOCX 路径提取为 UTF-8 TXT；
- 网络超时通过定向脚本和更换网络环境全部消除；
- 33 条无文本层公告被明确排除正文，但完整保留标题级索引和来源链接；
- 最终正文目录与可入库状态严格一一对应。

这套流程的价值不只在于“数据已经转完”，更在于每条记录都能说明它来自哪里、经历了什么处理、是否具备正文证据，以及为什么可以或不可以进入知识库。对于金融 Agent，这种可追溯性和保守的数据质量边界，比表面上的 100% 文档覆盖率更重要。
