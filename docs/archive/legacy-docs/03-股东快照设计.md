# FinTrace 十大股东快照数据设计与 Agent 应用方案

## 1. 文档目的

本文档说明比赛数据中“十大股东”数据的内容、质量、能力边界和工程接入方案，用于指导 FinTrace 将原始 Excel 数据转换为可查询、可穿透、可追溯的股权证据。

本数据首先是一组带披露日期的历史持股快照，其次才可以投影为股权图。系统不得将其描述为完整工商股权图谱，也不得仅凭第一大股东或最高持股比例直接认定实际控制人。

### 1.1 对应竞赛任务与指标

本文档对应任务 2 中的结构化股权底座和 `ownership_penetration` 工具。它可以支撑主要股东查询、时序持股边、部分上市公司多跳路径和比例计算，但不能单独满足“深度大于 3 的隐性控制链端到端准确率不低于 85%”。

为达到完整竞赛目标，还需补充：

- 招股说明书、年报中的发行前股权、子公司和实际控制人关系；
- 控制权变更、一致行动、表决权委托等公告正文；
- 合法可用的企业或工商关系数据；
- LLM 抽取后经过实体消歧和证据校验的 `CONTROLS`、`LEGAL_REPRESENTATIVE`、`RELATED_PARTY` 等关系；
- 深度大于 3 的人工复核路径测试集。

端到端路径只有在每一跳实体、方向、关系类型、比例、查询时点和证据均正确时才算成功。图查询和结果组装还需在固定硬件、预热数据库条件下验证不超过 5 秒。

## 2. 数据位置与规模

原始文件：

```text
14-知识图谱与智能推荐赛道-东吴证券-基于 Agentic AI 的金融长上下文推理、图谱穿透与财报反欺诈智能问答算法探索/2/clean.xlsx
```

工作表名称为“十大股东”，共有 16 个字段。

| 指标 | 统计结果 |
|---|---:|
| 总记录数 | 646,449 |
| 覆盖证券数 | 6,161 |
| 不同股东名称数 | 71,328 |
| 公司与截止日期组合数 | 72,802 |
| 每只证券快照数中位数 | 11 |
| 单只证券最多快照数 | 30 |
| 股东截止日期范围 | 2020-11-03 至 2026-06-02 |
| 公告日期范围 | 2024-01-02 至 2026-05-26 |
| 个人股东记录数 | 280,856 |
| 企业股东记录数 | 365,593 |

一条记录的业务含义是：某个股东在某个持股截止日期持有某只证券一定数量、一定比例和一定性质的股份，该信息在某个公告日期披露。

## 3. 字段解释

| 原始字段 | 含义 | 系统用途 |
|---|---|---|
| `s_info_windcode` | 被持股证券的 Wind 代码 | 目标上市公司 ID，例如 `600519.SH` |
| `ann_dt` | 公告日期 | 判断信息从何时开始对外公开，防止历史查询使用未来信息 |
| `s_holder_enddate` | 股东持股截止日期 | 确定持股快照所属时点 |
| `s_holder_holdercategory` | 股东类别，`1` 为个人、`2` 为企业 | 映射为 `PERSON`、`COMPANY` 等实体类型 |
| `s_holder_name` | 股东名称 | 实体展示名称和名称检索 |
| `s_holder_quantity` | 持股数量，单位为股 | 回答持股数量及跨期变化问题 |
| `s_holder_pct` | 持股比例，原始单位为百分数 | 转换为图边权重和集中度指标 |
| `s_holder_sharecategory` | 股份性质代码 | 区分流通股、限售股、H 股等 |
| `s_holder_restrictedquantity` | 持有限售股份数量 | 分析限售结构和潜在解禁影响 |
| `s_holder_aname` | 股东名称补充字段 | 用于名称校验，不应无条件覆盖主名称 |
| `s_holder_sequence` | 关联方序号 | 字段大量缺失且存在组合值，不直接作为股东排名 |
| `s_holder_sharecategoryname` | 股份性质名称 | 面向用户展示股份性质 |
| `s_holder_memo` | 股东说明，数据字典标记为废弃 | 可作为补充事件线索，不作为核心事实来源 |
| `s_info_compcode` | 股东主体代码 | 构造稳定实体 ID，并与上市公司主体建立映射 |
| `report_period` | 报告期 | 辅助判断定期报告快照和比较口径 |
| `s_holder_nat` | 股东性质 | 可用于细分机构、法人或个人属性，但存在缺失 |

`s_holder_pct` 在原始数据中以百分数存储。例如 `7.99` 表示 `7.99%`，转换为内部比例时为 `0.0799`。原始值和标准化值都应保留，避免重复换算。

## 4. 快照结构分析

### 4.1 快照不能简单理解为固定十条

按“证券代码 + 持股截止日期”分组：

| 快照记录数 | 快照数量 |
|---|---:|
| 恰好 10 条 | 59,554 |
| 少于 10 条 | 12,231 |
| 多于 10 条 | 1,017 |
| 最大记录数 | 134 |

加入公告日期后，仍有 1,013 个组合超过十条。部分超过十条的记录集中在特定证券和上市前后时点，样本更接近完整股东名册或特殊披露，而非标准定期报告前十大股东。

因此，导入时不得无条件截断为十条。每个快照应增加范围标签：

| `snapshot_scope` | 含义 |
|---|---|
| `top_ten` | 数据形态与标准十大股东快照一致 |
| `partial` | 快照少于十条，可能是不完整披露或特殊场景 |
| `extended_roster` | 快照超过十条，可能是完整股东名册或上市前数据 |
| `unknown` | 无法依据当前字段确认数据范围 |

该标签属于数据质量描述，不代表已经确认原始业务口径。

### 4.2 不使用 `s_holder_sequence` 直接排名

`s_holder_sequence` 约有 48.4 万条为空，其余记录还包含 `12`、`123` 等组合值。需要展示股东排名时，应在同一有效快照内按持股比例降序计算，并输出：

```text
rank_source = calculated_by_holding_ratio
```

计算排名不能覆盖原始字段，也不能在持股比例相同时武断确定唯一先后顺序。

### 4.3 时间字段必须同时保留

系统需要区分：

- `holder_end_date`：持股关系对应的业务时点；
- `announcement_date`：该关系开始公开可知的日期；
- `report_period`：定期报告口径。

历史查询不能只看持股截止日期。例如回答“2025 年 3 月 1 日当时已知的主要股东”时，只能使用 `announcement_date <= 2025-03-01` 的记录，防止使用后来披露的信息造成前视偏差。

## 5. 数据质量与处理规则

### 5.1 已发现的数据质量情况

| 项目 | 结果 |
|---|---:|
| 持股比例小于 0 或大于 100 的记录 | 0 |
| 持股比例为 0 的记录 | 0 |
| 持股数量缺失率 | 约 0.01% |
| 同一快照内股东名称重复组合 | 约 70 组 |
| 持股比例合计超过 100% 的快照 | 142 |
| 公告日期早于持股截止日期的记录 | 4,854 |
| `s_holder_memo` 有值比例 | 约 3.45% |
| `report_period` 缺失率 | 约 11.89% |
| `s_holder_nat` 缺失率 | 约 15.50% |
| `s_info_compcode` 全表缺失率 | 约 23.98% |

`s_info_compcode` 的全表缺失主要来自部分个人股东。企业股东记录中的该字段具有较高可用性。

### 5.2 质量标志

导入时建议为每条记录或每个快照生成以下 `quality_flags`：

```text
missing_holder_id
missing_quantity
missing_report_period
duplicate_holder_in_snapshot
snapshot_less_than_ten
snapshot_more_than_ten
snapshot_ratio_sum_over_100
announcement_before_holder_end
ambiguous_holder_identity
```

质量异常不应默认导致整批导入失败。系统应保留原始记录，将异常标志传递给工具，并根据问题类型决定是否允许使用。

### 5.3 重复记录处理

不能仅凭股东名称去重。建议业务唯一性检查至少包含：

```text
target_company_id
holder_end_date
announcement_date
holder_entity_id
share_category_code
holding_quantity
holding_ratio
```

完全相同的重复记录可以标记并在查询层折叠；股份性质、数量或比例不同的记录应保留并进入人工或规则复核。

## 6. 主体标识与实体消歧

### 6.1 上市公司实体

被持股公司使用规范证券代码作为实体 ID：

```text
LISTED:600519.SH
```

同时建立证券代码、证券名称和公司主体代码的映射表。

### 6.2 企业股东实体

企业股东优先使用 `s_info_compcode`：

```text
COMPANY:<s_info_compcode>
```

若该主体代码能够映射回某只上市公司，则实体同时保存对应 Wind 代码。该连接允许系统把“上市公司作为另一家公司的股东”继续向上穿透。

现有数据交叉检查结果：

- 604 个企业股东主体代码可以映射为上市公司；
- 对应 12,761 条持股记录；
- 约占企业股东记录的 3.49%。

这些记录可以形成有真实数据依据的上市公司间多跳持股路径。

### 6.3 个人股东实体

个人股东有稳定主体代码时优先使用该代码。缺少主体代码时，不得仅凭姓名在全市场合并同名个人。

建议生成限定作用域的临时实体 ID：

```text
PERSON_UNRESOLVED:<name_hash>:<target_company_id>
```

并标记：

```text
identity_quality = unresolved
```

这类实体可用于展示当前公司股东，但不应用于跨公司穿透或断言同名股东为同一人。

## 7. 本数据可以实现的功能

### 7.1 主要股东快照查询

支持问题：

- 某公司最新披露的主要股东有哪些？
- 某股东持有某公司多少股份？
- 某公司 2024 年末的第一大股东是谁？
- 某股东持有的是流通股还是限售股？

输出应包含截止日期、公告日期、持股数量、持股比例、股份性质和证据 ID。

### 7.2 跨期持股变化

支持比较同一股东在两个有效快照中的：

- 持股数量变化；
- 持股比例变化；
- 股东排名变化；
- 新进入或退出主要股东名单；
- 限售股份变化。

“退出前十大股东”不等于“已经清仓”。系统只能说明该股东未出现在后续主要股东快照中。

### 7.3 股权集中度分析

可以计算：

- 第一大股东持股比例；
- 前三大、前五大、前十大股东持股比例合计；
- 企业股东和个人股东占比；
- 股权集中度的跨期变化。

对于 `partial`、`extended_roster` 或比例和异常的快照，应附带质量警告，不应直接与标准十大股东快照横向比较。

### 7.4 有限多层持股穿透

当企业股东能够映射为上市公司时，可以继续查询该企业自身的主要股东，从而形成：

```text
股东 A -> 上市公司 B -> 上市公司 C
```

间接持股比例可以在每一跳均为普通持股关系且比例有效时计算：

```text
indirect_ratio = ratio_1 * ratio_2 * ... * ratio_n
```

该结果只能称为“基于主要股东披露数据发现的持股路径”，不能称为完整最终受益所有人路径。

### 7.5 股权异常和风险信号

可构造审慎的风险信号：

- 第一大股东持股比例显著下降；
- 主要股东频繁进入或退出；
- 股权集中度短期明显变化；
- 机构股东持股比例明显下降；
- 限售股份结构显著变化；
- 同一企业股东连接多家风险公司。

这些只能作为线索，必须结合减持公告、质押公告、控制权变更公告和其他文件进一步验证。

### 7.6 与其他工具联合分析

| 联合工具 | 可实现目标 |
|---|---|
| `event_timeline` | 将主要股东变化与增减持、质押、处罚或控制权变更公告对齐 |
| `financial_risk_analysis` | 检查股权结构变化是否与财务风险信号同期出现 |
| `document_search` | 检索公告和研报，对股东变化原因进行证据补充 |
| `ownership_penetration` | 查询主要股东路径、间接持股比例和有限多跳关系 |

## 8. 本数据不能单独支持的结论

当前数据不包含完整工商登记、全部非上市企业股权、子公司关系、表决权协议和一致行动协议，因此不能单独支持：

- 完整工商股权图谱；
- 全部直接和间接股东；
- 最终受益所有人识别；
- 一致行动关系；
- 表决权委托和协议控制；
- 实际控制人确定结论；
- 完整控制链；
- 股东退出主要股东名单后已经清仓的结论。

第一大股东不一定是控股股东，最高持股比例也不等于实际控制。由本数据生成的原始关系应统一标记为 `OWNS`，不得直接标记为 `CONTROLS`。

工具输出必须包含类似限制说明：

> 本结果仅基于主要股东披露数据，可能遗漏非主要股东、非上市企业、协议控制及一致行动关系，不构成完整股权或实际控制人认定。

## 9. 结构化存储设计

原始 Excel 保持只读，离线导入 SQLite。推荐建立以下表。

### 9.1 `ownership_entities`

```text
entity_id              主体稳定 ID
entity_name            主体名称
entity_type            PERSON、COMPANY、FUND、LISTED_COMPANY 等
windcode               可关联的证券代码
compcode               原始主体代码
identity_quality       resolved、scoped、unresolved
source_record_count    来源记录数
```

### 9.2 `shareholder_snapshots`

```text
snapshot_id
target_company_id
holder_end_date
announcement_date
report_period
snapshot_scope
record_count
holding_ratio_sum
quality_flags
```

### 9.3 `shareholder_snapshot_edges`

```text
edge_id
snapshot_id
shareholder_entity_id
target_company_id
holding_quantity
holding_ratio
holding_ratio_raw
share_category_code
share_category_name
restricted_quantity
calculated_rank
memo
quality_flags
evidence_id
```

### 9.4 推荐索引

```sql
CREATE INDEX idx_snapshot_target_dates
ON shareholder_snapshots(target_company_id, holder_end_date, announcement_date);

CREATE INDEX idx_edge_snapshot
ON shareholder_snapshot_edges(snapshot_id);

CREATE INDEX idx_edge_holder
ON shareholder_snapshot_edges(shareholder_entity_id);

CREATE INDEX idx_entity_compcode
ON ownership_entities(compcode);
```

在线 Agent 查询必须使用结构化索引，不应在每次问答时扫描 64 万行 Excel。

第一版可以使用 SQLite 时序边表配合 NetworkX 完成路径搜索；为贴合竞赛的动态图谱目标，应保持 `OwnershipRepository` 与存储实现解耦，并预留 Neo4j 实现。当补充控制、法人、关联方和事件关系后，可将已验证关系同步到 Neo4j，用于多类型模式匹配、动态图展示和大规模路径查询。无论使用哪种图库，关系证据和时点语义必须一致。

## 10. 有效快照选择规则

对于查询日期 `as_of_date`，推荐按以下顺序选择快照：

1. 过滤目标公司；
2. 要求 `announcement_date <= as_of_date`，确保当时已经公开；
3. 优先要求 `holder_end_date <= as_of_date`；
4. 排除或警告严重日期异常快照；
5. 选择 `holder_end_date` 最近的快照；
6. 同一截止日期有多次公告时，选择查询日期前最新公告版本；
7. 将快照范围和质量标志返回给 Agent。

若用户问“最新股东”，应解释最新是“当前数据源中最近已披露的持股截止日”，而不是实时股东名册。

多跳查询时，每一跳都必须以同一个 `as_of_date` 独立选择该目标公司的有效快照，不能把不同未来时点的边随意拼接成一条路径。

## 11. 接入现有 Agent 的方式

### 11.1 离线数据流程

```text
原始 clean.xlsx
  -> 字段解析与类型转换
  -> 主体 ID 生成及上市公司映射
  -> 快照识别与质量校验
  -> SQLite 实体、快照和持股边
  -> 导入清单及质量报告
```

离线流程负责复杂清洗和索引，在线工具只负责参数校验、快照选择和图查询。

### 11.2 Planner 参数

现有 `ownership_penetration` 建议逐步支持：

```json
{
  "company_id": "600519.SH",
  "as_of_date": "2025-12-31",
  "query_mode": "snapshot",
  "source_entity_id": null,
  "max_depth": 3,
  "max_paths": 50,
  "relation_types": ["OWNS"]
}
```

`query_mode` 可以包括：

| 模式 | 用途 |
|---|---|
| `snapshot` | 查询目标公司的主要股东快照 |
| `change` | 比较两个时点的持股变化 |
| `concentration` | 计算主要股东集中度 |
| `paths` | 查询有限多跳持股路径 |

如果用户没有明确日期，Planner 可以传入 `latest_available` 或省略日期，由工具选择最新已披露快照，并在结果中返回实际使用日期。

### 11.3 LangGraph 执行流程

```text
用户问题
  -> route：识别股东、持股、穿透或集中度意图
  -> validate_plan：校验公司、日期、模式和深度
  -> execute_tools：调用 ownership_penetration
  -> 工具选择有效快照并查询持股边
  -> validate_tool_results：检查快照、路径和质量标志
  -> check_evidence：确认每条持股关系有证据
  -> generate_answer：仅根据工具结果生成回答
```

对于“谁是实际控制人”之类超出数据能力的问题，工具可以返回主要股东路径，同时标记 `partially_answered` 或 `insufficient_evidence`。回答模型必须说明不能仅凭本数据确认实际控制人。

### 11.4 工具输出建议

```json
{
  "company_id": "600519.SH",
  "query_mode": "snapshot",
  "as_of_date": "2025-12-31",
  "snapshot": {
    "holder_end_date": "2025-09-30",
    "announcement_date": "2025-10-30",
    "snapshot_scope": "top_ten",
    "quality_flags": []
  },
  "holders": [
    {
      "entity_id": "COMPANY:...",
      "name": "某股东",
      "holding_quantity": 1000000,
      "holding_ratio": 0.0799,
      "calculated_rank": 1,
      "share_category": "A股流通股",
      "evidence_id": "EVID-OWN-..."
    }
  ],
  "paths": [],
  "limitations": [],
  "warnings": []
}
```

### 11.5 证据设计

每条持股边生成稳定证据 ID，例如：

```text
EVID-OWN-<target>-<holder_end_date>-<holder_entity_hash>-<record_hash>
```

证据事实至少包含：

```json
{
  "shareholder_name": "某股东",
  "target_company_id": "600519.SH",
  "holding_quantity": 1000000,
  "holding_ratio": 0.0799,
  "holder_end_date": "2025-09-30",
  "announcement_date": "2025-10-30",
  "share_category": "A股流通股"
}
```

证据来源应指向原始 Excel、工作表和稳定行标识。由于 Excel 没有文档页码，不应伪造页码。

### 11.6 回答生成约束

回答模型必须：

- 明确实际使用的持股截止日期和公告日期；
- 区分原始持股比例和计算得到的间接比例；
- 说明结果是主要股东范围内的有限穿透；
- 对异常快照显示质量警告；
- 不把未进入主要股东名单解释为清仓；
- 不把第一大股东直接解释为实际控制人；
- 不使用查询日期之后才公告的数据。

## 12. 与当前代码的适配关系

现有 `tools/ownership_graph` 已具备：

- 实体和关系 Schema；
- CSV 数据源接口；
- 有深度和路径数量限制的图搜索；
- 间接持股比例计算；
- 关系证据生成；
- 数据缺失和校验失败的结构化错误。

但比赛数据接入仍需补充：

1. Excel 到 SQLite 的离线导入器；
2. 快照模型和有效快照选择器；
3. `compcode` 与上市公司代码映射；
4. 个人股东消歧策略；
5. `snapshot`、`change`、`concentration` 查询模式；
6. 从有效快照动态投影图边；
7. 日期一致性和快照范围质量标志；
8. 面向 Agent 的能力限制和警告字段。

不建议先把原始 Excel 强行转换成现有静态 `entities.csv` 和 `relations.csv` 后长期使用，因为这会丢失快照版本、披露日期和数据质量信息。CSV 可以保留为测试接口，正式比赛数据应由 SQLite 快照数据源提供。

---

## 13. 推荐实施顺序

1. 定义 SQLite 实体、快照、持股边和证券主表；
2. 实现 Excel 流式导入，原始目录保持只读；
3. 生成导入清单、字段统计和质量报告；
4. 实现主体 ID 和 `compcode` 映射；
5. 实现按查询日期选择最近已披露有效快照；
6. 实现主要股东列表和跨期变化查询；
7. 实现集中度计算；
8. 将可映射企业股东投影为有限多跳图；
9. 接入现有 `ownership_penetration`；
10. 添加单元测试、数据质量测试和端到端 Agent 测试。

第一版应先把“指定公司、指定时点的主要股东快照查询”做准确，再逐步加入跨期比较和多跳穿透。快照选择如果不可靠，后续图算法即使计算正确，业务结论仍可能错误。

---

## 14. 最终原则

该数据最适合构建“有时间约束、有披露依据、能力边界明确的主要股东知识图谱”。FinTrace 应利用它完成股东查询、跨期变化、集中度和有限穿透，同时保留原始快照语义。

系统的可信度不取决于能画出多少层路径，而取决于每一条边是否来自正确时点、是否可以追溯，以及是否对数据覆盖范围作出了准确说明。
