# FinTrace 违规公告索引数据设计与 Agent 应用方案

## 1. 文档目的

本文档定义比赛数据组 3“违规公告索引”的数据语义、质量边界、标准化存储方式，以及它在 `event_timeline` 和 `document_search` 中的应用方案。

该数据是公告索引，不是公告正文，也不是已经确认的处罚事实清单。系统可以依据它确认“某公司在某日发布了某标题、某分类的公告”，但在未取得正文前，不得推断处罚金额、违规行为、责任人、监管依据或整改结果。

### 1.1 对应竞赛任务与指标

本文档对应任务 2 的事件脉络和任务 3 的监管证据补充。公告索引可以先形成标题级时间线并作为 PDF 下载入口；公告正文解析后，才能进入事件抽取、事件簇聚合和财务风险查证。

当前数据不包含新闻舆情正文，因此不能仅凭本数据宣称完成“海量新闻舆情事件簇”。达到竞赛目标还需补充允许使用的新闻或公开文本，并建立人工标注事件集，评价：

- 核心事件节点 Recall 不低于 85%；
- 事件日期、主体、类型和证据正确；
- 同一事项的聚类归属合理；
- 时间线没有明显时序断裂；
- 系统不把时间先后自动表述为因果关系。

## 2. 数据位置与规模

原始文件：

```text
14-知识图谱与智能推荐赛道-东吴证券-基于 Agentic AI 的金融长上下文推理、图谱穿透与财报反欺诈智能问答算法探索/3/clean.xlsx
```

配套字典：

```text
14-知识图谱与智能推荐赛道-东吴证券-基于 Agentic AI 的金融长上下文推理、图谱穿透与财报反欺诈智能问答算法探索/3/ditct.txt
```

| 指标 | 统计结果 |
|---|---:|
| 有效记录数 | 7,311 |
| 覆盖证券数 | 2,585 |
| 公告日期范围 | 2023-05-26 至 2026-05-26 |
| `object_id` 重复数 | 0 |
| 公告 PDF 链接缺失数 | 0 |
| 标题文本重复行数 | 700 |

每条记录都包含分类代码 `5507060000`，对应“违纪违规”。其中 5,911 条只包含该分类，其余记录还同时带有风险提示、补充更正、股份增减持、借贷担保、函件等分类。

这说明数据集是围绕违纪违规筛选的候选公告集合，不代表每条公告都确认公司存在违规事实。

## 3. 字段解释

| 原始字段 | 含义 | 系统用途 |
|---|---|---|
| `object_id` | 公告唯一 ID | 首选稳定 `document_id` 和去重主键 |
| `s_info_windcode` | 证券代码 | 标准化 `company_id` |
| `n_info_stockid` | 证券 ID | 保留为来源侧辅助标识 |
| `n_info_companyid` | 公司 ID | 与证券主表交叉校验，不直接替代证券代码 |
| `ann_dt` | 公告日期 | 事件日期和文档发布日期 |
| `n_info_title` | 公告标题 | 标题级事实、检索字段和候选事件识别 |
| `n_info_fcode` | 一个或多个公告类型代码 | 保留全部原始分类并映射候选事件类型 |
| `n_info_annlink` | 公告 PDF 链接 | 后续正文下载入口 |
| `id` | 公告 ID | 来源系统辅助 ID |
| `collect_dt` | 收录日期 | 数据进入来源系统的时间，不等于公告日期 |
| `n_info_windlink` | Wind HTML 链接 | 辅助来源链接 |

Excel 内日期可能以序列值存储。导入时应转换为 ISO 日期，同时保留原始值用于审计。

## 4. 公告分类与事件语义

### 4.1 原始分类必须完整保留

`n_info_fcode` 可能包含以 `|` 分隔的多个代码。导入时应拆分到关联表，不应只保留第一个代码，也不应根据代码顺序推断主次。

本数据常见的附加分类包括：

| 分类代码 | 名称 | 可辅助识别的主题 |
|---|---|---|
| `5507060000` | 违纪违规 | 监管或违规候选公告 |
| `5506190000` | 个股其他公告 | 通用补充分类 |
| `5506040000` | 风险提示 | 风险提示候选事件 |
| `5507240000` | 借贷担保 | 担保相关候选事件 |
| `5507200000` | 股份增减持 | 股东增减持候选事件 |
| `5508000000` | 函件 | 交易所或监管函件候选事件 |
| `5507210000` | 资金投向 | 资金用途候选事件 |
| `5502010000` | 特别处理 | ST 等特别处理候选事件 |
| `5506160000` | 中介公告 | 中介机构相关公告 |
| `5506140000` | 停牌提示 | 停牌相关候选事件 |

分类只能用于召回和候选事件映射。事件是否真实发生、事件主体、金额和法律性质仍需正文证据。

### 4.2 标题极性不能忽略

标题中至少包含以下不同语义：

- “关于收到行政监管措施决定书的公告”；
- “关于整改情况的公告”；
- “关于最近五年不存在被处罚或采取监管措施的公告”；
- “关于立案调查进展的公告”；
- “关于自查情况的公告”。

统计中有 248 条标题包含“不存在”。因此，不能看到 `5507060000` 就生成“公司被处罚”事件。

建议保存标题级状态：

| `title_assertion` | 含义 |
|---|---|
| `positive_candidate` | 标题表明可能收到处罚、措施、警示或立案 |
| `negative_statement` | 标题明确表示不存在相关事项 |
| `remediation` | 整改、回复或落实措施 |
| `progress_update` | 立案、调查或处罚事项进展 |
| `neutral_index` | 仅凭标题无法判断 |

该字段可以由规则预标注，但正式事件事实仍以正文抽取为准。

## 5. 本数据可以实现的功能

### 5.1 公告索引查询

可以准确回答：

- 某公司在指定时间范围发布了哪些相关公告；
- 公告的日期、标题、分类和原始链接；
- 某公司是否存在标题匹配“处罚”“警示函”“整改”等关键词的公告；
- 某段时间内相关公告的数量和分布。

回答应明确使用“公告标题显示”“索引记录表明”，不能把标题候选描述成正文确认事实。

### 5.2 标题级事件时间线

`event_timeline` 可以基于公告索引构建标题级时间线：

```text
公告日期
  -> 公告标题
  -> 原始分类
  -> 标题级状态
  -> 公告链接
```

例如可以排列“收到监管措施—发布整改报告—后续进展公告”，但在正文缺失时只能说明标题之间的时间关系，不能宣称存在因果链。

### 5.3 公告正文下载入口

`n_info_annlink` 可以作为离线下载任务输入。正文下载成功后，PDF 进入文档知识库，由 `document_search` 支持：

- 违规事实；
- 处罚或监管措施类型；
- 涉及金额；
- 责任主体；
- 监管依据；
- 整改要求和整改结果；
- 公告原文引用。

### 5.4 与其他数据联合分析

| 联合数据或工具 | 可实现目标 |
|---|---|
| 十大股东快照 / `ownership_penetration` | 对齐处罚公告与主要股东变化 |
| 财务报表 / `financial_risk_analysis` | 对齐监管公告与同期财务风险信号 |
| 公告正文 / `document_search` | 为标题级事件补充事实细节 |
| 研报摘要 / `document_search` | 检查机构是否讨论相关事件及风险影响 |

## 6. 本数据不能单独支持的结论

仅凭公告索引不能确认：

- 公司确实实施了某项违规行为；
- 处罚金额和处罚对象；
- 违法违规发生日期；
- 公告标题涉及的全部责任人；
- 整改已经完成或有效；
- 多份公告之间存在确定因果关系；
- 公告内容对股价或财务结果产生了确定影响。

标题包含“处罚”也可能是在说明历史上不存在处罚；标题包含“整改”不代表整改已经完成。Agent 必须在没有正文时披露这一限制。

## 7. 标准化存储设计

### 7.1 `announcement_index`

```text
announcement_id          规范公告 ID，优先使用 object_id
company_id               标准证券代码
source_stock_id          原始证券 ID
source_company_id        原始公司 ID
announcement_date        公告日期
title                    公告标题
title_assertion          标题级候选状态
pdf_url                  公告 PDF 链接
html_url                 Wind HTML 链接
source_record_id         原始 id
collected_date           收录日期
content_status           index_only、downloaded、parsed、failed
quality_flags            质量标志
evidence_id              标题级证据 ID
```

### 7.2 `announcement_categories`

```text
announcement_id
category_code
category_name
```

### 7.3 `announcement_documents`

```text
announcement_id
document_id
local_path
file_hash
download_status
parse_status
downloaded_at
error_message
```

### 7.4 推荐索引

```sql
CREATE INDEX idx_announcement_company_date
ON announcement_index(company_id, announcement_date);

CREATE INDEX idx_announcement_title
ON announcement_index(title);

CREATE INDEX idx_announcement_category
ON announcement_categories(category_code, announcement_id);
```

标题全文检索可以使用 SQLite FTS5；正文语义检索由现有知识库和 FAISS 负责。

## 8. 数据质量与处理规则

### 8.1 去重

`object_id` 在当前数据中无重复，应作为首选主键。标题重复不能直接删除，因为不同公司、日期或公告 ID 可能合法使用相同标题。

### 8.2 链接处理

原始数据中 PDF 链接完整，但不代表链接长期可访问。离线下载流程应：

1. 保留原始 URL；
2. 设置超时、限速和重试上限；
3. 校验响应类型和 PDF 文件头；
4. 计算文件哈希；
5. 记录下载状态和失败原因；
6. 支持断点续跑和跳过未变化文件；
7. 不在在线问答请求中临时批量下载。

在下载前还需确认比赛规则和数据授权允许保存、解析这些远程文件。

### 8.3 质量标志

建议包含：

```text
missing_company_id
invalid_announcement_date
unknown_category_code
duplicate_title
negative_title_statement
remote_document_unavailable
document_parse_failed
index_only_no_full_text
```

## 9. 接入 `event_timeline`

### 9.1 查询参数

```json
{
  "company_id": "600000.SH",
  "event_types": ["regulatory_action"],
  "start_date": "2024-01-01",
  "end_date": "2025-12-31",
  "include_negative_statements": false,
  "content_level": "index"
}
```

`content_level`：

| 值 | 含义 |
|---|---|
| `index` | 只使用标题、分类、日期和链接 |
| `full_text` | 只返回已经解析正文的事件 |
| `best_available` | 优先正文，没有正文时返回标题级结果并警告 |

### 9.2 事件类型扩展

现有 `EventType` 只覆盖少数事件，不能完整承载原始分类。建议区分：

- `raw_category_codes`：完整保留原始代码；
- `normalized_event_type`：工具可理解的统一类型；
- `assertion_status`：候选、否定陈述、已由正文确认；
- `content_level`：索引级或正文级。

第一版至少增加或统一支持：

```text
regulatory_action
risk_warning
shareholding_change
guarantee
special_treatment
correction
regulatory_letter
other_announcement
```

现有 `regulatory_inquiry`、`major_litigation` 等类型可以保留，但不能把所有 `5507060000` 都强制映射为其中一种。

### 9.3 聚类约束

现有“同公司、同类型、30 天、实体重合”只能作为轻量聚类。公告索引通常没有可靠实体列表，第一版可采用：

```text
同一 company_id
相同或兼容的 normalized_event_type
时间间隔不超过配置窗口
标题关键词或正文实体达到相似阈值
```

聚类结果表示“可能属于同一事项”，不得自动表述为确定因果链。

## 10. 接入 `document_search`

公告 PDF 下载并解析后：

```text
document_type = announcement
document_id = announcement_id
company_id = s_info_windcode
published_date = announcement_date
title = n_info_title
source_file = 本地 PDF 路径
```

每个 Chunk 应继承公告 ID、原始 URL、分类代码和页码。`document_search` 返回正文片段时，证据类型为 `document_excerpt`；只有标题级记录时，证据类型为 `reported_fact`，并注明 `content_level=index`。

不要把远程 URL 直接当作已经读取过的正文证据。

## 11. Agent 工作流

```text
用户问题
  -> Planner 判断需要事件时间线、公告原文或二者
  -> event_timeline 查询公告索引和结构化事件
  -> 如问题需要正文细节，则调用 document_search
  -> Evidence Guard 检查 content_level 和 assertion_status
  -> Answer Generator 区分标题级线索与正文确认事实
```

典型决策：

| 问题 | 工具策略 |
|---|---|
| “某公司最近有哪些违规相关公告？” | `event_timeline` 即可 |
| “某公司被处罚了多少钱？” | `event_timeline` 定位公告，再由 `document_search` 查正文 |
| “最近五年是否不存在处罚？” | 必须识别标题否定语义，最好查正文确认范围 |
| “处罚后财务风险如何变化？” | 事件、文档和财务工具联合调用 |

如果正文不存在，Agent 应返回 `partially_answered` 或 `insufficient_evidence`，并只陈述可确认的标题、日期和链接。

## 12. 证据设计

标题级证据 ID：

```text
EVID-ANN-<announcement_id>
```

标题级证据至少包含：

```json
{
  "announcement_id": "...",
  "company_id": "600000.SH",
  "announcement_date": "2025-01-01",
  "title": "...",
  "category_codes": ["5507060000"],
  "title_assertion": "neutral_index",
  "content_level": "index",
  "pdf_url": "..."
}
```

正文 Chunk 证据使用知识库的 Chunk 证据 ID，并保留 `announcement_id` 关联。标题级证据不能用于支持正文细节。

## 13. 与当前代码的适配缺口

现有 `event_timeline` 已支持 CSV 事件、时间过滤、聚类和证据生成，但正式接入比赛数据还需：

1. Excel 公告索引导入 SQLite；
2. 原始 `fcode` 多值分类表；
3. 标题否定、整改和进展状态；
4. 索引级与正文级证据区分；
5. 更宽的事件类型或原始分类保留字段；
6. SQLite `EventRepository`；
7. PDF 下载、校验和可恢复任务；
8. 公告正文与知识库 `document_id` 关联；
9. 防止标题推断正文事实的 Evidence Guard；
10. 对应单元测试和端到端测试。

---

## 14. 推荐实施顺序

1. 导入公告索引和分类表；
2. 实现按公司、日期和分类查询；
3. 接入 `event_timeline` 的标题级时间线；
4. 增加标题否定语义和 `content_level`；
5. 生成数据质量报告；
6. 确认授权后实现 PDF 下载器；
7. 将 PDF 解析进文档知识库；
8. 接入 `document_search`；
9. 实现正文事件抽取和标题级事件升级；
10. 增加跨工具分析和评测用例。

第一版应先把“公告索引查询”和“标题级时间线”做准确，再扩展正文下载。索引本身已经有价值，不应因为正文尚未准备就让整个事件工具不可用。

---

## 15. 最终原则

这组数据应被视为“违规与监管相关公告的候选索引”。FinTrace 可以利用它定位公告和构建可追溯时间线，但必须区分分类标签、标题陈述和正文确认事实。

系统宁可明确说明“目前只取得公告标题，无法确认处罚细节”，也不能把索引分类扩写成不存在的公告内容。
