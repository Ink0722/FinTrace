# FinTrace Agent 评测实施方案

## 1. 文档目的

本文档将竞赛要求转化为一套简单、明确、可执行的评测方案。评测只回答三个问题：

1. 完整 Agent 在长对话中能否正确回答、正确调用工具并从可恢复错误中恢复；
2. 股权穿透和事件时间线两个专项工具能否正确、及时地产生结构化结果；
3. 财务排雷模块能否识别问题财报，并生成可靠、无幻觉的分析报告。

评测过程统一遵循：

```text
准备测试集和金标
  -> 冻结 Agent、模型、工具和数据版本
  -> 运行完整 Agent 或指定工具
  -> 按预先确定的规则判分
  -> 输出指标和失败案例
```

多轮会话的输入输出字段见 [02-多轮评测方案.md](02-多轮评测方案.md)，赛方数据与工具的对应关系见 [01-数据与工具总览.md](01-数据与工具总览.md)。

## 2. 评测体系只保留三类、九项正式指标

### 2.1 三类评测

| 类别 | 被测对象 | 正式指标 |
|---|---|---|
| A. 完整 Agent 评测 | 从用户问题到最终回答的完整工作流 | 回答准确率、关键事实 Recall、工具调用 Precision、自纠错成功率 |
| B. 专项工具评测 | 股权穿透工具和事件时间线工具 | 股权穿透端到端准确率、事件节点 Recall、工具执行延迟达标率 |
| C. 财务排雷评测 | 财务风险规则和报告生成模块 | 财务风险 F1、报告专家盲评优秀率 |

一共九项正式指标，不再设置综合总分。

### 2.2 测试条件不是指标

以下内容只用于规定怎么测试，不单独计分：

- `10 轮以上`和`0.5M Tokens`是完整 Agent 的长对话测试条件；
- 文件夹 1、文件夹 2 等是数据来源；
- 人机一致率、平均延迟、错误类型分布用于解释结果，属于诊断信息；
- Prompt 版本、Token 成本、硬件环境用于复现，不属于能力指标。

这样可以避免把评测条件、工程日志和竞赛指标混为一谈。

### 2.3 九项指标总表

| 编号 | 指标 | 最小评测单位 | 目标 | 回答的问题 |
|---|---|---|---:|---|
| A1 | 回答准确率 | 一个 Turn | `>=90%` | 这一轮整体处理是否正确 |
| A2 | 关键事实 Recall | 一条核心事实 | `>=90%` | 应回答的核心事实是否完整出现 |
| A3 | 工具调用 Precision | 一次逻辑工具选择 | `>=92%` | 调用的工具是否必要且正确 |
| A4 | 自纠错成功率 | 一个可恢复故障案例 | `>=80%` | 发生可恢复错误后能否自主恢复 |
| B1 | 股权穿透端到端准确率 | 一个股权查询案例 | `>=85%` | 完整股权链是否全部正确 |
| B2 | 事件节点 Recall | 一个核心事件节点 | `>=85%` | 时间线关键节点是否完整 |
| B3 | 工具执行延迟达标率 | 一次有效工具执行 | `100%`在 5 秒内 | 工具自身执行是否满足 5 秒要求 |
| C1 | 财务风险 F1 | 一个公司报告期 | `>=85%` | 问题财报识别是否兼顾误报和漏报 |
| C2 | 财务报告优秀率 | 一份财务排雷报告 | `>=80%` | 报告是否正确、自洽且无幻觉 |

## 3. 数据如何支撑九项指标

| 数据 | 直接用途 | 不能直接完成的部分 |
|---|---|---|
| 文件夹 1：多轮问题集 | A1、A2、A3 的主测试集 | 文本规模不足 0.5M；没有故障脚本 |
| 文件夹 2：十大股东快照 | B1 的直接持股和部分路径案例 | 缺少大量三层以上完整控制链 |
| 文件夹 3：公告索引 | B2 的候选事件；C1 的问题样本线索 | 标题不能替代公告正文和最终标签 |
| 文件夹 4：财务报表 | C1 的财务指标计算和 C2 的报告输入 | 没有问题财报正负标签 |

因此需要补充三类测试数据：

1. **长对话压力集**：在文件夹 1 会话基础上加入经过标注的长文档和干扰事实，使累计历史达到 50K、100K、200K 和 500K Tokens；
2. **自纠错故障集**：为正常案例注入一次确定的可恢复故障；
3. **专项金标集**：补充深层股权链、公告正文事件节点和问题财报标签。

这些补充数据用于覆盖赛题指标，不取代文件夹 1 的原始多轮测试。

## 4. 金标怎么做

### 4.1 多轮问题金标

文件夹 1 的每个 Turn 至少标注以下内容：

```json
{
  "case_id": "SESSION-005-TURN-017",
  "session_id": "5",
  "turn_id": 17,
  "question": "太平洋保险最新净利润",
  "answerability": "answerable",
  "required_entities": ["601601.SH"],
  "required_period": "latest_available_as_of_cutoff",
  "valid_tools": ["financial_risk_analysis"],
  "gold_facts": [
    {
      "fact_id": "F-001",
      "entity": "601601.SH",
      "attribute": "net_profit",
      "period": "latest_available_as_of_cutoff",
      "expected": "<从冻结财务数据填写>",
      "unit": "CNY",
      "match_rule": "relative_tolerance",
      "tolerance": 0.001,
      "evidence_ids": ["<对应证据ID>"]
    }
  ]
}
```

上例中的尖括号内容是格式占位符，不是合法金标值。正式评测前必须替换为冻结数据中的真实数值和真实证据 ID。

各字段含义和标注要求如下：

| 字段 | 含义 | 标注要求 | 用于评测 |
|---|---|---|---|
| `case_id` | 当前案例的唯一标识 | 建议使用 `SESSION-{session_id}-TURN-{turn_id}`；生成后不得重复或随意修改 | 关联输入、金标、运行轨迹和评分结果 |
| `session_id` | 当前问题所属会话 | 直接使用文件夹 1 的原始会话编号；不同 Session 之间不共享上下文 | 多轮回放和会话隔离 |
| `turn_id` | 当前问题在 Session 中的顺序 | 按原始数据顺序填写，从 1 开始；不能因删除或筛选问题而重新改变原顺序 | 恢复会话历史、定位上下文来源 |
| `question` | 用户原始问题 | 保留原文，不纠正错别字、不补充实体、不改写成标准问法 | Agent 的正式输入 |
| `answerability` | 当前系统条件下 Agent 应如何处理问题 | 根据评测时冻结的数据、工具和问题必要参数判断，使用下文规定的三类标签 | A1 回答准确率中的处理方式判断 |
| `required_entities` | 正确完成任务必须识别的主体 | 使用规范化证券代码、公司 ID 或人物 ID；多主体问题按稳定顺序列出 | A1 实体正确性和 A3 参数正确性 |
| `required_period` | 正确回答所需的时间范围或报告期 | 尽量使用明确日期或报告期；`latest_available_as_of_cutoff`表示评测数据截止日时的最新可用期间 | A1 期间正确性和 A3 参数正确性 |
| `valid_tools` | 能为当前问题提供必要证据的工具集合 | 根据工具职责和冻结数据确定；不需要工具时填 `[]` | A3 工具调用 Precision |
| `gold_facts` | 答案必须正确包含的核心事实 | 每条事实单独记录实体、属性、值、期间、单位、容差和证据 ID；生成规则见 4.2 | A2 关键事实 Recall 及 A1 核心内容判断 |

空值应具有统一含义：

- 列表字段没有内容时使用 `[]`，不能使用空字符串；
- 当前问题没有时间条件时，`required_period`使用 `null`；
- 尚未完成标注的字段不能伪装成空值，应使用标注状态字段或留在待标注队列中；
- `gold_facts=[]`只适用于需要澄清或无法回答的案例，可回答问题不得为空；
- `valid_tools=[]`表示无需工具即可正确处理，不能表示“工具尚未标注”。

`answerability`只保留三类：

| 标签 | 含义 | Agent 应有行为 |
|---|---|---|
| `answerable` | 当前证据能够支持完整答案或有意义的部分答案 | 只回答有证据支持的内容；不能完整回答时同时说明限制 |
| `clarification_required` | 补充用户参数后可能回答，例如实体或时间存在歧义 | 提出具体澄清问题，不猜测缺失条件 |
| `unanswerable` | 当前系统缺少数据或能力，或问题要求收益保证、确定涨跌等不可靠结论 | 明确说明不能回答的原因，不生成确定性结论 |

判定顺序如下：

```text
是否缺少可由用户补充的必要参数？
  是 -> clarification_required
  否 -> 当前证据能否支持至少一个有意义的答案？
          是 -> answerable
          否 -> unanswerable
```

不再单独设置“部分可回答”标签。复合问题只有部分内容有证据时仍标为 `answerable`，`gold_facts`只记录可验证部分；评审同时检查答案是否明确披露未覆盖部分。安全预测也不单独成类，因为其合格行为与其他不可回答问题相同，均为说明原因并拒绝确定性结论。

多轮追问始终放在完整 Session 中评测。对于“那 2023 年呢”一类省略问题，标注员结合此前对话，直接在当前 Turn 的 `required_entities`、`required_period`和`gold_facts`中填写最终正确结果，不再额外标注继承关系或来源 Turn。Agent 若继承错误，最终实体、期间或事实无法匹配金标，A1 和 A2 会直接反映该错误。

### 4.2 核心事实如何产生

核心事实是：**如果缺失或错误，这一轮就没有真正回答用户的问题。**

例如“贵州茅台 2024 年净利润同比增长多少”的核心事实为：

- 公司是贵州茅台；
- 当前报告期是 2024 年；
- 对比期是 2023 年；
- 指标是净利润；
- 增长率数值及方向正确。

行业背景、投资建议和额外解释通常不是核心事实。额外内容可以不写，但写出来就不能出现错误数字或无证据结论。

核心事实不能由标注员自由撰写，按以下流程产生：

```text
根据问题确定实体、指标和期间
  -> 用冻结数据或独立查询脚本取得标准值
  -> 程序生成候选 gold_facts
  -> 标注员核对问题是否确实要求这些事实
  -> 第二人复核数值、单位、口径和证据
```

每条核心事实必须绑定原始数据或可核验证据，不能依据被测 Agent 的答案生成。数据只能支持部分内容时，仍标为 `answerable`并只记录可验证事实；完全无法提供有意义答案时标为 `unanswerable`。

为减少主观性，只允许以下内容进入 `gold_facts`：

- 用户直接询问的事实；
- 计算该答案不可缺少的期间、口径和比较基准；
- 回答复合问题时各个明确子问题的结果；
- 正确拒答所必须说明的缺失条件不放入 `gold_facts`，直接由 `answerability`及系统能力清单判断。

以下内容不标为核心事实：行业背景、投资建议、可有可无的解释、模型自行扩展的知识和答案表达形式。

### 4.3 专项金标

| 测试集 | 金标内容 |
|---|---|
| 自纠错 | 故障类型、是否可恢复、允许的修复动作、重试上限、正确最终结果 |
| 股权穿透 | 查询时点、完整节点、每跳方向、关系类型、比例和证据 |
| 事件时间线 | 核心事件、日期、主体、事件类型、所属事件簇和证据 |
| 财务风险 | 公司、报告期、正负标签、风险类型、标签依据和证据 |

### 4.4 人工标注流程

```text
程序预标注实体、日期、候选工具和候选证据
  -> 标注员 A 完成标注
  -> 标注员 B 复核关键字段
  -> 分歧由第三人或专家仲裁
  -> 冻结金标版本
  -> 开始正式测试
```

第一步先试标 100～200 个 Turn。只有当可回答性和核心事实的判定规则稳定后，再处理全量 1,410 个 Turn。

股权路径由熟悉企业关系数据的人员复核；财务风险标签由两名具备财务背景的人员独立标注，并由专家处理争议。金标冻结后不得根据 Agent 表现修改。

## 5. A 类：完整 Agent 指标

### 5.1 A1 回答准确率

#### 指标意义

回答准确率用于判断一个 Turn 是否被完整、可靠地处理。它不是语言风格分，也不是把多个维度加权平均。

#### 计算方法

```text
回答准确率 = 判定正确的 Turn 数 / 全部纳入评测的 Turn 数
```

一个 Turn 只有同时满足以下三条才算正确：

1. **处理方式正确**：该回答时回答，该澄清时澄清，该拒答时拒答；
2. **核心内容正确**：目标实体、时间和全部核心事实正确；
3. **没有严重错误**：没有编造关键数字、错误引用证据、错误继承上下文或把风险信号断言为造假事实。

原方案中的五项硬条件被合并为以上三条，避免重复判定。

#### 事实正确的边界

| 类型 | 判定边界 |
|---|---|
| 证券代码、日期、报告期、排名 | 与金标一致 |
| 公司或人物 | 指向同一规范实体；允许无歧义简称 |
| 金额 | 单位统一后相对误差不超过 0.1%，允许正常显示舍入 |
| 财务比例、增长率 | 绝对误差不超过 0.1 个百分点 |
| 持股比例 | 绝对误差不超过 0.01 个百分点 |
| 比较方向 | 增加、下降、高于、低于必须完全正确 |
| 文本事实 | 能被金标证据直接支持 |

原始数据精度低于上述标准时，以原始数据的有效精度为准。

#### 部分回答和拒答

- `answerable`案例可以是完整回答，也可以是有意义的部分回答；
- 只回答部分内容时，必须覆盖全部 `gold_facts`并明确说明未覆盖部分及原因；
- 无法回答时必须说明缺少的具体数据、参数或能力；
- 无数据却给出确定结论，或者有数据却无理由拒答，均判错。

#### 人工与 LLM 双重评估

1. 人工评审根据金标给出 `pass/fail`；
2. LLM 裁判在相同会话、工具结果和证据下独立判断；
3. 两者不一致时，由第二名人工评审仲裁；
4. 最终 `>=90%` 以仲裁后的结果为准。

不对人工分和 LLM 分取平均，因为二者判断冲突时，平均值没有明确语义。

### 5.2 A2 关键事实 Recall

#### 指标意义

回答准确率判断整轮是否合格；关键事实 Recall 专门检查答案是否遗漏用户真正需要的信息。二者不能互相替代。

#### 计算方法

只对 `answerable` Turn 计算：

```text
关键事实 Recall = 答案中正确出现的核心事实数 / 金标核心事实总数
```

实体、属性、值、时间和单位均符合金标，才算召回一条事实。该指标由人工依据 `gold_facts` 逐项勾选，LLM 只用于辅助定位答案中的候选事实。

### 5.3 A3 工具调用 Precision

#### 指标意义

该指标只判断 Agent **已经选择的工具是否选对**，不评价工具返回的数据是否正确。

#### 最小单位

一次“逻辑工具选择”为一个样本。同一工具因网络超时进行的原参数重试，仍算一次逻辑选择，避免把正常重试重复计数。

#### 计算方法

```text
工具调用 Precision = 正确工具选择数 / Agent 发起的全部逻辑工具选择数
```

满足以下条件才算正确：

- 工具属于该 Turn 的 `valid_tools`；
- 调用与当前问题有关；
- 公司、人物、期间等必要参数正确。

不需要工具却调用工具、选错工具、参数指向错误实体，均记为错误调用。

未调用必要工具不会降低 Precision，但会直接导致该 Turn 的回答准确率失败，因此不再新增正式的 Tool Recall 指标。开发阶段可以查看漏调用数量，但不纳入九项正式指标。

### 5.4 A4 自纠错成功率

#### 指标意义

自纠错只评价：发生**预先定义的可恢复错误**后，Agent 能否在不依赖用户的情况下恢复。它不是让 LLM 在回答后反思措辞，也不是无条件重试。

#### 可进入分母的故障

- Planner 漏选必要工具，但允许重新规划；
- 参数格式错误或遗漏必填参数；
- 可唯一修正的证券代码错误；
- 首次网络超时等临时故障；
- 工具结果缺少必要字段且允许重新获取；
- 当前证据不足，但存在明确可调用的补充工具。

没有数据源、超出数据时间范围、用户指代无法唯一确定、工具明确返回不可重试错误等情况不进入分母。此时正确行为是警告、澄清或拒答。

#### 成功边界

一个案例满足以下条件即为成功：

1. Agent 发现预设故障；
2. 采取金标允许的修复动作；
3. 未超过重试上限；
4. 最终得到正确的结构化工具结果；
5. 没有用 LLM 猜测代替工具结果。

```text
自纠错成功率 = 成功恢复的案例数 / 全部可恢复故障案例数
```

建议至少构造 100 个故障案例，并保证每种故障都有足够样本。需要用户补充信息的澄清不算自纠错成功。

## 6. B 类：专项工具指标

### 6.1 B1 股权穿透端到端准确率

#### 评测边界

```text
自然语言问题 -> Planner 解析参数 -> ownership 工具 -> 结构化股权路径
```

不评价最终回答 LLM 的措辞。

#### 成功边界

一个案例只有同时满足以下条件才算正确：

- 所有金标路径均被返回；
- 每条路径的实体、边方向和关系类型正确；
- 每跳持股或控制比例在允许误差内；
- 查询时点正确；
- 没有足以改变控制关系判断的错误路径。

```text
股权穿透端到端准确率 = 完整正确案例数 / 全部股权案例数
```

赛题要求链条中每一跳均正确，因此采用案例级完整匹配。逐跳准确率只用于开发定位，不作为正式指标。

### 6.2 B2 事件节点 Recall

#### 指标意义

该指标评价时间线是否漏掉核心阶段，不要求模型复述所有新闻和公告。

#### 核心事件节点

核心节点是删除后会导致事件发展过程不完整的节点，例如首次披露、监管问询、公司回复、立案调查、处罚决定和整改结果。重复转载不单独标为核心节点。

#### 计算方法

```text
事件节点 Recall = 正确返回的核心事件节点数 / 金标核心事件节点总数
```

主体、事件类型和日期均正确，并能关联到有效证据，才算召回。事件顺序错误、把不同事件错误合并或出现无依据因果关系时，该案例标记为“时间线不合格”，在报告中单独列出，但不再设计一套复杂的因果分数。

### 6.3 B3 工具执行延迟达标率

#### 评测边界

计时开始：合法 `ToolCall` 进入工具执行函数。

计时结束：查询、算法、证据和结构化 `ToolResult` 全部组装完成。

包含数据库或图查询、路径搜索、事件过滤或聚类、比例计算和结果组装；不包含 Planner LLM、最终回答 LLM、HTTP 传输及 CLI/Web 渲染。

#### 计算方法

```text
工具执行延迟达标率 = 执行时间 <= 5 秒的有效调用数 / 全部有效调用数
```

竞赛目标按“工具调用响应延迟不超过 5 秒”解释为达标率 `100%`。同时报告最大值用于证明没有单次超时；P50 和 P95 仅作为性能诊断，不再作为正式门槛。

只统计输入合法且数据服务正常的调用。人为注入的网络超时属于自纠错测试，不进入本指标。

## 7. C 类：财务排雷指标

### 7.1 先明确“财务风险”是什么

财务评测区分三个层次：

```text
指标异常 -> 风险信号 -> 经监管、审计或专家确认的问题财报
```

- 指标异常是可计算现象，例如利润增长但经营现金流下降；
- 风险信号是需要进一步核查的异常组合；
- 问题财报是用于 F1 金标的最终标签，需要监管、审计或专家证据支持。

FinTrace 可以提示“存在财务风险信号”，但不能仅根据一条规则断言“公司财务造假”。

### 7.2 财务风险金标

主评测单位为：

```text
company_id + report_period
```

每个样本使用以下标签：

| 标签 | 含义 | 是否进入 F1 |
|---|---|---:|
| `positive` | 该报告期存在经证据确认的问题风险 | 是 |
| `negative` | 经复核未发现目标问题风险 | 是 |
| `uncertain` | 证据冲突，无法确定 | 否 |
| `not_evaluable` | 缺少必要财务数据或附注 | 否 |

金标构造流程：

```text
从文件夹 3 筛选违规、差错更正、非标审计和问询候选
  -> 获取公告正文
  -> 确定受影响公司和报告期
  -> 与文件夹 4 的财务数据关联
  -> 两名财务标注员独立标注
  -> 专家仲裁
```

正样本优先采用监管或法院确认的虚假记载、重大会计差错更正、明确涉及目标风险的非标审计意见。监管问询只有在正文和专家判断均支持时才作为正样本。

负样本应从相同报告期、同行业和相近规模公司中选择并人工复核。“没有违规公告”不能直接等于负样本。

训练、开发和测试按公司划分，或者按时间划分，避免同一公司的相邻报告期同时出现在开发集和测试集。

### 7.3 C1 财务风险 F1

#### 指标意义

问题财报通常少于正常财报，只看准确率可能让系统通过全部预测为正常获得虚高成绩。F1 同时约束误报和漏报，因此使用 F1。

```text
Precision = TP / (TP + FP)
Recall = TP / (TP + FN)
F1 = 2 * Precision * Recall / (Precision + Recall)
```

主指标只判断每个公司报告期是否为 `positive`，目标为 `F1 >=85%`。风险类型只用于失败分析，不再将每类 F1、Macro-F1 等指标并列为正式指标。

财务工具必须输出：

```text
triggered
not_triggered
not_evaluable
```

缺少关联交易、附注或必要字段时必须输出 `not_evaluable`，不能当成未触发或低风险。

### 7.4 C2 财务报告专家盲评优秀率

#### 指标意义

F1 只检查风险标签是否识别正确；专家盲评检查报告中的数据、计算和结论是否可靠。

每份报告只评价四个必要维度，每项 0～2 分：

| 维度 | 0 分 | 1 分 | 2 分 |
|---|---|---|---|
| 数据与计算 | 核心数字或公式错误 | 存在轻微问题 | 数字、单位、期间、公式均正确 |
| 逻辑 | 结论与数据矛盾 | 部分解释不足 | 预警点、数据和归因连贯 |
| 证据 | 重要结论无证据 | 部分可追溯 | 重要结论均可追溯 |
| 审慎与完整 | 断言造假或缺少关键内容 | 边界说明不足 | 明确风险边界且内容完整 |

总分为 8 分。一份报告同时满足以下条件才算优秀：

- 总分不低于 7 分；
- “数据与计算”和“证据”均为 2 分；
- 没有编造数字、公司或期间错误、错误公式、伪造证据、缺数据却判断低风险、将风险信号认定为造假等红线错误。

```text
财务报告优秀率 = 优秀报告数 / 全部盲评报告数
```

建议抽取 50～100 份报告，由两名金融背景专家独立评分；意见不一致时由第三名专家仲裁。目标为 `>=80%`。

## 8. 评测怎么运行

### 8.1 运行前冻结

正式评测前记录并冻结：

- Agent 代码版本；
- 回答、Planner 和 Embedding 模型；
- Prompt、工具和知识库版本；
- 数据截止时间和金标版本；
- 温度、超时、重试上限和随机种子；
- 硬件及网络环境。

### 8.2 完整 Agent 回放

```text
加载 Session 1 -> 按原顺序执行全部 Turn -> 清空状态
加载 Session 2 -> 按原顺序执行全部 Turn -> 清空状态
...
加载 Session 35 -> 按原顺序执行全部 Turn -> 清空状态
```

同一 Session 内不提示话题是否切换，不提示是否继承上下文，也不提示该调用什么工具。每轮保存输入、解析上下文、计划、工具轨迹、证据、最终回答、错误和耗时。

长对话压力集使用相同流程，只改变累计历史规模。A1 和 A2 分别在原始多轮集和 50K、100K、200K、500K 压力集上报告，`0.5M`不单独计算新指标。

### 8.3 专项运行

- 自纠错集固定故障脚本和随机种子；
- 股权、事件工具只运行到结构化工具结果；
- 财务风险模块先输出风险标签，再生成专家盲评报告；
- 原始比赛数据保持只读，测试输入、金标和运行结果分别保存。

## 9. 人工、程序和 LLM 分工

| 内容 | 主要判定者 | 原因 |
|---|---|---|
| 工具名称、参数、数字、日期、证据 ID | 程序 | 可以精确复现 |
| 股权路径、事件节点、财务 F1 | 程序对照人工金标 | 结构化结果可直接比较 |
| 核心事实是否完整、上下文是否误用 | 人工，LLM 辅助 | 需要结合问题语义 |
| Turn 是否整体正确 | 人工 + LLM，冲突时人工仲裁 | 满足赛题双重评估要求 |
| 财务报告质量 | 金融专家 | 涉及专业逻辑和风险边界 |

LLM 裁判只能依据金标、工具结果和证据判断，不能使用自身知识替 Agent 补全事实。程序发现的硬错误优先于 LLM 的主观评分。

人机一致率、仲裁比例和各类失败数量只作为评测可信度说明，不新增为竞赛指标。

## 11. 实施顺序

1. 将文件夹 1 转为按 Session 和 Turn 排序的 JSONL；

## 12. 最终原则

本方案只保留赛题明确要求且能够解释的九项指标。每项指标都具有唯一的评测对象、样本单位、分子、分母和通过边界。

FinTrace 的目标不是强行回答所有问题，而是做到：有证据时准确回答，需要工具时正确调用，可恢复错误时自主修复，无法可靠处理时明确警告，并始终避免把财务风险信号夸大为造假事实。
