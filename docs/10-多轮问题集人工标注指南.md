# FinTrace 多轮问题集人工标注指南

## 1. 指南用途

本指南供参与 FinTrace 第 1 组多轮问题集标注的金融专业同学使用。标注目标不是替 Agent 写一份“标准答案”，而是确定每一轮问题：

1. 当前系统是否能够回答；
2. 问题实际指向哪个主体；
3. 问题要求哪个日期或时间范围；
4. 应使用哪些工具；
5. 如果需要检索公告或研报，哪些 Chunk 是回答所必需的。

标注完成后，这些字段将用于评价 Agent 的回答决策、上下文理解、工具调用和文本检索是否正确。

本指南是第 1 组问题集人工标注的直接执行依据。其他评测文档中的早期字段设计如与本文不一致，以本文为准。

---

## 2. 数据集概况

第 1 组问题集当前包含：

| 内容 | 数量 |
|---|---:|
| Session | 35 个 |
| Turn | 1,410 个 |
| 原始字段 | `session_id`、`question`、`think_flag` |

一个 `session_id` 代表一段完整对话。同一 Session 内的问题必须按照原始顺序处理，不同 Session 之间不共享上下文。

标注文件基于原始 `questions.jsonl` 扩展，但不直接覆盖原始文件：

```text
原始文件：data/jsonl/questions.jsonl
标注文件：evaluation/annotations/questions_annotated_v1.jsonl
```

原始文件只读。所有人工标注都写入标注文件。

## 3. 标注前会提供的材料

正式标注开始前，项目负责人需要向标注员提供并冻结以下内容：

| 材料 | 用途 |
|---|---|
| 数据截止日期 | 解释“今天”“最新”“当前”等相对时间 |
| Agent 能力清单 | 判断问题是否可回答 |
| 工具清单及说明 | 选择 `valid_tools` |
| Chunk 数据库及查看工具 | 选择 `required_chunk_ids` |
| 公司名称与证券代码表 | 统一 `required_entities` |
| 标注文件版本 | 防止不同批次互相覆盖 |

不得根据个人常识假设系统具有某个行情、账户或搜索接口。是否可回答，只能根据本批次冻结的能力清单判断。

## 4. 最终标注格式

所有标注字段与原始字段平级，不使用嵌套的 `annotation` 对象。

```json
{
  "case_id": "SESSION-005-TURN-017",
  "session_id": "5",
  "turn_id": 17,
  "question": "查询这家公司2024年净利润",
  "think_flag": false,
  "annotation_status": "completed",
  "answerability": "answerable",
  "required_entities": ["600000.SH"],
  "required_date": "2024-12-31",
  "valid_tools": ["financial_risk_analysis"],
  "required_chunk_ids": []
}
```

### 4.1 字段说明

| 字段 | 谁产生 | 如何填写 |
|---|---|---|
| `case_id` | 程序生成 | `SESSION-{session_id}-TURN-{turn_id}` |
| `session_id` | 原始数据 | 不修改 |
| `turn_id` | 程序生成 | 当前问题在 Session 内的顺序，从 1 开始 |
| `question` | 原始数据 | 不纠错、不补充、不改写 |
| `think_flag` | 原始数据 | 原样保留，不作为正确答案 |
| `annotation_status` | 标注员 | 标注状态，见下文 |
| `answerability` | 标注员 | `answerable`、`clarification_required` 或 `unanswerable` |
| `required_entities` | 标注员 | 正确理解问题所需的主体列表 |
| `required_date` | 标注员 | 单一目标日期、报告期截止日或时间范围截止日 |
| `valid_tools` | 标注员 | 能够合理完成问题的工具列表 |
| `required_chunk_ids` | 标注员 | 文本回答必须检索到的最小 Chunk 集合 |

### 4.2 标注状态

`annotation_status` 只使用：

| 状态 | 含义 |
|---|---|
| `pending` | 尚未标注 |
| `completed` | 已完成且标注员认为无争议 |
| `review_required` | 存在歧义、缺少 Chunk 或无法独立判断，需要复核 |

不得用空数组或 `null` 假装一个尚未标注的案例已经完成。

## 5. 每一轮的固定标注顺序

标注每个 Turn 时，严格按照以下顺序操作：

```text
阅读当前 Turn 之前的完整对话
  -> 判断应回答、澄清还是拒答
  -> 确定主体
  -> 确定日期或时间范围
  -> 选择有效工具
  -> 必要时选择 Chunk
  -> 完成自检
  -> 设置 annotation_status
```

这个顺序很重要。不要先搜索 Chunk，再根据搜到的内容倒推问题是什么意思。

### 5.1 只能使用此前对话

标注当前 Turn 时可以查看：

- 当前问题；
- 当前 Session 中更早的 Turn。

不能使用后续 Turn 帮助理解当前问题。因为 Agent 在真实运行时也看不到未来问题。

## 6. 如何标注 Answerability

`answerability` 只保留三类。

### 6.1 `answerable`

满足以下条件时标为 `answerable`：

- 问题的必要主体和时间已经明确；
- 冻结的数据和工具能够支持实质答案；
- 回答不需要猜测用户账户、实时行情或未来涨跌；
- 能够提供至少一个真正回应用户需求的结果。

示例：

```text
贵州茅台2024年净利润是多少？
```

如果冻结财务数据包含该公司和报告期，应标为 `answerable`。

### 6.2 `clarification_required`

缺少的信息可以由用户补充，而且不补充就存在多个合理答案时，标为 `clarification_required`。

示例：

```text
分析一下这家公司。
```

如果此前对话没有唯一公司主体，应要求用户说明公司。

再如：

```text
它的净利润怎么样？
```

如果此前同时讨论了两家公司，“它”无法唯一确定，也应标为 `clarification_required`。

不要为了提高可回答比例而自行选择最可能的公司。

### 6.3 `unanswerable`

即使问题本身表达清楚，当前系统仍没有数据、权限或可靠方法回答时，标为 `unanswerable`。

常见情况包括：

- 查询实时涨停、即时股价或实时资金流，但系统没有实时行情；
- 查询用户自选股、持仓、收益或银行卡，但系统没有账户权限；
- 要求保证收益、确定未来涨跌或给出必然成功的交易指令；
- 查询的数据不在冻结数据范围内；
- 所需工具在当前版本中不存在。

示例：

```text
今天自选股涨最多的是哪一只？
```

如果系统既没有用户自选股权限，也没有实时行情，应标为 `unanswerable`，而不是 `clarification_required`。让用户补充公司名称也不能使系统获得其账户数据。

### 6.4 复合问题

一个问题包含多个子问题时，先判断系统能否回答其主要请求：

- 主要请求可以得到有意义答案：标为 `answerable`；
- 只能回答无关紧要的边缘部分：标为 `unanswerable`；
- 缺少用户可补充的关键条件：标为 `clarification_required`。

拿不准时使用 `review_required`，不要自行创造第四种 Answerability。

## 7. 如何标注主体

`required_entities` 表示正确处理当前问题必须识别出的公司、人物或机构。

### 7.1 A 股上市公司

统一使用带交易所后缀的六位证券代码：

```text
上海证券交易所：600519.SH
深圳证券交易所：000001.SZ
北京证券交易所：920088.BJ
```

即使问题使用公司简称，也要填写标准证券代码。

### 7.2 多主体问题

比较问题需要列出全部主体：

```json
"required_entities": ["600519.SH", "000858.SZ"]
```

列表顺序应与问题中的出现顺序一致。

### 7.3 人物和非上市机构

没有统一证券代码的人物或机构，使用无歧义的正式名称：

```json
"required_entities": ["王旭宁"]
```

```json
"required_entities": ["某某投资管理有限公司"]
```

不要自行编造人物 ID 或公司代码。

### 7.4 没有主体要求

市场整体、一般金融知识、账户操作等问题可以使用：

```json
"required_entities": []
```

### 7.5 六位数字问题

原始数据中有 24 条 `question` 是整数形式的六位证券代码，例如：

```json
"question": 300285
```

不要修改原始值。理解问题时将其视为字符串 `"300285"`，并结合此前对话判断用户意图。可以确定主体时填写：

```json
"required_entities": ["300285.SZ"]
```

仅有代码但无法判断用户想查询什么时，通常应标为 `clarification_required`。

## 8. 如何处理多轮上下文

本项目不标注 `context_relation` 或 `context_dependencies`。标注员只填写当前轮最终应采用的主体、日期、工具和 Chunk。

### 8.1 正确继承

```text
Turn 10：分析贵州茅台2024年业绩。
Turn 11：那2023年呢？
```

Turn 11 应标为：

```json
{
  "required_entities": ["600519.SH"],
  "required_date": "2023-12-31"
}
```

不需要额外记录“公司来自 Turn 10”。

### 8.2 话题切换

```text
Turn 10：分析贵州茅台2024年业绩。
Turn 11：如何修改银行卡？
```

Turn 11 不得继续填写贵州茅台。应按照账户业务问题独立判断：

```json
{
  "required_entities": [],
  "answerability": "unanswerable"
}
```

### 8.3 重复问题

重复问题仍然是独立 Turn，必须逐条标注，不能删除或合并。它们用于测试 Agent 在相同上下文下回答是否稳定。

## 9. 如何标注日期

所有日期采用：

```text
YYYY-MM-DD
```

### 9.1 日期和报告期

使用 `required_date`：

| 问题时间 | 标注结果 |
|---|---|
| 2024 年年报 | `2024-12-31` |
| 2024 年一季度 | `2024-03-31` |
| 2024 年半年报 | `2024-06-30` |
| 2024 年三季度 | `2024-09-30` |
| 2024 年 5 月 20 日公告 | `2024-05-20` |

对应格式：

```json
"required_date": "2024-12-31"
```

### 9.2 时间范围

时间范围只记录截止日期，不再单独标注起始日期：

```text
分析公司2022年至2024年的变化。
```

```json
"required_date": "2024-12-31"
```

起始年份“2022年”已经保留在原始问题中，评测最终回答时仍需检查 Agent 是否正确理解完整范围。`required_date` 只承担统一时间锚点和工具截止日期校验，不重复保存问题中的全部时间表达。

### 9.3 “今天”“当前”和“最新”

相对时间必须按照本批次冻结的数据截止日期转换为具体日期，不能继续填写 `today` 或 `latest`。

假设本批次截止日期为 `YYYY-MM-DD`：

```json
"required_date": "YYYY-MM-DD"
```

这里表示“截至该日期查询最新可用信息”，不表示最新数据一定发布于截止日当天。

### 9.4 无时间要求

填写 `null`：

```json
"required_date": null
```

不要使用空字符串。

## 10. 如何选择工具

`valid_tools` 表示能够合理完成当前问题的工具。当前核心工具如下：

| 工具 | 适用问题 |
|---|---|
| `financial_risk_analysis` | 财务指标、跨表勾稽、财务风险和异常信号 |
| `ownership_penetration` | 股东、持股关系、控制链和股权穿透 |
| `document_search` | 公告正文、研报摘要和文本事实检索 |
| `event_timeline` | 公司事件、监管事件和时间线整理 |

### 10.1 选择原则

- 只选择解决问题真正需要的工具；
- 不要因为工具“可能有点关系”就加入列表；
- 一个工具足够时不要机械选择多个工具；
- 复合问题确实需要多个能力时可以填写多个工具；
- 工具顺序按照正常执行顺序填写；
- 当前系统没有相应工具时，不得虚构工具名称。

### 10.2 不需要工具

以下情况通常使用空数组：

```json
"valid_tools": []
```

- 需要用户澄清；
- 当前系统无法回答；
- 一般金融概念能够直接解释且不依赖外部事实。

### 10.3 常见选择

| 问题 | 工具 |
|---|---|
| 2024 年净利润和现金流是否背离 | `financial_risk_analysis` |
| 某自然人如何间接控制上市公司 | `ownership_penetration` |
| 查询最新监管公告原文 | `document_search` |
| 梳理公司近三年处罚事件 | `event_timeline`，必要时加 `document_search` |
| 今天涨停股票 | 当前无实时工具时为空，并标 `unanswerable` |
| 我的自选股收益 | 当前无账户工具时为空，并标 `unanswerable` |

## 11. 如何选择 Chunk

`required_chunk_ids` 只用于必须从文本知识库取得信息的问题，例如公告和研报摘要检索。

### 11.1 选择标准

选择的 Chunk 必须：

- 与问题主体一致；
- 与问题日期或时间范围一致；
- 直接包含回答所需信息；
- 是完成回答不可缺少的最小集合；
- 来自本批次冻结的 Chunk 版本。

示例：

```json
"required_chunk_ids": [
  "ANN-205442600-C001"
]
```

### 11.2 不要多选

如果一个 Chunk 已经完整支持答案，不要把同一公告的所有 Chunk 都选入。多选会错误提高检索难度，也会让关键内容 Recall 失去明确含义。

### 11.3 多个 Chunk

问题包含多个必要答案点，且这些内容分布在不同 Chunk 时，可以选择多个：

```json
"required_chunk_ids": [
  "ANN-205442600-C001",
  "ANN-205442600-C003"
]
```

列表中的每一个 Chunk 都应当是必要的，而不是相互替代的搜索结果。

### 11.4 什么时候留空

以下情况使用空数组：

- 财务工具直接读取结构化财务数据；
- 股权工具直接读取结构化关系数据；
- 需要澄清；
- 无法回答；
- 不依赖知识库的一般概念问题。

### 11.5 找不到合适 Chunk

如果问题理论上可回答，但冻结知识库没有直接支持答案的 Chunk：

- 不得选择只与主题相关但不支持结论的 Chunk；
- 不得自己编造 Chunk ID；
- 将 `annotation_status` 设置为 `review_required`；
- 交由复核人员判断是数据缺失、Chunk 切分问题还是应改为 `unanswerable`。

## 13. 常见错误

### 13.1 根据个人知识判断系统能力

错误做法：认为行情在互联网上能查到，就把实时行情问题标为可回答。

正确做法：只根据冻结工具和数据判断。

### 13.2 看到熟悉公司就自行补全主体

错误做法：问题中的简称存在多个对应公司，标注员按个人理解选一个。

正确做法：无法唯一确定时标为 `clarification_required`。

### 13.3 机械继承上一轮公司

错误做法：上一轮讨论贵州茅台，后续所有 Turn 都继续填写 `600519.SH`。

正确做法：每一轮重新判断当前问题是否仍然指向该公司。

### 13.4 把未来对话用于当前标注

错误做法：根据 Turn 15 的内容解释 Turn 10 中原本存在歧义的“它”。

正确做法：标注 Turn 10 时只能查看 Turn 1 至 Turn 10。

### 13.5 把相关 Chunk 当作必要 Chunk

错误做法：Chunk 提到了同一家公司，就加入 `required_chunk_ids`。

正确做法：Chunk 必须直接包含回答所需信息。

### 13.6 为结构化问题强行寻找 Chunk

错误做法：净利润问题明明由财务工具读取结构化数据，却为了填字段随便选择一篇研报。

正确做法：使用财务工具，并把 `required_chunk_ids` 留空。

### 13.7 修改原始问题

错误做法：修正错别字、补充公司名称、把数字证券代码改成文本。

正确做法：保留原始 `question`，只在标注字段中表达正确理解。

## 14. 自检清单

每个 Turn 提交前检查：

- 是否只使用了此前对话，没有查看未来 Turn；
- Answerability 是否依据冻结能力判断；
- 主体是否唯一且代码格式正确；
- 日期是否转换为具体的 ISO 日期；
- 时间范围是否使用范围截止日期；
- 工具是否真正必要；
- Chunk 是否直接支持答案；
- 结构化问题是否错误选择了文本 Chunk；
- 没有时间要求时 `required_date` 是否填写 `null`；
- 所有无需 Chunk 或工具的字段是否填写空数组；
- 存在疑问时是否使用 `review_required`，而不是猜测。

全部通过后，才将：

```json
"annotation_status": "completed"
```

---

## 15. 试标、复核与仲裁

### 15.1 试标

正式全量标注前，先选择若干完整 Session，形成约 150 至 200 个 Turn 的试标集。不能随机抽取孤立 Turn。

两名标注员独立完成试标，重点检查：

| 项目 | 建议目标 |
|---|---:|
| Answerability 一致性 | Cohen's Kappa 不低于 0.80 |
| 主体和日期一致率 | 不低于 95% |
| 工具集合一致率 | 不低于 90% |
| Chunk 复核通过率 | 不低于 90% |

未达到目标时，应先统一规则和示例，再开始全量标注。

### 15.2 全量标注

```text
标注员 A 按完整 Session 标注
  -> 标注员 B 复核全部关键字段
  -> 分歧案例设置 review_required
  -> 金融或数据负责人仲裁
  -> 冻结标注版本
```

同一 Session 应尽量由同一名主标注员连续完成，避免不同人员对上下文产生不同理解。

### 15.3 仲裁原则

仲裁只依据：

- 原始会话；
- 冻结数据；
- 冻结工具能力；
- 冻结 Chunk；
- 本指南。

不得查看被测 Agent 的答案后再决定金标。金标一旦冻结，只有发现数据或标注错误时才能通过新版本修订，并保留修改记录。

---

## 16. 标注结果如何用于评测

### 16.1 回答准确率

一个 Turn 同时满足以下条件才算处理正确：

1. 应回答、澄清或拒答的方式正确；
2. 主体和日期正确；
3. 工具选择和参数正确；
4. 文本问题使用了必要 Chunk；
5. 最终回答没有无依据的重要数字或结论。

### 16.2 文本关键内容 Recall

对于存在 `required_chunk_ids` 的问题：

```text
必要 Chunk 覆盖率
= 正确检索并使用的必要 Chunk 数
/ required_chunk_ids 总数
```

它是关键事实 Recall 在文本检索场景中的证据化实现。

### 16.3 工具调用 Precision

Agent 调用的工具必须属于 `valid_tools`，且实体和日期参数与标注一致。没有必要却调用工具、调用错误工具或把参数指向错误公司，都属于错误调用。

---

## 17. 最后原则

高质量标注不追求让更多问题变成“可回答”，而追求每一个判断都能够被数据和规则解释。

遇到不确定情况时，请遵循：

```text
不猜公司
不猜日期
不猜工具
不猜 Chunk
不根据 Agent 输出反推金标
```

宁可将案例提交复核，也不要填写一个看起来完整但无法证明的标签。
